## 論文概要（Abstract）

ツール拡張型LLMサービスでは、固定ワークフローは予測可能だが柔軟性に欠け、ReActのような自由形式ループは過剰なツール呼び出しやトークン消費を招く。著者らは、エージェントオーケストレーションを**コスト考慮型の逐次意思決定問題**として定式化し、5つのアクション（respond, retrieve, tool_call, verify, stop）から成るコンパクトなアクション空間上で、推定利得・ステップコスト・不確実性・冗長性を統合したユーティリティ関数による行動選択ポリシーを提案している。HotpotQAにおける実験では、意味的冗長性制御により最大10.6%のトークン削減を達成したと報告されている。本手法はIEEE JCC 2026（福岡）に採録された。

この記事は [Zenn記事: AutoGenからAgent Frameworkへ：自律エージェント移行実践ガイド](https://zenn.dev/0h_n0/articles/c5509c723c2670) の深掘りです。

## 背景と動機（Background & Motivation）

Zenn記事で解説したAutoGenやAgent Frameworkをはじめ、LLMエージェントフレームワークではツール呼び出しの**オーケストレーション**（いつ、どのツールを呼ぶか）が中核的な設計判断となる。現行のアプローチには以下の2つのパラダイムがある。

**固定ワークフロー型**（MetaGPT、ChatDev、AutoGen、DSPy）：クエリの難易度に関係なく同じ手順を実行するため、予測可能だがアダプティブでない。簡単なクエリでも不要なステップを実行し、困難なクエリでは追加の検索が必要でも対応できない。

**自由形式ループ型**（ReAct、Toolformer、Gorilla、ToolLLM）：LLM自身が次のアクションを決定するため柔軟だが、長いトラジェクトリ、冗長なツール呼び出し、トークンとレイテンシの増加を招きやすい。

著者らはこの問題を3点に整理している：（1）**適応性の限界**：固定パイプラインは限界効用に応じた調整ができない、（2）**過剰実行**：自由形式ループは精度に見合わないトークン消費を招く、（3）**暗黙的な停止判定**：プロンプト駆動の停止は品質-コストの検査が困難。

## 主要な貢献（Key Contributions）

著者らは以下の4点を貢献として挙げている：

- **貢献1**: エージェントオーケストレーションを、プロンプト依存の暗黙的動作から**明示的なユーティリティ誘導型意思決定プロセス**へ移行させるフレームワークの提案
- **貢献2**: 推定利得（Gain）、ステップコスト（StepCost）、不確実性（Uncertainty）、冗長性（Redundancy）を統合した**ユーティリティベースの行動選択**メカニズム
- **貢献3**: HotpotQAデータセットでの制御実験により、意味的冗長性制御で**最大10.6%のトークン削減**を達成（論文Table IVより）
- **貢献4**: コスト定義（ステップコスト vs. トークンコスト vs. レイテンシコスト）、冗長性制御、アブレーションの分析

著者らは、本手法が「普遍的に最高の精度を達成するオプティマイザではなく、解釈可能で防御可能な制御メカニズム」であると明示的に位置づけている。

## 技術的詳細（Technical Details）

### アクション空間と問題定式化

クエリ$q$に対し、ステップ$t$で状態$s_t$を観測し、以下の5つのアクションから選択する：

$$
\mathcal{A} = \{\text{respond}, \text{retrieve}, \text{tool\_call}, \text{verify}, \text{stop}\}
$$

ここで、
- $\text{respond}$: 現在の状態から回答を生成
- $\text{retrieve}$: 外部エビデンスを取得
- $\text{tool\_call}$: 外部APIや計算ツールを呼び出し
- $\text{verify}$: 現在の回答やエビデンスを検証
- $\text{stop}$: 実行を終了

著者らは、verifyとstopを明示的なアクションとしてモデル化することで、retrieveやrespondと同じユーティリティスケールで比較可能にしている点が設計上の特徴であると述べている。

### 状態表現

状態$s_t$は以下の4要素で構成される：

1. **元のクエリと作業コンテキスト**
2. **過去のアクションと中間推論トレース**
3. **検索やツールから返されたオブザベーション**
4. **実行ステータス信号**（ステップカウント、バジェットメタデータ等）

状態は構造化された制御インタフェースとして設計されており、プロンプトの膨張を防ぐようコンパクトに保たれる。

### ユーティリティ関数（Eq. 2）

各候補アクション$a$の状態$s_t$におけるユーティリティは以下で定義される：

$$
U(a \mid s_t) = \text{Gain}(a \mid s_t) - \lambda_1 \cdot \text{StepCost}(a \mid s_t) - \lambda_2 \cdot \text{Uncertainty}(a \mid s_t) - \lambda_3 \cdot \text{Redundancy}(a \mid s_t)
$$

ここで、
- $\text{Gain}(a \mid s_t)$: アクション$a$の推定限界利得。エビデンスが不十分なときretrieveやtool\_callで高く、十分なときrespondやstopで高い
- $\text{StepCost}(a \mid s_t)$: 追加ステップのコスト正規化プロキシ。正確なトークン数やレイテンシはアクション完了前には未知のため、近似値を使用
- $\text{Uncertainty}(a \mid s_t)$: 現在のエビデンスが十分かの自己推定信頼度。高い不確実性は早期終了にペナルティを与え、積極的すぎる停止を防止
- $\text{Redundancy}(a \mid s_t)$: 過去のアクションと意味的に類似した繰り返しへのペナルティ
- $\lambda_1, \lambda_2, \lambda_3$: 重み係数。コスト、不確実性、冗長性ペナルティの相対的強度を制御

### 行動選択規則（Eq. 3）

$$
a_t^* = \arg\max_{a \in \mathcal{A}} U(a \mid s_t)
$$

すべての候補アクションが同一テンプレートでスコアリングされるため、各選択をコンポーネント値と重みまで遡って追跡できる。

### 設計上の判断：ヒューリスティック vs. 学習ポリシー

著者らは、このユーティリティ関数が**ヒューリスティック**であり、最適なRLポリシーや校正された確率を出力するものではないと明記している。学習ベースのポリシーは追加の訓練データ、安定した報酬定義、ツール価格やSLO変更時の再訓練を必要とする。対照的に、本手法ではオペレータが$\lambda$パラメータを調整することでトレードオフを制御できる。例えば、低レイテンシサービスではコスト重みを上げ、分析志向サービスでは不確実性制御を強化するといった運用が可能である。

### 冗長性制御の2方式

| 方式 | 検出対象 | オーバーヘッド | トークン削減 |
|------|---------|-------------|------------|
| **完全一致** | 同一アクション・同一検索文字列の繰り返し | 低い | 限定的 |
| **意味的一致** | パラフレーズや意味的に類似したアクション | 高い（エンベディング比較） | 論文Table IVより最大10.6% |

### アルゴリズム

```python
from dataclasses import dataclass
from typing import Literal

Action = Literal["respond", "retrieve", "tool_call", "verify", "stop"]

@dataclass
class State:
    """オーケストレーションの状態表現"""
    query: str
    context: str
    actions_history: list[str]
    observations: list[str]
    step_count: int
    budget_remaining: int

def compute_utility(
    action: Action, state: State,
    lambda1: float = 0.3, lambda2: float = 0.2, lambda3: float = 0.2,
) -> float:
    """ユーティリティ関数によるアクションスコアリング"""
    gain = max(0.0, min(1.0, estimate_gain(action, state)))
    cost = max(0.0, min(1.0, estimate_step_cost(action, state)))
    unc = max(0.0, min(1.0, estimate_uncertainty(action, state)))
    red = max(0.0, min(1.0, estimate_redundancy(action, state)))
    return gain - lambda1 * cost - lambda2 * unc - lambda3 * red

def orchestration_loop(query: str, max_steps: int = 10) -> str:
    """ユーティリティ誘導型オーケストレーションループ"""
    state = State(query=query, context="", actions_history=[],
                  observations=[], step_count=0, budget_remaining=max_steps)
    actions: list[Action] = ["respond", "retrieve", "tool_call", "verify", "stop"]
    while state.step_count < max_steps:
        scores = {a: compute_utility(a, state) for a in actions}
        action = max(scores, key=scores.get)
        if action == "stop":
            break
        obs = execute_action(action, state)
        state.observations.append(obs)
        state.actions_history.append(action)
        state.step_count += 1
    return generate_final_answer(state)
```

著者らの実装では、LLMがヒューリスティック信号（gain, uncertainty等）を推定し、コントローラが行動選択のみを担当する分離設計を採用している。コントローラはモデルやリトリーバとは独立しており交換可能であると述べている。

## 実装のポイント（Implementation）

### コントローラの分離設計

LLMはあくまで推論トレースとツール引数の生成を担当し、**どのオペレーションを次に実行するか**はコントローラが決定する。この分離により、以下の利点がある：

- LLMのプロンプトにオーケストレーションロジックを埋め込む必要がない
- コントローラのパラメータ（$\lambda$値）はLLMの再訓練なしに調整可能
- 実行ログに各アクションのコンポーネントスコアが記録され、長いトラジェクトリの原因を特定できる

### 自己推定信号の[0, 1]クリッピング

各ヒューリスティック信号はLLMの自己推定に依存するため、**[0, 1]にクリッピング**される。これにより、単一の異常値がスコア全体を支配することを防止する。ただし、著者ら自身が認めているように、これらは校正された確率ではなく、あくまでヒューリスティックである。

### 異種ツールへの拡張可能性

著者らは、同一の定式化がローカル検索、リモートAPI、データベースアクセス、コード実行、追加モデル呼び出しなどの異種ツールに対応可能であると主張している。コストの安いローカル検索はより頻繁に許容し、高価なリモートAPIはより高いgainまたはuncertaintyを要求するといった制御が想定されている。ただし、**現在の実装はBM25による単一のリトリーバルインタフェースのみ**を使用しており、マルチツール環境での検証は今後の課題として残されている。

## 実験結果（Results）

### 実験設定

著者らは以下の環境で実験を実施している：
- **データセット**: HotpotQA開発セットから**200サンプル**を使用
- **ハードウェア**: Ubuntu 22.04.5、Intel Xeon Gold 6330×2、1TB RAM、NVIDIA A800-SXM4-40GB×8
- **推論サービス**: vLLMベースのOpenAI互換エンドポイント
- **検索**: HotpotQAコーパス上のローカルBM25インデックス
- **評価指標**: F1スコア、トークン消費量、ウォールクロック時間、効率性（F1/tokens）

### 主要結果（論文Table Iより）

| 手法 | F1 | トークン数 | 時間(s) | 効率性 |
|------|-----|----------|--------|--------|
| direct | 0.0719 | 93.0 | 0.122 | 0.000772 |
| workflow (minimal) | 0.1625 | 451.2 | 0.461 | 0.00036 |
| workflow-search-twice | 0.1698 | 514.1 | 0.902 | 0.00033 |
| workflow-search-verify | 0.063 | 1041.2 | 1.617 | 6.1e-05 |
| threshold | 0.1255 | 350.3 | 0.394 | 0.000358 |
| ReAct | **0.2662** | 546.6 | 0.56 | **0.000487** |
| policy (step-cost) | 0.236 | 1294.2 | 1.138 | 0.000182 |

著者らによると、ReActがF1で最高値（0.2662）を記録しており、自由形式のマルチステップ推論の価値を確認している。ユーティリティポリシー（step-cost）はF1 0.236で、ReActには及ばないものの、解釈可能な品質-コストコントローラとしての位置づけであると主張している。

**重要な注意点**: 論文Table Iにおいて、ユーティリティポリシーのトークン消費（1294.2）はReAct（546.6）の約2.4倍であり、効率性指標でもReActに劣る。著者らはこの点について「普遍的に最高の精度を達成するオプティマイザではない」と認めており、価値は**解釈可能性と$\lambda$パラメータによる制御可能性**にあると主張している。

### コスト定義の比較（論文Table IIより）

| コスト定義 | F1 | トークン数 | 効率性 |
|-----------|-----|----------|--------|
| step-cost | 0.236 | 1294.2 | 0.000182 |
| token-cost | 0.2562 | 1308.6 | 0.000196 |
| latency-cost | 0.2447 | 1272.9 | 0.000192 |

トークンコストとレイテンシコストの変種は若干高いF1を示している。著者らはステップコストを「デプロイメントフレンドリーなデフォルト」と位置づけ、精密な計装が利用可能な場合は置き換え可能としている。

### 意味的冗長性制御（論文Table IVより）

| 冗長性制御 | F1 | トークン数 | 時間(s) | ツール呼び出し |
|-----------|-----|----------|--------|-------------|
| step-cost | 0.2360 | 1294.2 | 1.138 | 1.56 |
| semantic redundancy | 0.2370 | 1156.6 | 1.346 | 1.40 |

意味的冗長性制御によりF1をほぼ維持しつつ、トークンを**約10.6%削減**（1294.2→1156.6）している。ただしウォールクロック時間は1.138秒から1.346秒に増加しており、これはエンベディング比較の局所的オーバーヘッドによるものと著者らは説明している。ホスト型サービスでは課金対象のトークンとリモートAPI呼び出しが削減されるため、より大きな恩恵があると主張している。

### アブレーション（論文Table Vより）

| 除去要素 | F1 | トークン数 |
|---------|-----|----------|
| full policy | 0.2383 | 1273.3 |
| − expected-gain | 0.2621 | 2716.6 |
| − uncertainty | 0.2487 | 1669.7 |
| − redundancy | 0.2435 | 1792.7 |
| − stop | 0.2621 | 2716.6 |

gainまたはstop項を除去するとトークンが約2倍（約2700）に膨張し、F1は0.2621に上昇する。これは、フルポリシーがF1最大化設定ではなく、**トークン膨張を防止する制御機構**として機能していることを示唆している。著者らは、gainのPearson相関がF1に対して0.1479、uncertaintyは0.0131であったと報告しており、これらが制御ヒューリスティックであり校正された確率ではないことを裏付けている。

## 実運用への応用（Practical Applications）

### Zenn記事との関連

Zenn記事で解説したAutoGenやAgent Frameworkでは、マルチエージェントワークフローにおけるトークンコスト管理が実運用上の課題として挙げられている。本論文のユーティリティ誘導型アプローチは、以下の点でAgent Framework上のエージェント設計に適用可能である：

1. **WorkflowBuilder上のコスト制御**: Agent FrameworkのDAGワークフローにユーティリティコントローラを挿入し、各エージェント呼び出し前にgain/cost評価を実行する
2. **$\lambda$パラメータのSLOマッピング**: サービスのSLO（レイテンシ要件、コスト予算）を$\lambda$パラメータに変換し、動的に調整する
3. **オーケストレーションログの監査**: DynamoDB等にステップごとのユーティリティスコアを記録し、長いトラジェクトリの原因分析を可能にする

### 制約と限界

- **評価範囲**: HotpotQA（200サンプル）のみ。マルチツール環境、コード実行、Web自動化等での検証は未実施
- **単一リトリーバ**: BM25のみ使用。異種ツール（API、DB、コード実行）の統合は未検証
- **ヒューリスティック信号**: LLMの自己推定に依存しており、校正されていない
- **統計的検定**: 論文に分散、信頼区間、シード情報の報告なし。すべての結果が単一ポイント値
- **F1-コストのトレードオフ**: Table Iにおいてユーティリティポリシーはreactより多くのトークンを消費しており、「コスト効率」の主張はsemantic redundancy設定（Table IV）に限定される

## 関連研究（Related Work）

著者らはIntroductionにおいて以下の関連分野を挙げている：

- **固定ワークフロー型フレームワーク**: MetaGPT、ChatDev、AutoGen、DSPy。予測可能だがクエリ難易度への適応が困難
- **自由形式推論ループ**: ReAct、Toolformer、Gorilla、ToolLLM。柔軟だが過剰実行のリスク
- **適応的計算**: Adaptive Computation Time、CALM、DeeBERT。推論コストの動的制御という共通テーマ
- **RAGシステム**: Lewis et al. (2020)、WebGPT、HuggingGPT

本論文は、固定ワークフローの予測可能性と自由形式ループの柔軟性を**ユーティリティ関数**で橋渡しする試みである。

## まとめと今後の展望

本論文は、LLMエージェントのツールオーケストレーションを明示的な逐次意思決定問題として定式化し、gain・cost・uncertainty・redundancyの4要素を統合したユーティリティ関数による行動選択ポリシーを提案した。著者らはHotpotQAでの実験により、意味的冗長性制御で最大10.6%のトークン削減を達成したと報告している。

ただし、本手法はReActに比べてF1・効率性ともに劣る場面があり、価値は解釈可能性とオペレータによるトレードオフ制御にある。評価はHotpotQA 200サンプル・単一リトリーバに限定されており、マルチツール環境や大規模評価での検証は今後の課題である。

今後の研究方向として、著者らは学習ベースのユーティリティ推定、低オーバーヘッド冗長性検出、異種ツールコスト対応を挙げている。
