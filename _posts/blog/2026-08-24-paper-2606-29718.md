本記事は [Diagnosing and Mitigating Context Rot in Long-horizon Search](https://arxiv.org/abs/2606.29718) の解説記事です。

## 論文概要

Xia et al. (2026) は、LLMベースの長期検索エージェントにおいて、コンテキストが蓄積するにつれてモデルが正解に到達する前に探索を放棄する現象を「Context Rot」と定義した。著者らは4モデル（GLM-4.7, GLM-5.0, Qwen3.5-397B-A17B, MiniMax-2.5）を3つのベンチマーク（BrowseComp, BrowseComp-Plus, xbench-DeepSearch）で評価し、エージェントの終了挙動を6つの状態に分類して劣化メカニズムを診断している。緩和策として7つのコンテキスト管理手法を3カテゴリに体系化し、FoldAgent（サブエージェント分離）で最高精度64.9%を達成したと報告している。さらに、rot-awareフィルタリングを用いた並列サンプリングで最大+9.6%の追加改善を確認している。

この記事は [Zenn記事: プロンプトキャッシュが覆すコンテキスト管理の常識：圧縮vs全保持の判断基準と実装](https://zenn.dev/0h_n0/articles/6319db2cded345) の深掘りです。Zenn記事ではプロンプトキャッシュの観点からコンテキスト管理の圧縮と全保持のトレードオフを議論しているが、本論文はコンテキスト蓄積そのものがもたらす性能劣化メカニズムを実験的に解明し、手法選択の判断基準を提供している。

## 背景と動機

LLMを用いたWeb検索エージェント（Deep Research, Open Deep Research等）は、複雑な質問に対して複数回の検索・読解を繰り返すReActパターンで動作する。各ステップの観測結果（Webページの内容、検索結果等）がコンテキストウィンドウに累積的に追加されるため、探索が長期化するとコンテキスト長が急速に増大する。

従来のlong-context研究では「Needle-in-a-Haystack」テストのような受動的な情報検索タスクが中心であり、エージェントが能動的に探索戦略を修正しながら推論する長期検索タスクでの劣化は体系的に検討されていなかった。著者らは、200Kトークン以上のコンテキストウィンドウを持つ最新モデルでも、トラジェクトリが長くなるにつれて「正解にたどり着けずに探索を放棄する」「自信なく誤った回答を出す」といった早期降参（premature termination）が顕著に観察されることに着目した。この現象を「Context Rot」と名付け、体系的な診断と緩和に取り組んでいる。

## 主要な貢献

- **Context Rotの定義と診断**: トラジェクトリ長と精度の関係を6つの終了状態に分類し、劣化の性質を定量的に可視化する枠組みを確立した
- **Behavior-Aware Filtering**: GPT-OSS-120Bをジャッジとして使用し、エージェントの終了挙動を自動判定する手法を導入。5回の多数決投票で人間アノテーションとの一致率98.7%を達成した（300軌跡で評価）
- **7つの緩和手法の体系化**: Context Compaction（3種）、Context Trimming（3種）、Context Isolation（1種）の3カテゴリ・7手法を統一的に評価し、各手法の特性と適用指針を明らかにした
- **rot-aware並列サンプリング**: 緩和手法とrot-awareフィルタリングの組み合わせで平均+2.6%から+4.9%の追加改善を確認した

## 技術的詳細

### 6つの終了状態分類

著者らは、検索エージェントのトラジェクトリが終了する状態を以下の6つに分類している。この分類がContext Rotの診断基盤となる。

| 終了状態 | 定義 | Context Rotとの関係 |
|---------|------|-------------------|
| Confident Correct | 正解かつ高確信 | 健全な終了 |
| Uncertain Correct | 正解だが低確信 | 探索は成功したが確信に至れず |
| Confident Incorrect | 不正解だが高確信 | 初期に多い（幻覚的回答） |
| Uncertain Incorrect | 不正解かつ低確信 | Context Rotの典型的症状 |
| Give Up | 回答を放棄 | Context Rotの典型的症状 |
| No Answer | 回答なしで終了 | システム的な終了 |

著者らの実験では、トラジェクトリ長の増加に伴いConfident IncorrectからUncertain IncorrectとGive Upへ遷移するパターンが観察されている。短いトラジェクトリでは情報不足による幻覚的回答（Confident Incorrect）が多く、長くなるにつれてコンテキスト蓄積による判断能力の劣化（Uncertain IncorrectとGive Up）が支配的になると報告されている。

### BrowseCompにおける終了状態分布

著者らは4モデルについて、BrowseComp（100サンプルサブセット）での終了状態分布を報告している。

| モデル | Confident Correct | Uncertain Correct | Confident Incorrect | Uncertain Incorrect | Give Up | No Answer |
|-------|------------------:|------------------:|-------------------:|-------------------:|--------:|----------:|
| Qwen3.5-397B-A17B | 32.8% | 2.2% | 11.6% | 33.6% | 19.8% | 0.0% |
| GLM-4.7 | 29.8% | - | - | - | 38.6% | - |
| GLM-5.0 | 41.8% | - | - | - | 18.6% | - |
| MiniMax-2.5 | 34.2% | - | - | - | 5.2% | - |

この分布から、モデルによってContext Rotの現れ方が異なることがわかる。GLM-4.7はGive Up率38.6%と探索放棄型の劣化が顕著であるのに対し、MiniMax-2.5はGive Up率5.2%と探索を継続する傾向があるが、不確実な誤答に陥りやすい。Qwen3.5-397B-A17BではUncertain Incorrect率33.6%がConfident Correct率32.8%とほぼ同水準であり、コンテキスト蓄積が判断の不確実性を大きく高めていることが示されている。

### Behavior-Aware Filtering

終了状態の自動判定にはBehavior-Aware Filteringを採用している。著者らはGPT-OSS-120Bをジャッジモデルとして使用し、各トラジェクトリの終了時の挙動を6つの状態に分類する。判定の信頼性を高めるため5回の多数決投票を行い、300トラジェクトリの人手アノテーションとの一致率98.7%を達成している。

このフィルタリングは並列サンプリングにおいても重要な役割を果たす。複数回の探索を並列実行した場合、rot-awareフィルタリングによってContext Rotが発生した軌跡（Give UpやUncertain Incorrectで終了した軌跡）を除外し、健全な軌跡のみを集約対象とすることで精度を改善する。

### 7つのコンテキスト管理手法

著者らは、Context Rotの緩和策を3つのカテゴリに分類し、計7つの手法を提案・評価している。

```mermaid
graph TD
    CR[Context Rot 緩和手法] --> CC[Context Compaction]
    CR --> CT[Context Trimming]
    CR --> CI[Context Isolation]
    CC --> CC1[Length-triggered]
    CC --> CC2[Turn-triggered]
    CC --> CC3[Semantic-triggered]
    CT --> CT1[Discard-all]
    CT --> CT2[Keep-latest]
    CT --> CT3[Keep-latest + Sum]
    CI --> CI1[FoldAgent]
```

#### Context Compaction（コンテキスト圧縮）

既存のコンテキストをLLMで要約し、短いテキストに圧縮する手法群である。トリガー条件によって3つのバリアントが定義されている。

**Length-triggered（長さトリガー）**: コンテキスト長が閾値（32K, 48K, 64Kの3設定で評価）を超えた時点で圧縮を実行する。実装が単純だが、閾値の選定がタスク依存になる点に注意が必要である。

**Turn-triggered（ターン数トリガー）**: 10ターンごとに圧縮を実行する。トークン数に依存しないため、各ターンの出力長のばらつきに対して頑健である。

**Semantic-triggered（セマンティックトリガー）**: Struggle Score（後述）が0.5を超えた時点で圧縮を実行する。エージェントの行き詰まりを検知してから圧縮するため、必要な場合にのみ介入する適応的な手法である。

圧縮時には、トラジェクトリ全体をLLMに入力し要約プロンプトで圧縮テキストを生成する。要約後のコンテキストは「元のシステムプロンプト + 要約テキスト + 新規アクション履歴」で構成される。

#### Context Trimming（コンテキスト切り捨て）

要約コストを避け、過去のコンテキストを単純に削除する手法群である。

**Discard-all（全破棄）**: トリガー条件を満たした時点で過去の全アクション履歴を破棄し、システムプロンプトのみを残す。Context Rotを確実に排除できるが、過去の探索で得た情報が完全に失われる。

**Keep-latest（直近保持）**: 直近の数ターンのみを保持し、それ以前を破棄する。情報損失と鮮度のバランスを取る手法である。

**Keep-latest + Summarization（直近保持+要約）**: 直近3ターンをそのまま保持し、それ以前を要約テキストに置換する。CompactionとTrimmingのハイブリッドであり、直近の詳細な文脈を維持しつつ過去の要約情報も利用できる。

#### Context Isolation（コンテキスト分離）

**FoldAgent（サブエージェント分離）**: メインエージェントが複雑なサブタスクを検出した場合、新しいサブエージェントを起動してそのサブタスクを独立したコンテキストウィンドウで実行する。サブエージェントの結果の要約のみがメインエージェントのコンテキストに追加される。各サブタスクのコンテキストが短く保たれるため、Context Rotの発生を根本的に回避する設計である。

### Struggle Score

Struggle Scoreは、エージェントの探索行動における「行き詰まり度合い」を定量化するメトリクスである。LLM-as-judgeアプローチで各ステップのアクション履歴を判定し、0から1のスコアを算出する。

$$
S_{\text{struggle}}(t) = f_{\text{judge}}(\mathcal{H}_{1:t})
$$

ここで $S_{\text{struggle}}(t)$ はステップ $t$ におけるStruggle Score（0: 順調、1: 完全に行き詰まり）、$f_{\text{judge}}$ はLLMジャッジ関数、$\mathcal{H}_{1:t}$ はステップ1から $t$ までのアクション履歴を表す。このスコアが高い状態が続く場合、エージェントは同じ検索クエリを繰り返す、関連性の低いページを読む、といった非生産的な行動パターンに陥っていることを示す。

## 実装のポイント

### Context Rot検知器の設計

論文の知見に基づくContext Rot検知・緩和システムの実装例を以下に示す。3種類のトリガー条件をサポートし、検知時に指定された緩和戦略を実行する設計である。

```python
from dataclasses import dataclass, field
from enum import Enum
from typing import Optional


class TerminalState(Enum):
    """エージェントの6つの終了状態分類（論文Section 3.2準拠）"""
    CONFIDENT_CORRECT = "confident_correct"
    UNCERTAIN_CORRECT = "uncertain_correct"
    CONFIDENT_INCORRECT = "confident_incorrect"
    UNCERTAIN_INCORRECT = "uncertain_incorrect"
    GIVE_UP = "give_up"
    NO_ANSWER = "no_answer"
    IN_PROGRESS = "in_progress"


ROT_STATES = {
    TerminalState.UNCERTAIN_INCORRECT,
    TerminalState.GIVE_UP,
    TerminalState.NO_ANSWER,
}
"""Context Rotの典型的症状を示す終了状態の集合"""


@dataclass
class TrajectoryStep:
    """トラジェクトリの各ステップを表現するデータクラス"""
    step_id: int
    action: str
    observation: str
    token_count: int
    struggle_score: float = 0.0


@dataclass
class ContextRotDetector:
    """Context Rotの検知と緩和を管理するクラス

    論文の3種類のトリガー条件（Length / Turn / Semantic）をサポートし、
    検知時に指定された緩和戦略を実行する。

    Attributes:
        length_threshold: Length-triggered圧縮の閾値（トークン数）
        turn_threshold: Turn-triggered圧縮の間隔（ターン数）
        struggle_threshold: Semantic-triggered圧縮の閾値（0-1）
        keep_latest_turns: Keep-latest戦略で保持するターン数
    """
    length_threshold: int = 32_000
    turn_threshold: int = 10
    struggle_threshold: float = 0.5
    keep_latest_turns: int = 3
    steps: list[TrajectoryStep] = field(default_factory=list)
    compaction_count: int = 0

    @property
    def total_tokens(self) -> int:
        return sum(s.token_count for s in self.steps)

    @property
    def current_turn(self) -> int:
        return len(self.steps)

    def should_compact_by_length(self) -> bool:
        """Length-triggered: 総トークン数が閾値を超えたか判定"""
        return self.total_tokens > self.length_threshold

    def should_compact_by_turn(self) -> bool:
        """Turn-triggered: ターン数が閾値の倍数に達したか判定"""
        if self.current_turn == 0:
            return False
        return self.current_turn % self.turn_threshold == 0

    def should_compact_by_struggle(self) -> bool:
        """Semantic-triggered: 直近のStruggle Scoreが閾値を超えたか判定"""
        if not self.steps:
            return False
        return self.steps[-1].struggle_score > self.struggle_threshold

    def add_step(self, step: TrajectoryStep) -> Optional[str]:
        """ステップを追加し、トリガーされた緩和戦略名を返す"""
        self.steps.append(step)
        if self.should_compact_by_struggle():
            return "semantic_compaction"
        if self.should_compact_by_length():
            return "length_compaction"
        if self.should_compact_by_turn():
            return "turn_compaction"
        return None

    def apply_keep_latest_with_summary(
        self, summary: str, summary_token_count: int,
    ) -> list[TrajectoryStep]:
        """Keep-latest + Summarization戦略を適用する

        直近keep_latest_turnsターンを保持し、それ以前を要約テキストに置換する。
        """
        if len(self.steps) <= self.keep_latest_turns:
            return self.steps
        summary_step = TrajectoryStep(
            step_id=0, action="[SUMMARY]",
            observation=summary, token_count=summary_token_count,
        )
        latest = self.steps[-self.keep_latest_turns:]
        self.steps = [summary_step] + latest
        self.compaction_count += 1
        return self.steps

    def compute_rot_rate(self) -> float:
        """Context Rot率: Struggle Score閾値超過ステップの割合"""
        if not self.steps:
            return 0.0
        rot_steps = sum(
            1 for s in self.steps
            if s.struggle_score > self.struggle_threshold
        )
        return rot_steps / len(self.steps)
```

### 実装上の注意点

**トークンカウントの正確性**: 圧縮トリガーの判定にはトークン数が重要である。tiktoken等のトークナイザライブラリで正確にカウントする必要があり、文字数ベースの近似は誤差が大きい。

**要約品質とコスト**: Context Compactionの要約にはLLM呼び出しが必要であり、レイテンシとコストが発生する。要約自体が不正確だと情報損失につながるため、要約プロンプトの設計が重要である。

**FoldAgentのオーバーヘッド**: サブエージェントの起動にはコンテキストの初期化コストが発生する。サブタスクが軽微な場合はオーバーヘッドが性能向上を上回る可能性があり、サブタスクの複雑度に応じた閾値設定が必要である。

## Production Deployment Guide

### AWS実装パターン（コスト最適化重視）

Context Rot検知・緩和システムをAWS上にデプロイする際の構成を、トラフィック量別に示す。コスト試算は2026年8月時点のap-northeast-1（東京）リージョンの概算料金に基づく。実際のコストはトラフィックパターンやバースト使用量により変動するため、最新料金はAWS料金計算ツールで確認を推奨する。

| 構成 | トラフィック | 主要サービス | 月額概算 |
|-----|-----------|------------|---------|
| Small | ~100 req/日 | Lambda + Bedrock + DynamoDB | $50-150 |
| Medium | ~1,000 req/日 | ECS Fargate + Bedrock + ElastiCache | $300-800 |
| Large | 10,000+ req/日 | EKS + Karpenter + Spot + Bedrock | $2,000-5,000 |

**Small構成**: Lambda（256MB RAM、最大15分タイムアウト）でContext Rot Detectorを実行し、BedrockでStruggle Score判定と要約生成を行う。DynamoDB（On-Demand）でトラジェクトリ履歴を永続化する。

**Medium構成**: ECS Fargate（0.5 vCPU, 1GB RAM）でDetectorをステートフルに動作させ、ElastiCache（Redis）でセッション状態をキャッシュする。コールドスタートを回避しレイテンシを安定させる。

**Large構成**: EKS上でKarpenterによるSpot Instances自動スケーリングを活用し、FoldAgentのサブエージェントを並列実行する。

### 運用・監視設定

```python
import json
from datetime import datetime, timedelta

import boto3


def setup_cloudwatch_alarm(
    function_name: str,
    sns_topic_arn: str,
) -> None:
    """Bedrockトークン使用量スパイク検知アラームを設定する

    Args:
        function_name: Lambda関数名
        sns_topic_arn: 通知先SNSトピックARN
    """
    cw = boto3.client("cloudwatch", region_name="ap-northeast-1")
    cw.put_metric_alarm(
        AlarmName=f"{function_name}-token-spike",
        MetricName="InputTokenCount",
        Namespace="Custom/ContextRot",
        Statistic="Sum",
        Period=3600,
        EvaluationPeriods=1,
        Threshold=500_000,
        ComparisonOperator="GreaterThanThreshold",
        AlarmActions=[sns_topic_arn],
    )


def daily_cost_report(sns_topic_arn: str) -> None:
    """日次コストレポートを生成しSNS通知する

    Bedrock, Lambda, EKSのコストを抽出し、
    $100/日を超過した場合にアラート通知する。

    Args:
        sns_topic_arn: 通知先SNSトピックARN
    """
    ce = boto3.client("ce", region_name="us-east-1")
    today = datetime.utcnow().strftime("%Y-%m-%d")
    yesterday = (datetime.utcnow() - timedelta(days=1)).strftime("%Y-%m-%d")

    response = ce.get_cost_and_usage(
        TimePeriod={"Start": yesterday, "End": today},
        Granularity="DAILY",
        Metrics=["UnblendedCost"],
        Filter={
            "Or": [
                {"Dimensions": {"Key": "SERVICE", "Values": ["Amazon Bedrock"]}},
                {"Dimensions": {"Key": "SERVICE", "Values": ["AWS Lambda"]}},
                {"Dimensions": {"Key": "SERVICE",
                                "Values": ["Amazon Elastic Kubernetes Service"]}},
            ]
        },
    )

    total = sum(
        float(r["Total"]["UnblendedCost"]["Amount"])
        for r in response["ResultsByTime"]
    )

    if total > 100.0:
        sns = boto3.client("sns", region_name="ap-northeast-1")
        sns.publish(
            TopicArn=sns_topic_arn,
            Subject="Context Rot Detector: cost alert",
            Message=json.dumps({
                "date": yesterday,
                "total_cost_usd": round(total, 2),
                "threshold_usd": 100.0,
            }),
        )
```

## 実験結果

### 緩和手法の比較

著者らはQwen3.5-397B-A17Bを用いて、BrowseComp-Plus（200インスタンス）で各緩和手法のAccuracyとContext Rot率を評価している。

| 手法 | カテゴリ | Accuracy | Rot率 |
|------|---------|--------:|------:|
| ReAct（ベースライン） | - | 54.4% | 53.4% |
| Summary (Length) | Compaction | 58.4% | 2.4% |
| Summary (Turn) | Compaction | 57.9% | 1.8% |
| Summary (Semantic) | Compaction | 56.2% | 3.6% |
| Discard-all | Trimming | 52.1% | - |
| Keep Latest | Trimming | 59.4% | - |
| Keep Latest w/ Sum | Trimming | 62.9% | 16.2% |
| FoldAgent | Isolation | **64.9%** | - |

**FoldAgentが最高精度**: サブエージェント分離によるContext Isolationが64.9%で最高精度を達成しており、ベースラインから+10.5ポイントの改善である。コンテキストを完全に分離することで、長いトラジェクトリにおける情報の干渉を根本的に回避している。

**Keep Latest w/ Sumが第2位**: 直近3ターンの保持と過去の要約を組み合わせた手法が62.9%で第2位である。要約による情報保持と直近文脈の詳細保持のバランスが有効に機能している。

**Context Compactionのトレードオフ**: Summary手法はRot率を53.4%から1.8-3.6%に大幅に低減するが、Accuracyの改善は+2-4ポイントにとどまる。圧縮時に有用な情報も一部失われるためと著者らは分析している。

**Discard-allの限界**: 全履歴破棄は52.1%とベースラインを下回っており、過去の探索情報を完全に失うコストの大きさを示している。

### rot-aware並列サンプリング

著者らは、緩和手法にrot-awareフィルタリングを用いた並列サンプリングを併用した場合の追加効果を報告している。

| モデル・手法 | フィルタなし | rot-aware | 改善幅 |
|-------------|----------:|----------:|------:|
| Qwen3.5 FT | 54.0% | 61.7% | +7.7% |
| Qwen3.5 FL | 56.7% | 63.0% | +6.3% |
| Qwen3.5 MV | 52.7% | 62.3% | +9.6% |
| GLM-4.7 FT | 52.7% | 56.7% | +4.0% |

Qwen3.5のMV（Majority Vote）でrot-awareフィルタリングを適用した場合に最大+9.6%の改善が得られている。Context Rotが発生した軌跡を投票対象から除外することで、健全な探索結果のみで集約が行われ精度が向上する。平均改善幅は+2.6%から+4.9%と報告されている。

## 実運用への応用

### 検索エージェントの品質監視

Context Rotの概念は、プロダクション環境の検索エージェント品質監視に直接応用できる。Struggle Scoreをリアルタイムで計算し、閾値を超えた場合に自動的にContext Compactionを適用することで、長時間の探索タスクでもエージェントの応答品質を維持できる。Behavior-Aware Filteringの高い判定精度（98.7%）は、品質監視の自動化を現実的にする根拠となる。

### プロンプトキャッシュとの連携

Zenn記事で議論されているプロンプトキャッシュの観点からは、Context Compactionの要約結果をキャッシュすることでコスト効率を改善できる。同一クエリパターンの要約は再利用可能であり、Prompt Cachingとの組み合わせで要約コストを30-90%削減できる可能性がある。ただし検索結果は動的であるため、キャッシュのinvalidation戦略が重要となる。

### FoldAgentの適用判断

FoldAgentは最高精度を達成するが、サブエージェント起動のオーバーヘッド（レイテンシ、コスト）が発生する。タスクの複雑度に応じて、単純な検索にはContext Compaction、複雑なマルチステップ検索にはFoldAgentを使い分けるルーティング設計が有効である。

### 制約と限界

本論文にはいくつかの制約がある。第一に、評価はBrowseCompとBrowseComp-Plusの計300インスタンスに限定されており、ドメイン固有タスクへの汎化性は未検証である。第二に、テスト対象が4モデルに限られており、他の大規模モデルでの検証は含まれていない。第三に、Struggle ScoreのLLM-as-judge手法はジャッジモデルへの依存があり、ジャッジモデル自体のバイアスが結果に影響する可能性がある。

## 関連研究

- **Lost in the Middle (Liu et al., 2023)**: 長いコンテキストの中間に配置された情報をLLMが見落としやすい現象を報告。Context Rotは受動的な情報検索ではなく、能動的な探索タスクにおける劣化を扱う点で異なる
- **ReAct (Yao et al., 2023)**: LLMに推論と行動を交互に行わせるフレームワーク。本論文の検索エージェントのベースラインアーキテクチャとして使用されている
- **Self-Refine (Madaan et al., 2023)**: LLMの出力を自己改善する手法。Context Compactionの要約ステップはSelf-Refineの知見を活用してトラジェクトリの情報を圧縮・再構成している
- **BrowseComp (OpenAI, 2025)**: 複雑なWeb検索タスクのベンチマーク。本論文はBrowseCompを拡張したBrowseComp-Plusで評価を行っている

## まとめ

Xia et al. (2026) は、LLMベースの長期検索エージェントにおけるContext Rotを体系的に定義・診断し、6つの終了状態分類とBehavior-Aware Filteringによる自動判定（一致率98.7%）を確立した。7つの緩和手法のうちFoldAgent（サブエージェント分離）が最高精度64.9%を達成し、Keep Latest w/ Sum（直近保持+要約）が62.9%で実用性とのバランスに優れることが示された。Context Rot率は最大53.4%から最小1.8%まで低減可能であり、rot-aware並列サンプリングで最大+9.6%の追加改善が得られている。長期検索タスクにおけるコンテキスト管理の実践的な設計指針を提供する論文である。
