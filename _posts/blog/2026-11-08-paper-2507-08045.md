本記事は[Krul: Efficient State Restoration for Multi-turn Conversations with Dynamic Cross-layer KV Sharing](https://arxiv.org/abs/2507.08045)の解説記事です。

## 論文概要

Krulは、マルチターン会話で非アクティブになった会話のKVキャッシュをCPUメモリへオフロードし、再開時に再計算とCPUからの読み込みを組み合わせて状態を復元するLLM推論システムである。著者らは、会話ごとに層のattentionパターンの類似性を測り、類似した層どうしでKVキャッシュを共有（cross-layer KV sharing）する戦略を動的に選ぶ点を提案として挙げている。評価ではLLaMA-7B、LLaMA-30B、Qwen1.5-7B、Qwen2-72B（8-bit量子化）を用い、LongBenchで品質を、ShareGPTでスループットを測定している。著者らは平均精度低下が1%未満であり、TTFT（Time To First Token）を既存手法に対して改善したと報告している。

## 背景と動機

LLMのマルチターン会話では、各ターンでそれまでの対話履歴のKVキャッシュを再利用する。会話が一時的に非アクティブになると、GPU HBM上のKVキャッシュを解放するか、CPUメモリ等に退避する必要がある。再開時にはこの状態を復元しなければならず、その方法として「プロンプトから再計算する」と「退避したKVを読み込む」の2つがある。

論文の導入部で著者らは、2000トークン程度の会話ターン1つにつき、Qwen1.5-7Bで平均1GB規模のKVキャッシュ領域が必要になると述べている。会話数が増えると、この領域がGPUメモリを圧迫する。一方で、全KVを読み込む方式はCPU-GPU間の転送がボトルネックになり、全再計算方式はプロンプトが長いほどTTFTが伸びる。

著者らは、これら2つの極端な戦略の間で、会話ごとに最適な点を選ぶ必要があると位置づけている。また、Krulはプロンプトキャッシュのように「同じプレフィックスを再利用する」発想を、マルチターン会話の状態復元の文脈へ拡張するものとして読むことができる。プロンプトキャッシュの設計観点は本記事の関連Zenn記事で扱っている。

## 主要な貢献

論文が挙げている貢献を、著者らの記述に沿って整理する。

- **会話ごとの動的なKV圧縮戦略の選択**: 固定の圧縮方式ではなく、会話ごとにattentionの類似性に基づいてcross-layer KV sharingの組み合わせを決める（Abstract、Section 2.3、Section 4.2）。
- **attentionパターンの分類**: 層を情報抽出型（I-E）、情報処理型（I-P）、初期・直近重視型（I-R）に分け、I-R層が全体の75%から87.5%を占めると報告している（Section 4.1、Table 3）。
- **再計算とCPU読み込みの並列パイプライン**: 再計算とCPU DRAMからの読み込みをCUDAストリームで並列に走らせ、両者の完了時刻が揃うように再計算比率を調整する（Section 3、Section 6）。
- **Token-wise similarity estimator**: プリフィル時の大きなattention計算をCPUへ非同期にオフロードする仕組みを提案する（Section 5）。
- **評価**: 4モデル、LongBench、ShareGPTを用いて、品質、TTFT、スループット、ストレージを測定したと報告する（Section 8）。

## 技術的詳細

### 動的cross-layer KV sharing

cross-layer KV sharingとは、異なる層のKVキャッシュを1つにまとめて保持する方式である。論文では、層ペア $[0,1]$ が層0と層1のキャッシュを共有することを意味する（Figure 1）。著者らは、この共有の組み合わせを固定せず、会話ごとに決めると述べている。

各層の標準的なattentionは次のように書かれる（Section 2.1）。

$$
\mathrm{Attention}(Q, K, V) = \mathrm{softmax}\left(\frac{QK^\top}{\sqrt{d_K}}\right)V
$$

ここで $Q, K, V$ はクエリ、キー、バリューの行列、$d_K$ はキーの次元である。

### 圧縮戦略の選択（Algorithm 1）

Section 4.2のAlgorithm 1の手順は次のとおりである。

1. **I-R層の判定**: 各層について、先頭10%のトークンと直近90%のトークンへの平均attentionを計算する。その合計値が閾値 $\gamma$ を下回る層は、I-R層ではないとして除外する。
2. **類似度の計算**: 残ったI-R層について、flatten済みのattention重みどうしのユークリッド距離を計算し、昇順に並べる。距離が小さい（類似度が高い）ペアが先に来る。
3. **貪欲な選択**: 既に共有されていない層だけを使い、共有された層数が $N \times r_l$ に達するまでペアを選ぶ。ここで $N$ は層数、$r_l$ は圧縮率である。

出力は圧縮対象の層ペアの集合 $M$ である。圧縮の計算式はMiniCache（論文のSection 8.5で言及）と同じだと著者らは述べている。

ここで注意すべき点として、Algorithm 1は会話ごとに実行されるため、そのコストが無視できる必要がある。著者らは、類似度計算を後述のCPU側推定器で処理することでこれを抑えると説明している。

### 状態復元メカニズム

非アクティブな会話のKVは、圧縮された形式でCPUメモリに退避される。再開時には、次の2経路を並行して実行する（Section 3、Section 6）。

- **再計算経路**: 退避された隠れ状態（hidden states）からKVの一部を再計算する。
- **読み込み経路**: 残りのKVをCPU DRAMからGPU HBMへ転送する。

2つの結果は `torch.cat()` で結合される。再計算比率 $r_c$ は、両経路の完了時刻が揃うように調整される。著者らはこの関係を次のように書いている（Section 6.1, Eq. (1)）。

$$
\min_{r_c} \left| T_C - T_L \right|, \quad T_C = \frac{F(N, L, d)}{F_{\text{peak}}}, \quad T_L = \frac{G(N, L, d)}{B_{\text{peak}}}
$$

各変数の定義は次のとおりである。

- $N$: 層数
- $L$: プロンプト長（トークン数）
- $d$: 隠れ次元
- $T_C$: 再計算に要する時間の見積もり
- $T_L$: 読み込みに要する時間の見積もり
- $F(\cdot)$: 再計算の仕事量
- $G(\cdot)$: 読み込みの仕事量
- $F_{\text{peak}}$: 最大計算速度
- $B_{\text{peak}}$: 最大メモリ帯域

また、Section 6.2では、読み込み量が層番号とともに増え、再計算量が減るピラミッド型の分割を提案している。隠れ状態の長さは深い層ほど短くなる（Eqs. (4)–(5)）ため、深い層の再計算に必要な隠れ状態は浅い層で既に用意されていることになる。

### Token-wise similarity estimator

Section 5では、プリフィルとデコードでattention計算の性質が異なる点に着目している。プリフィルのattentionはプロンプト長の二乗に比例して大きくなるため、CPUへ非同期にオフロードする。一方、デコード時は1ステップごとに1行のattentionしか計算せず、ステップごとに破棄されるので、GPUで処理する。両者の部分的な類似度結果を足し合わせて、層選択に使う。

著者らは、ShareGPTのデータでは、デコード長がプリフィル長のおよそ6.56倍になると報告している（Section 5）。この比率が、CPU側の計算をデコードと並行させて隠せるという議論の根拠になっている。

## 実装のポイント

著者らの記述から、実装時に押さえるべき点を3つに絞る。

第一に、**I-R層の判定閾値 $\gamma$ と圧縮率 $r_l$ は、モデルごとのキャリブレーションが必要**である。著者らは、最適な $r_c$ は「キャリブレーションデータセットを用意して探す」と述べている（Section 6.1）。本番運用で会話の性質が変わると、この調整をやり直す必要がある。

第二に、**再計算と読み込みは同一のGPUストリームで直列に実行しない**。論文では別々のCUDAストリームを用いている（Section 6）。ただし、個別の同期点や `torch.cat()` の順序は論文の記述から一意に決められないため、再現する場合は論文のソースコードまたは補足資料を確認する必要がある。

第三に、**Algorithm 1の類似度計算で距離行列を組む際のメモリ量**に注意する。層数 $N$ が大きいほど、ペアの数は $O(N^2)$ で増える。Section 7では、CPU上で距離を計算する方法として $a^2 + b^2 - 2ab$ の形の展開が示されているが、本記事では論文の記法の正確さは検証していない。実装する場合は、論文のコードを参照して内積とノルムの定義を確認すること。

以下は、ユークリッド距離で層ペアを選ぶ部分の簡単な参考実装である。論文の実装そのものではなく、Algorithm 1の流れを示すための例である。

```python
from __future__ import annotations

import torch


def select_shared_layer_pairs(
    attn_weights: torch.Tensor,
    i_r_mask: torch.Tensor,
    compression_ratio: float,
) -> list[tuple[int, int]]:
    """I-R層の中から、attention重みが近い層ペアを貪欲に選ぶ。

    Args:
        attn_weights: 形状 (N, D) の層ごとのattention重み（flatten済み）。
        i_r_mask: 形状 (N,) のbool値。Trueの層のみ共有候補とする。
        compression_ratio: 共有する層数の比率 r_l（0.0 から 1.0）。

    Returns:
        共有する層ペア (i, j) のリスト。i < j を満たす。
    """
    candidates = torch.nonzero(i_r_mask, as_tuple=False).flatten().tolist()
    n_layers = attn_weights.shape[0]
    target = int(n_layers * compression_ratio)

    # 全ペアのユークリッド距離を昇順に並べる
    pairs: list[tuple[float, int, int]] = []
    for a_idx, i in enumerate(candidates):
        for j in candidates[a_idx + 1 :]:
            dist = torch.dist(attn_weights[i], attn_weights[j]).item()
            pairs.append((dist, i, j))
    pairs.sort(key=lambda t: t[0])

    # 既に共有済みの層を使わずに、目標数まで選ぶ
    used: set[int] = set()
    selected: list[tuple[int, int]] = []
    for _, i, j in pairs:
        if len(used) >= target:
            break
        if i in used or j in used:
            continue
        used.update((i, j))
        selected.append((i, j))
    return selected
```

この例は全ペアを $O(N^2)$ で列挙するため、層数が多いモデルでは非効率である。本番では距離行列をバッチで計算するなどの最適化が必要になる。

## Production Deployment Guide

この節は、本論文の手法を自社のAWS環境で運用する場合の構成案である。論文はGPUサーバ上の推論システムを対象としており、マネージドAPIのBedrockは内部KVキャッシュを直接操作できない。そのため、Krulの機構をそのまま再現できるのは、オープンモデルを自前のGPUインスタンスで動かす構成だけである。Small構成はマネージドAPIを使う場合の簡易版として、論文の手法は含まない点に注意してほしい。

### AWS実装パターン

**Small構成（マネージドAPI、Krulの機構は含まない）**

- Lambda: 会話IDを受け取り、履歴を組み立ててBedrockを呼ぶ
- Bedrock: 応答生成。プロンプトキャッシュ機能を有効にする場合は、関連Zenn記事の設計に従う
- DynamoDB: 会話状態（履歴の要約、TTL付きの会話メタデータ）を保存する

このパターンは、マルチターン会話の状態管理を簡単に始めるための基盤である。KVキャッシュの圧縮や復元は行わない。

**Medium構成（自己ホストGPU、単一ノード）**

- EC2のGPUインスタンス（例: g5系）で推論サーバを動かす
- 退避したKVはインスタンスのローカルメモリ、またはEBSに置く
- DynamoDBは会話IDと退避先の対応だけを保持する

**Large構成（EKS + Karpenter + Spot）**

- EKSで推論Podを管理し、Karpenterでノードを動的に起動する
- GPUノードはSpotを基本とし、中断時は退避済みKVから復元する
- 会話状態の退避先はS3またはFSxを使い、CPU DRAMは一時キャッシュとして扱う

### セキュリティ・監視・コスト最適化チェックリスト

**セキュリティ**

1. 会話データはS3・DynamoDBで保存時暗号化（KMS）を有効にする
2. 通信はTLSのみとし、ALBのHTTP待ち受けを無効にする
3. IAMは最小権限で、Lambdaには必要なテーブルとモデルだけを許可する
4. KVキャッシュに含まれる会話内容は個人情報として扱い、保存期間をTTLで制限する
5. 退避先のS3バケットはパブリックアクセスをブロックする
6. 監査ログ（CloudTrail）を有効にし、データアクセスを記録する
7. Secrets ManagerでAPIキーや認証情報を管理し、コードに直接書かない
8. GPUノードのOSとドライバは定期的に更新する

**監視**

9. 構造化ログには `event`、`level`、`ts`、`request_id`、`duration_ms` を含め、会話内容は記録しない
10. TTFTとデコード速度をCloudWatchのメトリクスとして収集する
11. 復元時間（再計算と読み込みの両経路の所要時間）を別のメトリクスとして記録する
12. CPUメモリ使用率と退避済みKVの総量を監視し、閾値超過で警告する
13. Spotの中断通知をEventBridgeで受け、退避済みKVの保存を先に完了させる
14. アラートの閾値は、本番のトラフィックを一定期間観測してから決める

**コスト最適化**

15. Small構成ではDynamoDBをオンデマンドにし、利用量が安定したらプロビジョンドを検討する
16. Large構成ではSpotを基本とし、オンデマンドは最低限の冗長分だけ確保する
17. 退避先のS3はライフサイクルルールで古い会話データを低コストのストレージへ移す
18. 圧縮率 $r_l$ を上げると保存量が減る一方、精度への影響が出るため、品質指標と合わせて決める
19. ノードの統合（consolidation）を有効にし、アイドル時のGPUを減らす
20. 推論サーバのバッチサイズは、TTFTの目標値を満たす範囲で最大化する
21. 月次で、Cost ExplorerからGPU・ストレージ・転送量の内訳を確認する

## 実験結果

著者らの報告をSectionごとに整理する。

- **品質（Section 8.2、Figure 13）**: 平均精度低下は1%未満である。Table 4のLongBench平均では、ベースラインが26.94、MiniCacheが25.82、Krul（Fixed）が25.72、Krulが26.70であり、Krulはベースラインに対して約0.24ポイント低い（Section 8.5）。
- **TTFT（Section 8.3、Figure 15）**: 全再計算に対して、LLaMA-7B、LLaMA-30B、Qwen1.5-7Bでは平均2.65倍、Qwen2-72Bでは6.62倍と報告されている。全読み込みに対しては2.35倍、固定圧縮に対しては1.76倍、部分再計算に対しては1.5倍である。
- **TTFTの範囲についての注意**: 論文の要旨では既存手法に対するTTFT改善を「1.5倍から2.68倍」と記載しているが、導入と結論では「1.28倍から2.68倍」と記載されている。両者は食い違っているため、本記事では両方の数値を併記する。どちらが正しいかは、論文の最終版を確認する必要がある。
- **プリフィルのスループット（Section 8.3）**: 全再計算、全読み込み、固定圧縮、部分再計算に対して、それぞれ平均2.5倍、1.9倍、1.41倍、1.29倍と報告されている。
- **パイプラインの比率（Section 8.3、Figure 17）**: 再計算と読み込みの比率を2:3にすると、全再計算に対して約2倍、全読み込みに対して約1.35倍の改善が得られたと報告されている。
- **ストレージ（Section 8.4、Figure 19）**: 平均で、全KVの保存に対して2.35倍、固定圧縮に対して1.75倍の削減と報告されている。
- **オーバーヘッド（Section 8.6、Figure 21）**: CPUでのプリフィル類似度計算は、同じ長さのGPUデコードより速いと報告されている。

これらの数値は、論文の図表と本文の記述に基づく。図の値を読み取った数値は、論文の本文で明示された値と区別して扱うべきである。

## 実運用への応用

論文は実運用の評価を含まず、ShareGPTを使ったスループット測定と、LongBenchを使った品質評価にとどまる。そのため、実運用に当てはめるときは次の点を確認する必要がある。

まず、**会話の長さと再開頻度**である。論文は、非アクティブな会話からの復元を対象とする。再開が少ない会話では、退避の効果が小さくなる可能性がある。

次に、**モデルの選択**である。論文が扱うのはLLaMA系とQwen系であり、MQAモデルのQwen2-72Bでは再計算のレイテンシが長く、一部の結果は省略されている（論文の脚注2）。自社モデルで同じ傾向が出るかは、実測が必要である。

さらに、**品質の評価方法**である。論文は、最後の128トークンをユーザー入力として擬似的に切り出して評価している（Section 8.1）。実際の対話ログとは性質が違うため、実運用の品質は別途評価する必要がある。

## 関連研究

論文の比較対象は、Section 8.1で次のとおり挙げられている。全再計算、全読み込み、部分再計算、H2O、固定の圧縮（MiniCache）である。

MiniCacheは、Krulが圧縮の計算式を共有している手法である。ただし、Krulは層の組み合わせを会話ごとに動的に選ぶ点で、固定の圧縮と異なると著者らは位置づけている。H2Oとの詳細な比較は、本記事の情報源からは確認できなかったため記述しない。

また、プロンプトキャッシュ（同じプレフィックスのKVを再利用する仕組み）は、Krulと問題設定が近い。関連Zenn記事で扱っているプレフィックス設計は、マルチターン会話での再利用性を高めるという点で、Krulの動機と重なる部分がある。ただし、プロンプトキャッシュはマネージドAPI側の機能であり、Krulのように層単位のKVを操作することはできない。

## まとめ

著者らは、マルチターン会話のKVキャッシュ状態復元を、会話ごとに動的なcross-layer KV sharingで効率化するKrulを提案している。平均精度低下は1%未満で、TTFTは既存手法に対して改善したと報告している。ただし、TTFTの改善倍率には論文中で食い違いがあり、実運用の評価は含まれていない。

本論文は、KVキャッシュの管理を層単位で最適化する方向性を示している。マネージドAPIを使う場合には直接適用できないが、自己ホストのGPU環境では設計の参考になる。実装する場合は、キャリブレーションと実トラフィックでの品質評価を前提にすること。
