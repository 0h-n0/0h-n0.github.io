## 論文概要

本記事は [Tree of Thoughts: Deliberate Problem Solving with Large Language Models](https://arxiv.org/abs/2305.10601) (NeurIPS 2023) の解説記事です。

著者らは、LLMの推論プロセスをChain-of-Thought (CoT) の線形な思考連鎖から木構造に一般化するフレームワーク**Tree of Thoughts (ToT)**を提案している。ToTでは各ノードが「思考（thought）」と呼ばれるテキストの意味的単位であり、LM自身が各思考の有望さを評価（self-evaluation）しながら、BFSやDFSで複数の推論パスを探索する。Game of 24タスクでGPT-4のCoTが成功率4%にとどまるのに対し、ToTは74%を達成したと著者らは報告している（論文Table 2）。

## 背景と動機

LLMの推論は本質的に**左から右へのトークン逐次生成**（auto-regressive decoding）であり、一度生成を始めると途中で戻ることができない。CoTプロンプティングにより中間ステップを記述させる手法が登場したが、それでも単一の推論パスを順方向にたどるだけであり、探索・後戻り・代替案の比較検討ができない。

著者らはこの制約を認知科学の「二重過程理論」（Kahneman, 2011）から分析している。従来のLLM生成はSystem 1（高速・直感的）に相当し、CoTでもSystem 2（低速・熟慮的）の一部にとどまる。真のSystem 2的推論には、複数の選択肢を生成・評価・選択し後戻りする仕組みが必要である。ToTは古典的AIのヒューリスティック探索をLLMに適用し、LM自身を思考の生成器かつ評価器として機能させる。

## 主要な貢献

- **貢献1: 推論フレームワークの一般化** --- IO、CoT、CoT-SC（Self-Consistency）を木探索の特殊ケースとして包含する統一フレームワークを提案した。木の深さ（depth）と幅（breadth）を制御することで、従来手法が自然に導出される。
- **貢献2: LMによる自己評価メカニズム** --- 外部の報酬モデルや学習済み価値関数を使わず、LM自身が中間状態を「sure / maybe / impossible」で分類する手法を導入した。これにより追加学習なしで探索の枝刈りが可能になる。
- **貢献3: モジュラーな設計** --- 思考の分解粒度、生成戦略（独立サンプリング vs 逐次提案）、評価方式（独立評価 vs 投票）、探索アルゴリズム（BFS / DFS）を独立に選択可能な設計とし、タスク特性に応じた柔軟な構成を実現した。
- **貢献4: 3つのタスクでの有効性実証** --- Game of 24、Creative Writing、Mini Crosswordsの3タスクで、GPT-4単体のCoTを大幅に上回る性能を示した。

## 技術的詳細

### ToTフレームワークの形式的定義

ToTは問題解決を木構造の探索として定式化する。入力問題を $x$ とし、言語モデルのパラメータを $p_\theta$ とする。各ノードは**状態** $s = [x, z_1, \ldots, z_i]$（入力 $x$ と $i$ 個の思考の連結）であり、根ノードが $s_0 = x$、葉ノードが最終出力に対応する。

ToTの動作は以下の4つのコンポーネントで定義される。

### 1. 思考の分解（Thought Decomposition）

思考（thought）$z$ は「推論の中間ステップとなるテキストの意味的単位」であり、タスクに応じて粒度を調整する。

- **Game of 24**: 1つの数式（例: $13 - 9 = 4$）
- **Creative Writing**: 段落レベルの文章計画
- **Mini Crosswords**: 1つの単語（例: "5-across: APPLE"）

思考は多様な候補を生成可能なほど小さく、かつ評価可能なほど大きくする。

### 2. 思考の生成（Thought Generation）

状態 $s = [x, z_{1 \ldots i}]$ から次の思考候補を $k$ 個生成する。2つの戦略がある。

**戦略A: 独立サンプリング（i.i.d. sampling）**

$$
z^{(j)} \sim p_\theta^{\text{CoT}}(z_{i+1} \mid x, z_{1 \ldots i}) \quad \text{for } j = 1, \ldots, k
$$

思考空間が広い場合（Creative Writing等）に有効で、多様な候補を生成できる。

**戦略B: 逐次提案（sequential proposal）**

$$
[z^{(1)}, \ldots, z^{(k)}] \sim p_\theta^{\text{propose}}(z_{i+1}^{(1 \ldots k)} \mid s)
$$

思考空間が制約的な場合（Game of 24等）に有効で、単一のプロンプトで $k$ 個の候補を一括生成し重複を避ける。

### 3. 状態の評価（State Evaluation）

各状態の有望さを評価するヒューリスティック関数 $V(p_\theta, S)$ を、LM自身で実現する。

**方式A: 独立評価（Independent valuation）**

$$
V(p_\theta, S)(s) \sim p_\theta^{\text{value}}(v \mid s) \quad \forall s \in S
$$

各状態を独立に評価し、数値（1-10）やカテゴリ（sure / maybe / impossible）を出力する。Game of 24では「この中間状態から24に到達可能か」を3値分類させる。

**方式B: 投票（Deliberate voting）**

$$
s^* \sim p_\theta^{\text{vote}}(s^* \mid S)
$$

候補状態群 $S$ を比較し、最も有望な状態に投票する。Creative Writingのように絶対的な評価基準が設定しにくい場合に有効である。

### 4. 探索アルゴリズム

**BFS（幅優先探索）**: 各深さでビーム幅 $b$ の候補を保持し、評価値上位 $b$ 個を次の深さに展開する。初期状態 $S^0 = \{x\}$ から始め、各深さ $t$ で候補 $S'^t = \{[s, z] : s \in S^{t-1}, z \in G(p_\theta, s, k)\}$ を生成し、$S^t = \arg \text{top-}b(V(p_\theta, S'^t))$ で上位を選択する。浅い木（$T \leq 3$）に適している。

**DFS（深さ優先探索）**: 最も有望な状態を優先的に展開し、評価値が閾値 $v_{\text{th}}$ 以下になったら枝刈り・バックトラックする。可変深さの問題（Mini Crosswords等）に適している。

### IO, CoT, CoT-SCとの関係

ToTはこれらの手法を特殊ケースとして包含する。

- **IO prompting**: 深さ $T = 1$、幅 $b = 1$（思考なし、直接回答）
- **CoT**: 深さ $T \geq 1$、幅 $b = 1$（思考あり、単一パス）
- **CoT-SC**: 深さ $T \geq 1$、幅 $b = 1$、$k$ 回独立サンプル後に多数決（探索なし、事後集約のみ）

ToTは $b > 1$（複数パスの同時探索）かつ中間ステップでの評価・枝刈りを行う点で、これらと本質的に異なる。

## 実装のポイント

以下にToT-BFSの簡易実装を示す。

```python
from dataclasses import dataclass
from typing import Callable


@dataclass
class ThoughtNode:
    """木探索における思考ノード

    Attributes:
        state: 現在の状態（入力+これまでの思考の連結テキスト）
        value: LMによる評価スコア
        depth: 木の深さ
    """
    state: str
    value: float = 0.0
    depth: int = 0


def tot_bfs(
    problem: str,
    generate_fn: Callable[[str, int], list[str]],
    evaluate_fn: Callable[[str], float],
    max_depth: int = 3,
    beam_width: int = 5,
    num_candidates: int = 5,
) -> str:
    """Tree of Thoughts - BFS実装

    Args:
        problem: 入力問題テキスト
        generate_fn: 状態から思考候補k個を生成する関数
        evaluate_fn: 状態の有望さをスコアリングする関数
        max_depth: 探索の最大深さ T
        beam_width: 各深さで保持するビーム幅 b
        num_candidates: 各ノードから生成する候補数 k

    Returns:
        最も評価の高い最終状態テキスト
    """
    # 初期状態
    current_nodes = [ThoughtNode(state=problem, depth=0)]

    for depth in range(1, max_depth + 1):
        candidates: list[ThoughtNode] = []
        for node in current_nodes:
            # 思考候補を k 個生成
            thoughts = generate_fn(node.state, num_candidates)
            for thought in thoughts:
                new_state = f"{node.state}\n{thought}"
                score = evaluate_fn(new_state)
                candidates.append(
                    ThoughtNode(
                        state=new_state,
                        value=score,
                        depth=depth,
                    )
                )
        # 上位 b 個を選択
        candidates.sort(key=lambda n: n.value, reverse=True)
        current_nodes = candidates[:beam_width]

    # 最も評価の高い最終ノードを返す
    best = max(current_nodes, key=lambda n: n.value)
    return best.state
```

実装上の注意点として以下が挙げられる。

- **プロンプト設計**: 生成器と評価器はそれぞれ異なるプロンプトを使用する。評価器のプロンプトはタスク固有のヒューリスティクスを自然言語で記述し、LMに判断基準を与える。
- **サンプリング回数**: 評価の安定性のため、著者らはGame of 24で各状態に対し3回のサンプリングを行い多数決をとっている。
- **コスト管理**: ToTはCoTと比較して5-100倍のトークンを消費する。ビーム幅 $b$ と候補数 $k$ を小さくすることでコストを削減できるが、性能とのトレードオフがある。

## Production Deployment Guide

### AWS実装パターン（コスト最適化重視）

ToTはLLM API呼び出しが探索の各ノードで発生するため、リクエストあたりのトークン消費が大きい。トラフィック量に応じた構成を推奨する。

**コスト試算の注意事項**: 以下は2026年9月時点のAWS ap-northeast-1（東京）リージョン料金に基づく概算値である。実際のコストはトラフィックパターン、リージョン、バースト使用量により変動する。最新料金はAWS料金計算ツールで確認を推奨する。

| 構成 | トラフィック | サービス構成 | 月額概算 |
|------|-------------|-------------|---------|
| Small | ~100 req/日 | Lambda + Bedrock + DynamoDB | $50-150 |
| Medium | ~1,000 req/日 | ECS Fargate + Bedrock + ElastiCache | $300-800 |
| Large | 10,000+ req/日 | EKS + Spot Instances + Bedrock Batch API | $2,000-5,000 |

**Small構成の詳細**: Lambda (256MB, 30秒タイムアウト) + Bedrock (Claude Sonnet) + DynamoDB (On-Demand, 探索キャッシュ用) + CloudWatch。木探索の各ステップをLambda内で逐次実行し、中間状態をDynamoDBにキャッシュして重複評価を削減する。

**Large構成の詳細**: EKS (t3.medium コントロールプレーン) + Karpenter (Spot Instances 優先, c5.xlarge/c5.2xlarge) + Bedrock Batch API + ElastiCache (Redis, 評価キャッシュ) + S3 (結果保存)。並列度の高い探索を複数Podで分散実行する。

**コスト削減テクニック**:
- Spot Instances活用: EKSワーカーノードで最大90%削減
- Bedrock Batch API: 非リアルタイム処理で50%削減
- Prompt Caching有効化: 評価プロンプトの共通部分を再利用し30-90%削減
- 評価結果キャッシュ: 同一中間状態の再評価を回避

## 実験結果

### Game of 24

4つの数字と四則演算で24を作る数学パズルであり、4nums.comのインデックス901-1000の100問を使用している。

著者らは以下の結果を報告している（論文Table 2）:

| 手法 | 成功率 |
|------|--------|
| IO prompt | 7.3% |
| CoT prompt | 4.0% |
| CoT-SC (k=100) | 9.0% |
| ToT (b=1) | 45% |
| **ToT (b=5)** | **74%** |

著者らの分析によると、CoTでは約60%のサンプルが最初のステップで既に不正な式を生成しており、左から右への逐次生成の限界を示している。ToTは各ステップで「sure / maybe / impossible」の3値評価を行い、impossibleな分岐を早期に枝刈りすることで探索効率を向上させている。

コスト面では、CoT best-of-100が6,700生成トークン・$0.47で成功率49%であるのに対し、ToT (b=5)は5,500生成トークン・$0.74で成功率74%であると報告されている（論文Table 2）。少ないトークンで高い成功率を達成しているが、評価呼び出しの分だけ総コストは高くなる。

### Creative Writing

4つのランダムな文を末尾に持つ4段落の文章を生成するタスクである（100問）。

著者らは以下の結果を報告している（論文Table 3）:

| 手法 | GPT-4スコア (1-10) |
|------|-------------------|
| IO prompt | 6.19 |
| CoT prompt | 6.93 |
| **ToT** | **7.56** |

人間評価では100ペア中41でToTが好まれ、21でCoTが好まれている（論文Figure 5）。

### Mini Crosswords

5x5クロスワード（GooBix 20問）の結果（論文Table 4）:

| 手法 | 文字正解率 | 単語正解率 | 完全正解 |
|------|-----------|-----------|---------|
| IO prompt | 38.7% | 14% | 0/20 |
| CoT prompt | 40.6% | 15.6% | 1/20 |
| **ToT** | **78%** | **60%** | **4/20** |

ToTではDFSと優先度付きキューで可変深さ探索を行い、制約充足を評価関数としている。アブレーション実験で枝刈りなし（65.4%）、バックトラックなし（54.6%）を検証し、両方が性能に寄与することを確認している。

### GPT-3.5での検証

著者らはGPT-3.5-turboでも検証し、Game of 24ではToTで19%にとどまるが、生成をGPT-4・評価をGPT-3.5にすると64%に達し、生成能力がボトルネックであることを示している。

## 実運用への応用

ToTの実務応用としては以下のシナリオが考えられる。

**コード生成・デバッグ**: 複数の実装アプローチを並列に検討し、テストケース通過率で評価する構成が有効である。各ステップで静的解析やユニットテストを評価関数に組み込むことで、単一パス生成より信頼性の高い出力が期待できる。

**構造化データ抽出**: 非構造テキストからの複数フィールド抽出で、フィールド間整合性を評価関数で検証しながら探索できる。

**コスト・レイテンシの課題**: ToTは1問あたり約$0.74（Game of 24）と、CoTの約1.6倍のコストがかかる。レイテンシは深さ $T$ とビーム幅 $b$ に比例して増大するため、リアルタイム大量処理にはバッチ処理・キャッシング・並列API呼び出しの組み合わせが必要である。

## 関連研究

- **LATS** (Zhou et al., 2023): ToTにMCTSのUCB1選択とrolloutを追加し、外部フィードバックを報酬とする手法。Zenn記事のMCTS統合はこの方向性に対応する。
- **RAP** (Hao et al., 2023): LMをworld modelとしてMCTSで推論パスを探索する同時期の手法。ToTがプロンプティングベースであるのに対し、より形式的な計画問題として定式化している。
- **Self-Consistency** (Wang et al., 2023): 複数CoTパスの多数決。中間ステップでの評価・枝刈りを行わない点でToTと異なる。
- **RethinkMCTS** (Liao et al., 2024): ToT+MCTSに探索過程でのLM自己修正を導入。枝刈り前に修正を試みる。

## まとめと今後の展望

ToTはLLMの推論を線形な思考連鎖から木構造に拡張し、中間ステップでのLMによる自己評価と古典的探索アルゴリズムの組み合わせにより、GPT-4単体では困難だったタスクで大幅な性能向上を実現した。IO、CoT、CoT-SCを特殊ケースとして包含する統一的なフレームワークとしての理論的位置づけも明確である。

一方で著者ら自身が指摘するように、GPT-4が既に高い性能を示すタスクでは改善幅は限定的であり、トークンコスト増大（CoTの5-100倍）は実運用上の制約となる。今後はMCTS/A*等のより効率的な探索、探索履歴を用いたLM微調整、外部ツール統合による評価精度向上が方向性として挙げられる。
