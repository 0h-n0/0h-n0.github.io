## 論文概要（Abstract）

Flash-Searcherは、LLMベースのWebエージェントにおける逐次実行の非効率性を解消するために、タスクをDAG（有向非巡回グラフ）として分解し独立サブタスクを並列実行するフレームワークである。著者らは、BrowseCompで67.7%、xbench-DeepSearchで83%の精度を達成し、実行ステップを最大35%削減したと報告している。動的なDAG再構成により中間結果に基づくワークフロー最適化も実現している。

## 背景と動機（Background & Motivation）

現在のLLMベースWebエージェントフレームワーク（例: ReAct、Smolagents）は、ツール呼び出しを逐次的に実行する。検索 → 閲覧 → 要約 → 次の検索…というチェーンでは、互いに依存しないサブタスクも直列に処理されるため、ステップ数とレイテンシが大きくなる。特に複雑なリサーチ系タスクでは数十ステップに及ぶことも珍しくない。

著者らは、多くのWebリサーチタスクで複数の独立した情報探索パスが存在する点に着目している。たとえば「ある人物の出身大学と代表的な業績」を調べる場合、この2つの検索は互いに依存せず並列実行が可能である。Flash-Searcherは、この構造的な並列性をDAGとして明示的にモデル化し、並列実行可能なサブタスクを同時に処理することで実行効率を向上させる。

## 主要な貢献（Key Contributions）

- **DAGベースプラン構築**: 複合タスクを明示的な依存関係付きサブタスクに分解し、DAGとして表現するDecomposition関数$D$の提案
- **並列推論実行エンジン**: 準備完了判定関数$\phi$に基づき、独立サブタスクを最大5並列で同時実行するスケジューリング機構
- **動的ワークフロー最適化**: 一定間隔$\Delta$ごとにDAGを再構成し、完了ノードの除去・依存関係の再検証・新規サブタスクの動的挿入を行うRefinement関数$\mathcal{R}$
- **オープンソースモデルでの検証**: Qwen-2.5-32B/72Bバックボーンでもオープンソース手法を上回る性能を確認し、フレームワークとモデルの重みを公開

## 技術的詳細（Technical Details）

### DAGベースプラン構築

Flash-Searcherの中核は、複合タスク$T$をDAG $G_{\text{plan}} = (V, E)$ に分解するDecomposition関数$D$である。ここで$V$はサブタスク（ノード）の集合、$E$はサブタスク間の依存関係（有向辺）を表す。

$$
G_{\text{plan}} = D(T) = (V, E)
$$

各ノード$v_i \in V$は独立した探索ゴール（最大5個）に対応し、各ゴールは1〜5の実行パスを持つ。実行パスはゴール内で順次試行され、主パスが失敗した場合のフォールバックとして機能する。

### 並列実行スケジューリング

時刻$t$における実行可能サブタスクの集合$E_t$は、準備完了判定関数$\phi$によって決定される。

$$
E(G_t, P_t) = \{v_i \in P_t \mid \phi(v_i, G_t, s_t) = 1\}
$$

ここで、
- $P_t$: 時刻$t$での未完了サブタスクの集合（Pending set）
- $s_t$: 時刻$t$でのエージェントの状態
- $\phi(v_i, G_t, s_t)$: サブタスク$v_i$の前提条件が満たされているか、または部分的な実行結果から補助的信号が得られているかを判定する関数

この$\phi$の設計が重要な点で、厳密な前提条件の完了だけでなく「部分的な結果から実行開始可能」という緩和条件も許容する。これにより、Graph of ThoughtsやPlan-over-Graphのような厳密な依存関係に基づく手法と比較してより積極的な並列化が可能となる。

複数のサブタスクが並列実行された場合の状態更新は以下の通りである。

$$
s_{t+1} = f\left(s_t, \{a_t^{(k)}\}_{k=1}^{m}, \{o_t^{(k)}\}_{k=1}^{m}\right)
$$

ここで、
- $a_t^{(k)}$: $k$番目の並列サブタスクのアクション
- $o_t^{(k)}$: $k$番目の並列サブタスクの観測結果
- $m$: 並列実行されたサブタスク数

### 動的ワークフロー最適化（Refinement）

一定間隔$\Delta$ステップごとにDAGを再構成するRefinement関数$\mathcal{R}$が適用される。

$$
G_{\text{plan}}^{(t+\Delta)} = \mathcal{R}(G_{\text{plan}}^{(t)}, C_t, P_t, s_t)
$$

ここで、
- $C_t$: 完了済みサブタスクの集合
- $\Delta$: Refinement間隔（論文では7〜9ステップ）

$\mathcal{R}$は以下の3つの操作を行う。
1. **完了ノードの除去**: 解決済みサブタスクをDAGから削除
2. **依存関係の再検証**: クロスバリデーション結果に基づく未解決依存の更新
3. **新規ノードの動的挿入**: 中間結果に基づき必要な追加サブタスクを生成

### アルゴリズム全体像

```python
from __future__ import annotations
from dataclasses import dataclass, field
from typing import Any
import asyncio


@dataclass
class SubTask:
    """DAGのノードに対応するサブタスク"""
    task_id: str
    description: str
    dependencies: list[str] = field(default_factory=list)
    status: str = "pending"  # pending | running | completed
    result: Any = None


@dataclass
class DAGPlan:
    """サブタスク間の依存関係を表すDAG"""
    nodes: dict[str, SubTask] = field(default_factory=dict)

    def get_ready_tasks(self, completed: set[str]) -> list[SubTask]:
        """前提条件が満たされた実行可能サブタスクを返す

        Args:
            completed: 完了済みサブタスクIDの集合

        Returns:
            実行可能なサブタスクのリスト
        """
        ready: list[SubTask] = []
        for node in self.nodes.values():
            if node.status != "pending":
                continue
            deps_met = all(d in completed for d in node.dependencies)
            if deps_met:
                ready.append(node)
        return ready


async def execute_subtask(
    subtask: SubTask,
    agent_state: dict[str, Any],
) -> dict[str, Any]:
    """サブタスクを実行しツール呼び出し結果を返す

    Args:
        subtask: 実行するサブタスク
        agent_state: 現在のエージェント状態

    Returns:
        ツール呼び出し結果を含む辞書
    """
    subtask.status = "running"
    # 実際にはLLM推論 + ツール呼び出し（検索・クロール等）
    result = await llm_tool_call(subtask.description, agent_state)
    subtask.status = "completed"
    subtask.result = result
    return result


async def flash_searcher(
    task: str,
    max_steps: int = 40,
    delta: int = 7,
    max_parallel: int = 5,
) -> dict[str, Any]:
    """Flash-Searcherメインループ

    Args:
        task: 入力タスク文字列
        max_steps: 最大実行ステップ数
        delta: DAG Refinement間隔
        max_parallel: 最大並列実行数

    Returns:
        最終エージェント状態
    """
    # Step 1: タスクをDAGに分解
    dag = decompose_task(task)  # D(T) -> G_plan
    completed: set[str] = set()
    state: dict[str, Any] = {}

    for step in range(max_steps):
        # Step 2: 実行可能サブタスクを取得
        ready = dag.get_ready_tasks(completed)
        if not ready:
            break

        # Step 3: 並列実行（最大max_parallel個）
        batch = ready[:max_parallel]
        results = await asyncio.gather(
            *[execute_subtask(st, state) for st in batch]
        )

        # Step 4: 状態更新 s_{t+1} = f(s_t, actions, observations)
        for subtask, result in zip(batch, results):
            completed.add(subtask.task_id)
            state[subtask.task_id] = result

        # Step 5: Δステップごとにリファインメント
        if (step + 1) % delta == 0:
            dag = refine_dag(dag, completed, state)

    return state
```

### Zenn記事の`graphlib.TopologicalSorter`との対応

Zenn記事で紹介している`graphlib.TopologicalSorter`のstatic scheduling APIとFlash-Searcherの並列スケジューリングは類似した構造を持つ。主な違いは、Flash-Searcherが「実行中にDAGそのものを書き換える」動的リファインメント機構を備えている点である。Zenn記事で解説しているLangGraphの`Send()` APIによる動的ノード生成は、この動的リファインメントの実装手段として位置付けられる。

## 実装のポイント（Implementation）

**モデルとツール構成**: 著者らはGPT-5（medium reasoning effort、2025-08-07版）を主要バックボーンとし、検索にSerper API（クエリあたり5結果）、Webクロールにはコンテンツ先頭60,000文字を取得するJina Readerを使用している。オープンソース版ではQwen-2.5-32B/72BをvLLMでサーブし、8基のNVIDIA A800 GPUでテンソル並列推論を行っている。

**パラメータ設計**: 並列ゴール数は最大5、各ゴールのパス長は最大5ステップ、1ステップあたりのツール呼び出しは5〜10回、全体の最大ステップ数は40、サマリ間隔は7〜9ステップに設定されている。

**実装上の注意**: 公開リポジトリのオープンソース版ではツール呼び出しが逐次実行となっており、完全な並列実行は`FlashOAgents/agent.py`のコメントに記載されたパターンを参考に独自実装する必要がある。smolagentsフレームワークをベースとしており、LLaMA-Factoryによるファインチューニングパイプラインも含まれる。

## Production Deployment Guide

### AWS実装パターン（コスト最適化重視）

Flash-SearcherのDAGベース並列Webエージェントをプロダクション環境にデプロイする場合、トラフィック量に応じて以下の3構成を推奨する。コスト試算は2026年9月時点のAWS ap-northeast-1（東京）リージョン料金に基づく概算値であり、実際のコストはトラフィックパターン、バースト使用量により変動する。最新料金はAWS料金計算ツールで確認を推奨する。

| 構成 | トラフィック | アーキテクチャ | 月額コスト |
|------|-------------|---------------|-----------|
| Small | ~100 req/日 | Lambda + Bedrock + DynamoDB | $50-150 |
| Medium | ~1000 req/日 | ECS Fargate + Bedrock + ElastiCache | $300-800 |
| Large | 10000+ req/日 | EKS + Karpenter + Spot + vLLM self-host | $2,000-5,000 |

**Small構成の内訳**: Lambda（128MB〜1GB、$5/月）+ Bedrock Claude Sonnet（input/output token課金、$30-100/月）+ DynamoDB On-Demand（DAG状態保存、$5-10/月）+ API Gateway（$3-5/月）。DAGのサブタスク並列実行はLambdaの同時実行で実現する。

**Medium構成の内訳**: ECS Fargate（0.5 vCPU、1GB RAM × 2タスク、$50-80/月）+ Bedrock（$150-500/月）+ ElastiCache Redis（cache.t4g.micro、DAG状態キャッシュ、$15/月）+ ALB（$25/月）。Fargateタスク内でasyncioによる並列実行を管理する。

**Large構成の内訳**: EKS（コントロールプレーン$75/月）+ Karpenter管理Spot Instances（g5.xlarge × 2-4台、vLLMサーブ、$400-1500/月）+ オンデマンドワーカー（m6i.large × 2-4台、DAGスケジューラ、$200-400/月）+ S3/DynamoDB（$20-50/月）。Spot活用で最大90%のGPUコスト削減が可能。

**コスト削減テクニック**:
- Spot Instances活用（GPU推論ワーカー）: 最大90%削減
- Reserved Instances（1年コミット、スケジューラノード）: 最大72%削減
- Bedrock Batch API（非リアルタイムタスク）: 50%削減
- Prompt Caching有効化（類似検索クエリ）: 30-90%削減

| ベンチマーク | Flash-Searcher | ChatGPT Agent | OpenAI DeepResearch | Manus |
|-------------|---------------|---------------|---------------------|-------|
| BrowseComp | 67.7% | 68.9% | 51.5% | — |
| xbench-DeepSearch | 83% | — | — | — |
| GAIA | 82.5% | — | — | 73.3% |
| HLE | 44.0% | — | — | — |

BrowseCompではChatGPT Agentに迫る67.7%を達成しており、xbench-DeepSearchでは83%と他手法（Metaso DeepResearch: 64%、Kimi Researcher: 69%）を上回っている。

### オープンソースモデルでの結果

論文Table 2より、Qwen-2.5-32B/72Bバックボーンでの結果を以下に示す。

### 実行効率

著者らは論文のefficiency analysisにおいて、OAgentsとの比較でステップ数とツール呼び出し密度を報告している。

- **平均ステップ数**: Flash-Searcher 7.4 vs OAgents 11.2（35%削減）
- **ステップあたりツール呼び出し数**: Flash-Searcher 3.00 vs OAgents 0.83

この差は、Flash-Searcherが1ステップ内で複数のツール呼び出しを並列実行するため、少ないステップ数で多くの情報を収集できることを示している。

### Ablation: ステップ数拡張の効果

BrowseComp-100サブセットにおいて、最大ステップ数を40から80に拡張した場合、Flash-Searcher-32Bで+5.0%、72Bで+7.0%の性能向上が確認されている。著者らはこの結果から、性能のボトルネックがモデル能力ではなく推論ステップ数の制約にあると分析している。

## 実運用への応用（Practical Applications）

Flash-SearcherのDAGベース並列実行アーキテクチャは、企業内リサーチ自動化システムの効率化に直接応用可能である。たとえば、カスタマーサポートにおける複雑な技術調査では、複数の公式ドキュメント・ナレッジベース・チケット履歴を同時に検索し、結果を統合して回答を生成する場面で並列化の恩恵が大きい。

Zenn記事で解説している`graphlib.TopologicalSorter`によるDAGスケジューリングは、Flash-Searcherの並列実行エンジンを自前で構築する基盤として適している。Zenn記事のretry/patch/replanによるフォールト回復機構はFlash-Searcherの動的リファインメントに対応し、LangGraphの`Send()` APIによる動的ノード生成はRefinement関数$\mathcal{R}$の新規ノード挿入に相当する。

レイテンシ面では、逐次実行で40ステップ要するタスクが並列実行により7-8ステップで完了するため、ユーザ体感レイテンシの大幅な改善が見込める。一方、並列度を上げるとLLM API呼び出しのバースト負荷が増大するため、レートリミット管理とコストコントロールが運用上の重要課題となる。

## 関連研究（Related Work）

- **Graph of Thoughts (Besta et al., 2024)**: LLMの推論をグラフ構造で表現する手法。Flash-Searcherとの違いは、GoTが記号推論に重点を置くのに対し、Flash-Searcherはツール呼び出しの並列化に特化している点、および依存関係の緩和による積極的な並列化を許容する点である。
- **OAgents (Qi et al., 2025)**: オープンソースのWebエージェントフレームワーク。逐次実行が基本であり、Flash-Searcherはこれに対して35%のステップ削減を達成している。
- **MiroFlow (2025)**: GAIAベンチマークで82.4%を達成したマルチエージェントフレームワーク。Flash-Searcherの82.5%と同等水準だが、アーキテクチャアプローチが異なる。
- **Search-o1 (2025)**: プロンプトベースのTool-Integrated Reasoningアプローチ。Flash-Searcherが採用するポストトレーニングパラダイムとは対照的な手法である。

## まとめと今後の展望

Flash-Searcherは、WebエージェントのタスクをDAGとして構造化し、独立サブタスクの並列実行と動的リファインメントにより、実行効率と精度の両面で改善を実現したフレームワークである。著者らは、ステップ数拡張によるさらなる性能向上の余地や、マルチモーダルタスクへの拡張を今後の課題として挙げている。Zenn記事で実装した`graphlib`ベースのDAGスケジューラやLangGraphの`Send()` APIは、Flash-Searcherの設計思想をPythonで実装するための実用的な基盤となる。
