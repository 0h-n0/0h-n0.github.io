## 論文概要（Abstract）

本記事は [https://arxiv.org/abs/2510.24663](https://arxiv.org/abs/2510.24663) の解説記事です。

エージェントによるツール呼び出しが注目を集める一方で、マルチターンにわたる複雑なツール相互作用の複雑性は十分に研究されていない。OrchDAGは、ツール実行を有向非巡回グラフ（DAG）としてモデル化し、複雑さを制御可能な合成データ生成パイプラインを提案する。さらに、Graph Edit Distance（GED）に基づくグラフ構造報酬を導入し、GRPO系アルゴリズムと組み合わせたRLVR訓練の有効性を示している。著者らは、OrchDAGデータセットが既存モデルにとって挑戦的だが解決可能なベンチマークであり、トポロジカル構造とデータ複雑性がマルチターンツール使用の訓練において重要であると報告している。

## 背景と動機（Background & Motivation）

LLMのツール呼び出し（tool calling）能力は急速に向上しているが、従来のベンチマークは単一ターン・単一ツール呼び出しに偏重しており、実世界のエージェントタスクで必要となるマルチターン・複数ツールの複雑なオーケストレーションを十分に評価できていない。

実際のエージェントタスクでは、ツール間に依存関係が存在し、あるツールの出力が別のツールの入力となるDAG構造を形成する。例えば、天気APIの出力を用いて旅行プランAPIを呼び出し、その結果をカレンダーAPIに渡すといった連鎖的な依存がある。従来のデータセット（APIGen、ToolACE等）はこうした依存構造の複雑さを制御的に評価する手段を持たず、また強化学習ベースの訓練（RLVR）における報酬関数も、ツール実行の構造的正しさを捕捉できていなかった。

OrchDAGは、DAGの高さ（height）と幅（width）をハイパーパラメータとして複雑さを段階的に制御できる合成データ生成パイプラインと、予測DAGと正解DAGの構造的類似度を測るグラフベース報酬を提案することで、これらの課題に取り組んでいる。

## 主要な貢献（Key Contributions）

- **OrchDAGパイプライン**: APIGenおよびToolACEから抽出したツール定義を用いて、DAGの高さ・幅で複雑さを制御可能な合成データを自動生成するパイプライン。ルールベース検証（JSON妥当性、AST照合、シンボリック引数検証、トポロジカル順序検証）により高品質なデータを保証する
- **マルチターン拡張**: 3つのシナリオ（新規無関連クエリ、ターン間依存、エラーリカバリ）でマルチターン相互作用を体系的にモデル化
- **グラフ構造報酬 $R_{\text{DAG}}$**: Graph Edit Distance に基づく報酬関数で、GRPO系アルゴリズムと組み合わせてRLVR訓練を改善。従来の粗い正解/不正解の二値報酬に比べ、部分的に正しいDAG構造にも適切な報酬を与える
- **ベンチマーク評価**: GPT-4o、Claude 4、DeepSeek-R1を含む複数モデルでゼロショット/フューショット評価を実施し、OrchDAGが挑戦的なベンチマークであることを実証

## 技術的詳細（Technical Details）

### LLM推論フレームワーク

OrchDAGでは、LLMのツール使用を以下の形式で定式化している。ツール集合 $\mathcal{T}$、ツール記述 $\mathcal{D}$、ユーザクエリ $x$ が与えられたとき:

1. **計画生成**: LLMがDAG形式の実行計画を生成する

$$
p = \{\mathcal{P}_1, \ldots, \mathcal{P}_n\} \sim \rho_\theta(p \mid \mathcal{T}, \mathcal{D}, x)
$$

2. **中間推論**: 各ステップで観測結果を受けて次の推論を生成する

$$
r_t \sim \rho_\theta(r_t \mid \mathcal{T}, \mathcal{D}, x, p, \mathcal{O}_1, \ldots, \mathcal{O}_{t-1})
$$

3. **最終応答**: 全観測結果を統合して最終回答を生成する

$$
\mathcal{R} \sim \rho_\theta(\mathcal{R} \mid \mathcal{T}, \mathcal{D}, x, p, \mathcal{O}_1, \ldots, \mathcal{O}_n)
$$

ここで、$\rho_\theta$ はパラメータ $\theta$ を持つLLM、$\mathcal{P}_i$ は $i$ 番目のツール呼び出し計画、$\mathcal{O}_t$ は $t$ 番目のツール実行結果（観測）、$n$ はDAG内のノード数を表す。各 $\mathcal{P}_i$ は `(task_id, toolname, payload, dependencies)` のタプルとして表現され、`dependencies` が親ノードのリストとしてDAGのエッジ構造を定義する。

### DAG生成パイプライン

OrchDAGのデータ生成は以下の6段階で構成される。

**Step 1 -- データ収集**: APIGen（2,542件）およびToolACE（1,005件）から、2つ以上の異なる関数を含む高品質なツール定義を抽出する。

**Step 2 -- DAGテンプレート作成**: 高さ（height）と幅（width）のハイパーパラメータに基づき、トポロジカル順序をランダムサンプリングしてDAGテンプレートを生成する。高さはDAGの最長パス長、幅は各レイヤの最大並列ノード数を制御する。

**Step 3 -- ツール合成**: DAGをレイヤごとに走査し、各ノードにツール定義を割り当てる。親ノードの出力キーが子ノードの入力キーに依存するよう制約を課し、フィールド名はインスタンスごとにランダムに変化させる。

**Step 4 -- クエリ生成**: DAGとフューショット例を条件としてLLMにユーザクエリを生成させる。

**Step 5 -- 拡張**: システムプロンプトに無関係なツール（ディストラクタ）を追加し、タスクの難度を調整する。

**Step 6 -- ルールベース検証**: 以下の5段階で品質を保証する:

```python
def verify_orchdag_instance(instance: dict) -> bool:
    """OrchDAGインスタンスの検証パイプライン

    Args:
        instance: DAGインスタンス（plan, tools, query, observations）

    Returns:
        全検証を通過した場合True
    """
    # 1. JSONフォーマットの妥当性
    if not validate_json_format(instance["plan"]):
        return False

    # 2. AST照合: ツール呼び出しがツール定義に一致するか
    for call in instance["plan"]:
        if not ast_match(call, instance["tools"]):
            return False

    # 3. シンボリック引数検証: 親ノード出力→子ノード入力の参照整合性
    for call in instance["plan"]:
        for dep in call["dependencies"]:
            parent = find_node(instance["plan"], dep)
            if not validate_symbolic_args(call["payload"], parent["output_schema"]):
                return False

    # 4. DAGトポロジカル順序検証
    if not verify_topological_order(instance["plan"]):
        return False

    # 5. 観測スキーマ検証
    for obs in instance["observations"]:
        if not validate_observation_schema(obs):
            return False

    return True
```

### マルチターン拡張

著者らは3つのシナリオでマルチターン相互作用をモデル化している。

- **シナリオ1（新規クエリ）**: 前ターンとは無関係な新しいクエリで、新しいDAGを生成する。ターン間の依存はない
- **シナリオ2（ターン間依存）**: 新しいツールを必要とするが、前ターンの出力を入力として参照するクエリ。ターン間のDAGエッジが存在する
- **シナリオ3（エラーリカバリ）**: ツール実行エラーが発生した場合に、DAGの部分的な再スケジューリングを要求するシナリオ

### グラフ構造報酬関数

OrchDAGの報酬関数は、フォーマット報酬とDAG構造報酬の2つの成分から構成される。

$$
R_{\text{Total}} = R_{\text{Format}} + \alpha \cdot R_{\text{DAG}}
$$

**フォーマット報酬 $R_{\text{Format}}$**: 出力が所定の特殊トークン（計画開始・終了タグ等）を正しい順序で含む場合に1、それ以外は0とする二値報酬。

**DAG構造報酬 $R_{\text{DAG}}$**: 予測DAG $g_1$ と正解DAG $g_2$ のGraph Edit Distance（GED）に基づく連続値報酬。

$$
R_{\text{DAG}} = 1 - \frac{\text{GED}(g_1, g_2)}{\text{GED}(g_1, \emptyset) + \text{GED}(g_2, \emptyset)}
$$

ここで、
- $g_1$: モデルが予測したDAG
- $g_2$: 正解（ground-truth）DAG
- $\text{GED}(g_1, g_2)$: $g_1$ を $g_2$ に変換するための最小編集操作数（ノード挿入・削除・置換、エッジ挿入・削除）
- $\text{GED}(g_1, \emptyset)$: $g_1$ を空グラフに変換するコスト（$g_1$ の全ノード数+全エッジ数に相当）
- $\alpha$: $R_{\text{Format}}$ と $R_{\text{DAG}}$ のバランスを制御するハイパーパラメータ

この正規化により $R_{\text{DAG}} \in [0, 1]$ となる。完全一致で $R_{\text{DAG}} = 1$、完全不一致で $R_{\text{DAG}} = 0$ に近づく。従来の二値報酬（完全一致=1、不一致=0）と比較して、部分的に正しいDAG構造に対しても勾配信号を提供できる点が利点である。

### GRPO訓練との統合

著者らはGRPO（Group Relative Policy Optimization）スタイルのアルゴリズムでRLVR訓練を実施している。訓練にはVerlフレームワークを使用し、8基のA100 GPUで実行されている。主要な訓練パラメータは以下の通り:

- **ベースモデル**: Qwen2.5（3Bおよび7Bバリアント）
- **ロールアウト数 $n$**: 4または8（$n=8$ で顕著な性能向上）
- **KL正則化**: モデルが参照ポリシーから大きく逸脱するのを防止
- **エントロピー正則化**: 性能崩壊の防止に寄与
- **推論温度**: 0.1

```python
from dataclasses import dataclass
from typing import Optional
import networkx as nx


@dataclass
class GRPOConfig:
    """GRPO訓練設定

    Attributes:
        n_rollouts: グループ内のロールアウト数
        alpha: DAG報酬の重み係数
        kl_coeff: KL正則化係数
        entropy_coeff: エントロピー正則化係数
        temperature: 推論時の温度パラメータ
    """
    n_rollouts: int = 8
    alpha: float = 1.0
    kl_coeff: float = 0.01
    entropy_coeff: float = 0.001
    temperature: float = 0.1


def compute_graph_edit_distance(g1: nx.DiGraph, g2: nx.DiGraph) -> float:
    """2つのDAG間のGraph Edit Distanceを計算する

    Args:
        g1: 予測DAG
        g2: 正解DAG

    Returns:
        正規化されたDAG報酬値 [0, 1]
    """
    ged = nx.graph_edit_distance(
        g1, g2,
        node_match=lambda n1, n2: n1.get("tool") == n2.get("tool"),
        edge_match=lambda e1, e2: True,
    )
    # 空グラフへの編集距離 = ノード数 + エッジ数
    ged_g1_empty = g1.number_of_nodes() + g1.number_of_edges()
    ged_g2_empty = g2.number_of_nodes() + g2.number_of_edges()

    denominator = ged_g1_empty + ged_g2_empty
    if denominator == 0:
        return 1.0  # 両方空グラフの場合は完全一致

    r_dag = 1.0 - ged / denominator
    return max(0.0, r_dag)


def compute_total_reward(
    predicted_dag: nx.DiGraph,
    ground_truth_dag: nx.DiGraph,
    output_text: str,
    config: GRPOConfig,
) -> float:
    """OrchDAGの総合報酬を計算する

    Args:
        predicted_dag: モデルが出力したDAG
        ground_truth_dag: 正解DAG
        output_text: モデルの生のテキスト出力
        config: GRPO訓練設定

    Returns:
        総合報酬値
    """
    # フォーマット報酬: 特殊トークンの存在と順序を検証
    required_tokens = ["<plan>", "</plan>", "<execute>", "</execute>"]
    r_format = 1.0 if all(
        tok in output_text and
        (i == 0 or output_text.index(tok) > output_text.index(required_tokens[i - 1]))
        for i, tok in enumerate(required_tokens)
    ) else 0.0

    # DAG構造報酬
    r_dag = compute_graph_edit_distance(predicted_dag, ground_truth_dag)

    return r_format + config.alpha * r_dag
```

## 実装のポイント（Implementation）

OrchDAGの実装において注意すべき点を以下に整理する。

**DAGテンプレートの生成制御**: 高さと幅のハイパーパラメータは訓練データの複雑さを直接制御する。著者らのデータセット統計（論文Table 1）によれば、訓練データは平均高さ $2.50 \pm 0.12$、平均幅 $3.4 \pm 0.24$ で構成されている。高さが深いほどツール間の依存チェーンが長くなり、幅が広いほど並列実行可能なツール数が増える。

**GED計算の計算量**: Graph Edit Distanceの厳密計算はNP困難であり、大規模なDAGでは近似アルゴリズムの使用が必要となる場合がある。OrchDAGのDAGは比較的小規模（平均高さ2-3、幅3-4）であるため、厳密計算が実用的な範囲に収まっている。

**ロールアウト数の影響**: 著者らの実験では、$n=4$ から $n=8$ への増加で単一ターンのPass@1精度が $0.276$ から $0.402$（45ステップ時点、論文Table 4）へ大幅に向上しており、ロールアウト数が性能に与える影響は極めて大きい。ただし計算コストも比例して増加するため、実用上のトレードオフが存在する。

**シンボリック引数の参照整合性**: DAGにおいて子ノードが親ノードの出力を参照する際、フィールド名の一致を厳密に検証する必要がある。OrchDAGではインスタンスごとにフィールド名をランダム化するため、モデルは表面的なパターンマッチではなく構造的な依存理解を要求される。

## Production Deployment Guide

OrchDAGで訓練されたツールオーケストレーションモデルをプロダクション環境にデプロイする際のAWS実装パターンを示す。DAGベースのマルチターンツール実行は、計画生成・ツール呼び出し・結果統合の各フェーズで異なる計算リソースを要求するため、適切なアーキテクチャ選択が重要となる。

### AWS実装パターン（コスト最適化重視）

**トラフィック量別の推奨構成**:

| 構成 | トラフィック | アーキテクチャ | 月額コスト概算 |
|------|-------------|---------------|--------------|
| Small | ~100 req/日 | Lambda + Bedrock + DynamoDB | $80-200 |
| Medium | ~1,000 req/日 | ECS Fargate + Bedrock + ElastiCache | $400-900 |
| Large | 10,000+ req/日 | EKS + Karpenter + Spot + vLLM自前ホスト | $2,500-6,000 |

**Small構成（~100 req/日）**: Lambda関数がユーザクエリを受け取り、Bedrock（Claude/Mistral）でDAG計画を生成する。DAGの各ノード（ツール呼び出し）はStep Functionsで並列実行し、DynamoDBに中間結果を格納する。月額内訳: Lambda $5、Bedrock $50-150（トークン量依存）、DynamoDB $5-10、Step Functions $5-15、CloudWatch $5。

**Medium構成（~1,000 req/日）**: ECS Fargateで常時稼働のAPIサーバを配置し、ElastiCacheでDAG実行の中間状態をキャッシュする。Bedrockへのリクエストはバッチ化して効率化する。月額内訳: ECS Fargate（0.5vCPU, 1GB RAM x 2タスク）$60、Bedrock $300-600、ElastiCache（cache.t3.micro）$15、ALB $25、CloudWatch $10。

**Large構成（10,000+ req/日）**: EKSクラスタにvLLMでセルフホストしたモデルをデプロイし、Karpenterによる自動スケーリングとSpot Instancesで計算コストを最適化する。DAGスケジューラはカスタムKubernetesオペレータとして実装し、ノード間並列度を最大化する。月額内訳: EKS コントロールプレーン $75、EC2 Spot（g5.xlarge x 2-4台）$800-2,000、EBS $50-100、ALB $25、監視 $50。

**コスト削減テクニック**:
- Spot Instances活用でGPUインスタンスコスト最大90%削減（g5.xlargeオンデマンド$1.006/h → Spot約$0.30/h）
- Bedrock Batch API使用で50%削減（リアルタイム性不要な計画生成バッチに適用）
- Prompt Caching有効化でシステムプロンプト（ツール定義）部分を30-90%削減
- Reserved Instances（1年コミット）でオンデマンド比最大72%削減

**コスト試算の注意事項**: 上記は2026年9月時点のAWS ap-northeast-1（東京）リージョン料金に基づく概算値である。実際のコストはトラフィックパターン、DAGの平均深さ・幅、ツール呼び出しのレイテンシにより変動する。最新料金はAWS料金計算ツール（calculator.aws）で確認を推奨する。

**X-Ray トレーシング設定**:

```python
from aws_xray_sdk.core import xray_recorder, patch_all

patch_all()  # boto3自動計装

@xray_recorder.capture("plan_dag")
def plan_dag(query: str, tools: list[dict]) -> dict:
    """DAG計画を生成しトレーシングする

    Args:
        query: ユーザクエリ
        tools: 利用可能なツール定義のリスト

    Returns:
        生成されたDAG計画
    """
    subsegment = xray_recorder.current_subsegment()
    subsegment.put_annotation("dag_query_length", len(query))
    subsegment.put_annotation("num_tools", len(tools))

    dag = invoke_bedrock_for_plan(query, tools)

    subsegment.put_metadata("dag_depth", dag["depth"])
    subsegment.put_metadata("dag_width", dag["width"])
    return dag
```

**Cost Explorer自動レポート**:

```python
import boto3
from datetime import datetime, timedelta

ce = boto3.client("ce", region_name="ap-northeast-1")
sns = boto3.client("sns", region_name="ap-northeast-1")

def daily_cost_report(sns_topic_arn: str, threshold_usd: float = 100.0) -> dict:
    """日次コストレポートを取得しSNS通知する

    Args:
        sns_topic_arn: 通知先SNSトピックARN
        threshold_usd: アラート閾値（USD/日）

    Returns:
        コストレポート辞書
    """
    today = datetime.utcnow().strftime("%Y-%m-%d")
    yesterday = (datetime.utcnow() - timedelta(days=1)).strftime("%Y-%m-%d")

    resp = ce.get_cost_and_usage(
        TimePeriod={"Start": yesterday, "End": today},
        Granularity="DAILY",
        Metrics=["UnblendedCost"],
        Filter={"Tags": {"Key": "Project", "Values": ["orchdag"]}},
        GroupBy=[{"Type": "DIMENSION", "Key": "SERVICE"}],
    )

    total = sum(
        float(g["Metrics"]["UnblendedCost"]["Amount"])
        for r in resp["ResultsByTime"] for g in r["Groups"]
    )

    if total > threshold_usd:
        sns.publish(
            TopicArn=sns_topic_arn,
            Subject=f"OrchDAG Cost Alert: ${total:.2f}/day",
            Message=f"Daily cost ${total:.2f} exceeded threshold ${threshold_usd}",
        )

    return {"date": yesterday, "total_usd": total, "details": resp["ResultsByTime"]}
```

### コスト最適化チェックリスト

**アーキテクチャ選択**:
- [ ] トラフィック量に応じた構成を選択（~100 req/日→Serverless、~1,000→Hybrid、10,000+→Container）
- [ ] DAGの平均深さ・幅に基づくレイテンシ要件を確認
- [ ] マルチターン比率に応じたステートフル/ステートレス設計を決定

**リソース最適化**:
- [ ] GPU: Spot Instances優先（g5.xlarge Spot: ~$0.30/h、オンデマンド比70%削減）
- [ ] Reserved Instances: 安定ワークロードには1年コミットで最大72%削減
- [ ] Savings Plans: Compute Savings Plansで柔軟にコスト削減
- [ ] Lambda: メモリサイズをPower Tuningで最適化（512MB推奨、DAG計画生成用）
- [ ] ECS/EKS: Karpenterの`consolidationPolicy`でアイドルノードを自動削減
- [ ] DynamoDB: On-Demandモードで低トラフィック時のコストを最小化

**LLMコスト削減**:
- [ ] Bedrock Batch API: 非リアルタイムのDAG計画バッチ生成に使用（50%削減）
- [ ] Prompt Caching: ツール定義（システムプロンプト）のキャッシュ有効化（30-90%削減）
- [ ] モデル選択ロジック: 低複雑度DAG（height≤2）はHaiku、高複雑度はSonnetに振り分け
- [ ] トークン数制限: DAG出力の最大トークン数を `max_tokens=2048` に制限

**監視・アラート**:
- [ ] AWS Budgets: 月次予算アラート設定（閾値80%/100%）
- [ ] CloudWatch: トークン使用量・レイテンシアラーム
- [ ] Cost Anomaly Detection: 自動異常検知有効化
- [ ] 日次コストレポート: Cost Explorer API + SNS通知
- [ ] X-Ray: DAG実行のエンドツーエンドトレーシング

**リソース管理**:
- [ ] 未使用リソース削除: Trusted Advisorで定期スキャン
- [ ] タグ戦略: `Project=orchdag` タグで全リソースを追跡
- [ ] ライフサイクルポリシー: CloudWatch Logsの保持期間を30日に設定
- [ ] 開発環境夜間停止: EventBridgeスケジュールでECS/EKSをスケールイン

## 実験結果（Results）

### ゼロショット/フューショットベンチマーク

著者らはOrchDAGテストセット（250件、マルチターン25%、平均高さ $2.7 \pm 0.08$、平均幅 $3.1 \pm 0.14$）で複数のモデルを評価している（論文Table 2）。Pass@1精度で以下の結果が報告されている:

| モデル | Zero-Shot | One-Shot | Three-Shot |
|--------|-----------|----------|-----------|
| GPT-4o | $0.18 \pm 0.03$ | $0.22 \pm 0.02$ | $0.24 \pm 0.04$ |
| Claude 4 | $0.15 \pm 0.01$ | $0.23 \pm 0.03$ | $0.22 \pm 0.01$ |
| Claude 3.7 | $0.16 \pm 0.04$ | $0.18 \pm 0.03$ | $0.23 \pm 0.01$ |
| DeepSeek-R1 | $0.12 \pm 0.02$ | $0.14 \pm 0.01$ | $0.11 \pm 0.04$ |
| Qwen2.5 7B | $0.02 \pm 0.01$ | $0.03 \pm 0.02$ | $0.03 \pm 0.02$ |
| Qwen2.5 3B | $0 \pm 0$ | $0 \pm 0$ | $0.02 \pm 0.01$ |

最高性能のGPT-4oでもThree-Shot Pass@1が0.24にとどまり、OrchDAGが既存モデルにとって挑戦的なベンチマークであることが示されている。また、Qwen3-4BのPass@64は20.23%、Qwen3-8BのPass@64は26.55%と報告されており、ロールアウト数を増やすことで解決可能性は存在するが、1回の試行での正解率は極めて低い。

### グラフ構造報酬によるRLVR訓練

Qwen2.5-7Bをベースとしたグラフ構造報酬RLVR訓練の結果（論文Table 4）では、KL正則化 + $n=8$ の構成が最高性能を示している:

| 構成 (Qwen2.5-7B) | 15ステップ | 30ステップ | 45ステップ | 60ステップ |
|-------------------|-----------|-----------|-----------|-----------|
| KL, $n=4$ | 0.184 | 0.276 | 0.276 | -- |
| KL+Entropy, $n=4$ | 0.195 | 0.276 | 0.253 | -- |
| KL, $n=8$ | 0.230 | 0.330 | **0.402** | 0.391 |

$n=8$ の構成では45ステップで最高精度0.402に達し、$n=4$ の最高値0.276を大幅に上回っている。60ステップでは0.391にわずかに低下しており、過学習の兆候が示唆される。一方、Qwen2.5-3Bでは $n=4$ の構成でPass@1が0のままであり、ベースモデルの容量が不足していることが読み取れる。

### 外部ベンチマーク（StableToolBench）

著者らはOrchDAGで訓練したQwen2.5-7B（45ステップ、$n=8$、KL）をStableToolBenchでも評価している。L1 Instruction: 47.1、L1 Category: 56.4、L1 Tool: 47.2という結果は、GPT-4-0613（45.5、57.4、48.8）と同等水準であり、7Bモデルでありながら汎化性能を維持していることが報告されている。

## 実運用への応用（Practical Applications）

OrchDAGの知見は、Zenn記事「graphlib×LangGraphで動的DAGスケジューラを自作しエージェント並列実行を高速化する」で扱われたDAGベースのエージェント並列実行と直接関連する。

**訓練データ生成への応用**: OrchDAGパイプラインは、自社のツール定義をStep 1のシードデータとして投入することで、ドメイン固有のDAGベースツールオーケストレーション訓練データを自動生成できる。高さ・幅パラメータで難易度を段階的に制御できるため、カリキュラム学習戦略との組み合わせが考えられる。

**報酬設計への応用**: GEDベースの報酬関数は、LangGraphやgraphlibで構築したDAGスケジューラの評価指標としても活用可能である。計画DAGと実行DAGの構造的類似度を定量化することで、エージェントの計画能力を段階的に改善できる。

**マルチターンエラーリカバリ**: OrchDAGのシナリオ3（エラーリカバリ）は、プロダクション環境でのツール呼び出し失敗時の再計画戦略に直接対応する。部分的なDAG再スケジューリングにより、失敗したノード以降のサブグラフのみを再実行する効率的なリカバリが実現できる。

## 関連研究（Related Work）

- **ToolRL**（Qin et al.）: ツール使用のRL訓練を提案するが、DAG構造の複雑さ制御と構造的報酬設計はOrchDAGの独自の貢献である
- **ReWOO / ReasonFlux**: 計画と実行の分離やDAGベース推論を扱うが、合成データ生成パイプラインは提供していない
- **APIGen / ToolACE**: ツール呼び出しデータセットとして広く使用されるが、依存構造の複雑さを制御的に操作する機構を持たない。OrchDAGはこれらをシードデータとして活用する
- **GRPO / DAPO**: 強化学習アルゴリズムとしてOrchDAGの訓練基盤を提供。OrchDAGはこれらに対して構造的な報酬信号を追加する

## まとめと今後の展望

OrchDAGは、ツールオーケストレーションをDAGとしてモデル化し、複雑さを制御可能な合成データ生成パイプラインとGEDベースのグラフ構造報酬を提案した研究である。著者らは、GPT-4oを含む既存モデルでもPass@1が最大0.24にとどまるベンチマークの挑戦性と、グラフ構造報酬 + GRPO訓練（$n=8$）で0.402まで改善可能であることを示している。

今後の方向として、著者らは2ターン以上の長期ホライズンへの拡張、ファイル操作のような暗黙的依存を含むcomputer-useタスクへの対応を課題として挙げている。DAGの高さ・幅とモデル容量の関係をより体系的に解明することも、実用的なエージェント訓練に向けた重要な研究方向である。
