## 論文概要（Abstract）

RouteLLMは、LLMデプロイにおけるコストと品質のトレードオフを最適化するフレームワークである。GPT-4クラスは約$75/MTokと高コストである一方、Mixtral-8x7Bは約$0.24/MTokと安価だが性能は劣る。著者らは、人間の嗜好データを学習したルーターでクエリの難易度に応じてリクエストを動的に振り分け、品質を95%維持しながらコストを最大3.66倍削減できることを報告している。

## 背景と動機（Background & Motivation）

LLMの商用デプロイにおいて、コストと性能のバランスは最も重要な課題の1つである。GPT-4のような高性能モデルはAPIコストが高く、Mixtral-8x7Bのような小規模モデルはコスト約300分の1だが複雑なタスクで品質が低下する。

プロダクション環境では単純な質問と高度な質問が混在しており、前者は安価なモデルで十分対応できる。従来のLLM-BlenderやFrugal-GPTはアンサンブル手法で複数モデル呼び出しのためコスト削減が限定的であった。RouteLLMは1リクエスト1モデルの設計で、ルーティングオーバーヘッドを最小化しつつコスト最適化を実現する。

## 主要な貢献（Key Contributions）

- **人間嗜好データに基づくルーティング**: Chatbot Arenaの80,000件以上の対戦データを活用し、4種のルーターアーキテクチャを提案
- **データ拡張戦略**: Golden-Label（MMLU）やLLM-Judge-Label（GPT-4評価）によるルーター性能の大幅向上

- **コスト効率の実証**: MT-Benchで95%のGPT-4品質を維持しつつ、強モデル呼び出しを63%削減
- **オープンソース公開**: フレームワーク全体を公開し再現性を確保

## 技術的詳細（Technical Details）

### アーキテクチャ/手法

RouteLLMの中心的なアイデアは、**Win Prediction Model**と呼ばれる確率モデルにある。クエリ$q$が与えられたとき、強いモデルが弱いモデルに「勝つ」確率$P(\text{wins} \mid q)$を推定し、閾値$\alpha$と比較してルーティングを決定する。

$$
\text{route}(q) = \begin{cases} \text{strong model} & \text{if } P(\text{wins} \mid q) \geq \alpha \\ \text{weak model} & \text{if } P(\text{wins} \mid q) < \alpha \end{cases}
$$

ここで、
- $q$: 入力クエリ（ユーザーのプロンプト）
- $P(\text{wins} \mid q)$: 強モデルが弱モデルに勝つ確率（ルーターの出力）
- $\alpha \in [0, 1]$: コスト閾値パラメータ。$\alpha$が大きいほど弱モデルへのルーティングが増加し、コストが低下する

#### 評価指標

著者らは以下の2つの指標を定義している。

**Performance Gap Recovered（PGR）**: 強弱モデル間の性能差のうち、ルーターが維持できた割合を表す。

$$
\text{PGR}(c) = \frac{p_{\text{router}}(c) - p_{\text{weak}}}{p_{\text{strong}} - p_{\text{weak}}}
$$

ここで$p_{\text{router}}(c)$はコストレベル$c$でのルーターの性能、$p_{\text{strong}}$と$p_{\text{weak}}$はそれぞれ全リクエストを強モデル・弱モデルに送った場合の性能である。

**Average PGR（APGR）**: 全コストレベルにわたるPGRの積分値で、ルーターの総合的な品質を示す。

$$
\text{APGR} = \int_{0}^{1} \text{PGR}(c) \, dc
$$

#### 4種のルーターアーキテクチャ

**1. Similarity-Weighted（SW）Ranking**: Bradley-Terryモデルのスコアとコサイン類似度を組み合わせ、類似クエリの勝敗履歴を重み付き投票で集約する。

**2. Matrix Factorization**: モデルとクエリを8次元埋め込み空間で表現し、$S \approx \mathbf{u}_q^\top \mathbf{v}_m$として双線形分解でスコアを予測する。

**3. BERT Classifier**: BERT$_{\text{BASE}}$の[CLS]トークン＋ロジスティック回帰でクエリ難易度を2値分類する。

**4. Causal LLM Classifier**: Llama 3 8Bを命令追従形式でファインチューニングし難易度を判定する。

### アルゴリズム

以下にMatrix Factorizationルーターの概念的な実装を示す。

```python
import numpy as np
from dataclasses import dataclass


@dataclass
class MatrixFactorizationRouter:
    """Matrix Factorization based LLM Router.

    Attributes:
        embedding_dim: 埋め込み次元数（論文では8）
        threshold: ルーティング閾値 alpha
    """

    embedding_dim: int = 8
    threshold: float = 0.5

    def compute_win_probability(
        self, query_emb: np.ndarray, model_embs: dict[str, np.ndarray]
    ) -> float:
        """強モデルが弱モデルに勝つ確率を推定する。

        Args:
            query_emb: クエリの埋め込みベクトル (embedding_dim,)
            model_embs: モデル名→埋め込みの辞書

        Returns:
            強モデルの勝利確率 [0, 1]
        """
        diff = float(query_emb @ model_embs["strong"] - query_emb @ model_embs["weak"])
        return 1.0 / (1.0 + np.exp(-diff))  # Bradley-Terry sigmoid

    def route(
        self, query_emb: np.ndarray, model_embs: dict[str, np.ndarray]
    ) -> str:
        """クエリを適切なモデルにルーティングする。

        Args:
            query_emb: クエリの埋め込みベクトル
            model_embs: モデル名→埋め込みの辞書

        Returns:
            選択されたモデル名 ("strong" or "weak")
        """
        if self.compute_win_probability(query_emb, model_embs) >= self.threshold:
            return "strong"
        return "weak"
```

## 実装のポイント（Implementation）

RouteLLMを実装する際の主要な注意点を以下に整理する。

**閾値$\alpha$のキャリブレーション**: $\alpha$はコストと品質のバランスを直接制御する。著者らは$\alpha = 0.5$がバランスの取れた初期値であると報告しており、MT-Benchのバリデーションセットでの探索を推奨している。

**データ拡張の効果**: MMLU validation split（約1,500問）やGPT-4によるLLM-Judge-Label（約120,000件、$700 USD）を追加することで、APGRが最大60%以上改善したと報告されている。

**ルーターの選択基準**: Matrix Factorizationは155 req/sのスループットと$3.32/Mリクエストのコストでバランスが良い。SW Rankingは最高精度だが2.9 req/sでリアルタイム用途には不向きである。

**モデルペアの一般化**: GPT-4 vs Mixtral-8x7Bで学習したルーターが、Claude 3やLlama 3.1ファミリーにも汎化することが示されている。

**X-Ray トレーシング + コスト監視（Python）**:

```python
import boto3
from datetime import datetime, timedelta
from aws_xray_sdk.core import xray_recorder, patch_all


def configure_observability(service_name: str = "routellm-router") -> None:
    """X-Ray分散トレーシングとboto3自動計装を設定する。

    Args:
        service_name: X-Rayサービス名
    """
    xray_recorder.configure(service=service_name)
    patch_all()


@xray_recorder.capture("route_decision")
def trace_route_decision(
    query: str, win_probability: float, routed_to: str, latency_ms: float
) -> None:
    """ルーティング決定をX-Rayアノテーションとして記録する。

    Args:
        query: 入力クエリ（先頭100文字のみ記録）
        win_probability: 強モデル勝利確率
        routed_to: ルーティング先モデル名
        latency_ms: ルーティング判定にかかった時間（ミリ秒）
    """
    subsegment = xray_recorder.current_subsegment()
    if subsegment:
        subsegment.put_annotation("routed_to", routed_to)
        subsegment.put_annotation("win_prob_bucket", round(win_probability, 1))
        subsegment.put_metadata("latency_ms", latency_ms)


def get_daily_cost_report(
    ce_client: boto3.client, sns_client: boto3.client, sns_topic_arn: str
) -> dict:
    """日次コストレポートを取得し、$100/日超過時にSNS通知する。

    Args:
        ce_client: Cost Explorer boto3クライアント
        sns_client: SNS boto3クライアント
        sns_topic_arn: 通知先SNSトピックARN

    Returns:
        Cost Explorerレスポンス
    """
    yesterday = (datetime.utcnow() - timedelta(days=1)).strftime("%Y-%m-%d")
    today = datetime.utcnow().strftime("%Y-%m-%d")
    response: dict = ce_client.get_cost_and_usage(
        TimePeriod={"Start": yesterday, "End": today},
        Granularity="DAILY", Metrics=["UnblendedCost"],
        Filter={"Tags": {"Key": "Project", "Values": ["routellm"]}},
    )
    total = sum(float(g["Metrics"]["UnblendedCost"]["Amount"])
                for r in response["ResultsByTime"] for g in r["Groups"])
    if total > 100.0:
        sns_client.publish(TopicArn=sns_topic_arn,
            Subject="RouteLLM Cost Alert",
            Message=f"Daily cost ${total:.2f} exceeds $100.")
    return response
```

## 実験結果（Results）

著者らは3つのベンチマーク（MT-Bench、MMLU、GSM8K）でルーターの性能を評価している。以下の表は主要な結果をまとめたものである（論文Table 2-4に基づく）。

| ベンチマーク | ルーター | APGR | CPT(50%)での強モデル呼び出し割合 | ランダム比改善 |
|-------------|---------|------|-------------------------------|-------------|
| MT-Bench | Matrix Factorization | 0.802 | 13.40% | 60.4% |
| MT-Bench | SW Ranking | 最高精度 | - | - |
| MMLU | 全ルーター平均 | - | ランダムより20%削減 | 20% |
| GSM8K | Causal LLM | - | - | 25.3% |

MT-Benchにおいて、拡張データを用いたMatrix FactorizationルーターはAPGR 0.802を達成し、ランダム比60.4%改善が報告されている。CPT(50%)は49.03%から13.40%に低下し、約75%の強モデル呼び出し削減に相当する。コスト削減ではCPT(50%)で3.66倍、CPT(80%)で2.49倍が実現されている（論文Table 2）。GPT-4品質の95%達成には37%の強モデル呼び出しで十分とされている。

クロスモデル汎化では、未見のClaude 3ファミリーでSW RankingがAPGR 56.6%改善、Llama 3.1でMatrix Factorizationが44.1%改善を達成したと著者らは報告している。

## 実運用への応用（Practical Applications）

RouteLLMは、関連Zenn記事で紹介されているPortkey AIゲートウェイとの組み合わせにおいて、特に有用なコンポーネントとなる。PortkeyのGateway Configでフォールバック・負荷分散を設定する際、どのモデルにルーティングするかの判断ロジックとしてRouteLLMのルーターを統合できる。

**マルチモデルゲートウェイとの統合**: Portkey等のLLMゲートウェイのルーティング層にMatrix Factorizationルーターを組み込むことで、動的モデル選択が可能になる。閾値$\alpha$をAPIパラメータとして外部制御すれば、コスト・品質バランスの即時調整ができる。

**段階的導入**: A/Bテストとしてトラフィックの10%をRouteLLMルーティングに振り分け、PGRと応答品質を2-4週間モニタリングした後、段階的にルーティング割合を引き上げるアプローチが望ましい。

**コスト監視との連動**: CloudWatch Metricsで強モデル呼び出し割合を日次で可視化し、閾値$\alpha$の自動調整パイプライン（目標PGR ≥ 0.8を維持しつつコスト最小化）を構築すれば、運用の自動化が可能になる。

- **Zooter**: 報酬モデルラベル依存。RouteLLMはクロスモデル汎化で優れた結果を示している。

## まとめと今後の展望

RouteLLMは人間嗜好データに基づくルーターでLLMデプロイコストを大幅に削減するフレームワークである。MT-Benchで95%のGPT-4品質を維持しつつ強モデル呼び出しを63%削減でき、未見のモデルファミリーへの汎化能力も実証されている。

今後の展望として、著者らはマルチモデル（3モデル以上）へのルーティング拡張、ドメイン特化型ルーターの学習、リアルタイム嗜好データ更新による継続学習を挙げている。
