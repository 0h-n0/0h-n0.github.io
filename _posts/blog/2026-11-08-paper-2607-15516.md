本記事は [Cache-Aware Prompt Compression: A Two-Tier Cost Model for LLM API Caching](https://arxiv.org/abs/2607.15516) の解説記事です。

## 論文概要

本論文は、LLM APIのプロンプトキャッシュとプロンプト圧縮を組み合わせた場合のコストを分析した研究である。著者のYan Song氏（PayPal Inc.）は、Anthropic の Sonnet 4.6 APIでキャッシュの振る舞いを実測し、キャッシュが効く割合 ρ が約3,500トークンを境に2段階で変化すると報告している。この知見に基づき、圧縮比を「キャッシュの段階（tier）」を落とさない範囲に制限する Cache-Aware Prompt Compression（CAPC）を提案し、LongBench-v2の16構成すべてで最安だったと報告している。

## 背景と動機

長い文書や大量のツール定義を繰り返しLLMに渡すシステムでは、2つのコスト削減手法がよく使われる。1つ目はプロンプトキャッシュで、同じ接頭辞（prefix）が再利用されたときに、通常より安い読み出し単価で処理する仕組みである。2つ目はプロンプト圧縮で、送るトークン数そのものを減らす。

両者は独立に効くと考えられがちだが、論文はその前提に疑問を投げかけている。多くの圧縮手法は問い（query）ごとに異なる圧縮結果を作るため、接頭辞が毎回変わり、キャッシュが毎回無効化される。論文は、キャッシュの効果が理想的に ρ = 1.0 で働くという文献上の仮定が、実際のAPIでは成り立たないことを実測で示している（Section 3.1）。
## 主要な貢献

論文は、著者らの主張を以下のように整理している。

- **二層キャッシュ構造の実測**: 著者らは、Sonnet 4.6のキャッシュが約3,500トークンを境とする二層構造を持つと報告している（Section 3.1, Table 2）。
- **トークン厳密一致の確認**: 著者らは、キャッシュ無効化がトークン単位で厳密に判定されることを、4種類のミューテーション試験（4/4 PASS）で確認したと報告している（Section 3.2）。
- **2段階コストモデルとクロスオーバー条件**: 4つの戦略のコスト式と、どの戦略が安くなるかを決めるヒット率の閾値 ρ_cross(r) を導出している（Section 4, Table 3）。
- **CAPCアルゴリズム**: 問い非依存の圧縮を1回だけ行い、キャッシュ用マーカーを圧縮済み文書側に付ける手法と、tierを保つ圧縮比の上限を提案している（Section 5）。
- **多段階の評価**: LongBench-v2、エンタープライズ業務アシスタント、graphify を使ったRAG、τ-bench retail で評価している（Section 6）。

## 技術的詳細

### 記号と4つの戦略

論文の記号は以下のとおりである。$N$ は問いの数、$|D|$ は文書のトークン数、$D_q$ は1問あたりの問いのトークン数、$O$ は1問あたりの出力トークン数、$r$ は圧縮比（$|D|/r$ が圧縮後のトークン数）である。単価は $p_{in}$（通常入力）、$c_w$（キャッシュ書き込み）、$c_r$（キャッシュ読み出し）、$p_{out}$（出力）の4つである。$\rho$ はキャッシュヒット率で、論文ではこれを接頭辞長 $|P|$ と呼び出し回数 $N$ の関数 $\rho(N, |P|)$ として扱っている（Section 3.1）。

論文が比較する4戦略のコストは次のとおりである。

$$
C_A = N\bigl[(|D|+D_q)\,p_{in} + O\,p_{out}\bigr]
$$

$$
C_B = N\bigl[(1-\rho_B)\,|D|\,c_w + \rho_B\,|D|\,c_r + D_q\,p_{in} + O\,p_{out}\bigr]
$$

$$
C_C = N\bigl[(|D|/r + D_q)\,p_{in} + O\,p_{out}\bigr]
$$

$$
C_D = N\bigl[(1-\rho_D)\,(|D|/r)\,c_w + \rho_D\,(|D|/r)\,c_r + D_q\,p_{in} + O\,p_{out}\bigr]
$$

$A$ は素の入力、$B$ はキャッシュのみ、$C$ は問い依存の圧縮、$D$ は CAPC である。

### クロスオーバー分析

$B$ と $C$ を比べると、キャッシュのみが安くなる条件は、ヒット率が次の閾値を超えることである。

$$
\rho_{\text{cross}}(r) = \frac{\alpha - 1/r}{\alpha - \beta}, \quad \alpha = \frac{c_w}{p_{in}}, \quad \beta = \frac{c_r}{p_{in}}
$$

Sonnet 4.6の5分TTLでは、$c_w = 3.75$、$c_r = 0.30$、$p_{in} = 3.00$（USD / MTok）なので $\alpha = 1.25$、$\beta = 0.10$ となる。論文はこの値で次の表を示している（Table 3）。

| 圧縮比 $r$ | $\rho_{\text{cross}}(r)$ | 解釈 |
|---|---|---|
| 2 | 0.652 | $\rho > 0.65$ なら cache-only が query-aware に勝つ |
| 3 | 0.797 | $\rho > 0.80$ なら cache-only が勝つ |
| 4 | 0.870 | $\rho > 0.87$ なら cache-only が勝つ |
| 6 | 0.942 | $\rho \ge 0.94$ でないと cache-only は勝てない |
| 8 | 0.978 | $\rho \ge 0.98$ でないと cache-only は勝てない |
| 10 | 1.000 | cache-only は勝てない |

圧縮を強くするほど（$r$ が大きいほど）、キャッシュだけで勝つには高いヒット率が必要になる。論文のSection 3.1では、2.4Kトークンの接頭辞で ρ が $N=5$ で 0.47、$N=50$ で 0.89 まで上がることも示している。Table 3のキャプションによれば、$r \ge 6$ では閾値が Sonnet 4.6 の実測 plateau（約0.89）を超えるため、キャッシュのみの戦略は実測上は勝ちにくい。

### 二層構造と閾値

論文は、接頭辞長による ρ の違いを Table 2 で示している。$N=30$ の場合、2,053トークンでは ρ = 0.83、4,096トークン以上では ρ = 1.00 である。論文はこれを、約3,500トークンを境とする「hot tier」（閾値未満、ρ が 1 に届かない）と「persistent tier」（閾値以上、ρ = 1）の二層構造と呼んでいる（Section 3.1）。

ここで注意すべきは、閾値付近の ρ の値が節によって異なることである。要旨では ρ ≈ 0.83（N=30）と述べられ、Section 5.2では「およそ 0.85」と書かれている。本記事では、数値を使うときは出典の節を明示する。

## 実装のポイント

### CAPCの手続き

論文のCAPCは、次の2点で構成される（Section 5.1, Listing 1）。

1. 文書 $D$ から圧縮済みの $D'$ を1回だけ作る（リクエストの経路の外で行う）。
2. `cache_control` マーカーを $D'$ のブロックにだけ付け、問いのブロックには付けない。

これにより、$N$ 回の問いのすべてで同じ接頭辞 $D'$ が再利用される。問い依存の圧縮が接頭辞を毎回変えてしまう問題を、「問い非依存の圧縮を1回だけ行う」ことで回避する設計である。

### tier を保つ圧縮比の上限

圧縮比を上げると $|D|/r$ が減り、コストも下がる。しかし $|D|/r$ が閾値 $T \approx 3{,}500$ を下回ると、ρ が約0.85まで下がり、書き込み単価 $c_w$（論文では $c_r$ の 12.5 倍）を払う呼び出しが増える。論文は、これを避ける上限として次の式を提案している（式 (7)）。

$$
r_{\max}^{\text{safe}}(|D|) = \left\lfloor \frac{|D|}{T} \right\rfloor, \quad T = 3{,}500 \text{ tokens (Sonnet 4.6)}
$$

Section 5.2 の例では、12,191トークンの文書で $r = 3$ の圧縮後接頭辞は 4,067 トークン（persistent）、1回あたりのコストは $0.0057 である。$r = 4$ では 3,119 トークン（hot）となり、コストは $0.0101 に上がる（77%増）。式 (7) の $\lfloor 12191/3500 \rfloor = 3$ は、この例と一致する。

ただし、単純な除算の $12191/4 \approx 3048$ と、論文が実測した 3,119 トークンは一致しない。圧縮器の出力長が理論値からずれるためである。実運用では、理論値ではなく圧縮後の実トークン数で閾値を確認すべきである。

以下は、本記事で検算に使ったPythonコードである（論文の式をそのまま実装したもの）。

```python
from __future__ import annotations

from dataclasses import dataclass


@dataclass(frozen=True)
class Pricing:
    """Sonnet 4.6 の単価（USD / 1M tokens）。論文 Section 4 の値。"""

    p_in: float = 3.00
    c_w: float = 3.75
    c_r: float = 0.30
    p_out: float = 15.00


def alpha_beta(p: Pricing) -> tuple[float, float]:
    """α = c_w / p_in（書き込みプレミアム）、β = c_r / p_in（読み出し割引率）を返す。"""
    return p.c_w / p.p_in, p.c_r / p.p_in


def rho_cross(r: float, p: Pricing = Pricing()) -> float:
    """cache-only(B) が query-aware 圧縮(C) に勝つために必要な最小ヒット率 ρ。"""
    a, b = alpha_beta(p)
    return (a - 1.0 / r) / (a - b)


def r_max_safe(doc_tokens: int, threshold: int = 3500) -> int:
    """tier を落とさない圧縮比の上限 floor(|D| / T)。"""
    return doc_tokens // threshold
```

この実装で `rho_cross` を $r = 2, 3, 4, 6, 8, 10$ に適用すると、0.652、0.797、0.870、0.942、0.978、1.000 となり、Table 3 と一致する。`r_max_safe(12191)` は 3 である。

文書が時間とともに変わる場合の AdaptiveCacheBoundary（Section 5.3, 付録A）は、主に合成的なバージョン変動で検証されている（Section 7.6）。本記事では参考情報として扱う。

## Production Deployment Guide

本節は論文の主張ではなく、論文の知見を実運用に持ち込むための設計案である。

### 前提と注意

- 論文の計測は Anthropic の first-party API（Sonnet 4.6、5分TTL）で行われている。Amazon Bedrock 上で閾値 3,500 トークン、ρ の値、最小キャッシュ長が同じになるかは、論文では検証されていない。
- 単価は論文の値（$3.00 / $3.75 / $0.30 / $15.00 per MTok）を使う。Bedrock の最新単価と仕様は、必ず公式の料金ページで確認すること。
- 以下の Terraform は設計例である。`terraform fmt` による整形確認のみ行い、デプロイはしていない。

### AWS 実装パターン

| 構成 | 想定規模 | 主な構成要素 | キャッシュ・圧縮の扱い |
|---|---|---|---|
| Small | 小規模なバッチ・社内向け | Lambda + Bedrock + DynamoDB | 圧縮済み $D'$ を文書更新時に1回作り、DynamoDBに保存して問いごとに再利用 |
| Medium | 複数の文書セット | Lambda + Step Functions（圧縮バッチ） + S3 | 圧縮を非同期バッチに分離し、$D'$ をS3に保存 |
| Large | 高トラフィック・複数テナント | EKS + Karpenter + Spot | 圧縮ワーカーをSpotで実行。キャッシュ参照の経路は常時稼働のPodで処理 |

### 監視: 構造化ログと ρ の代理指標

ログは1行1イベントのJSONで、必須フィールド（`event`, `level`, `ts`, `request_id`, `duration_ms`）と使用量フィールドを記録する。

```json
{"event":"llm_call","level":"INFO","ts":"2026-11-08T09:00:00+09:00","request_id":"req-123","duration_ms":842,"doc_hash":"sha256:ab12...","prefix_tokens":3119,"cache_read_input_tokens":3119,"cache_creation_input_tokens":0,"input_tokens":120,"output_tokens":210}
```

本節では、ρ を次のように操作的に定義する。論文の ρ は呼び出しごとのヒット率であるが、ここでは「キャッシュ読み出しトークンの割合」を代理指標とする。

$$
\hat{\rho} = \frac{\sum \text{cache\_read\_input\_tokens}}{\sum (\text{cache\_read\_input\_tokens} + \text{cache\_creation\_input\_tokens})}
$$

CloudWatch Logs Insights での集計例は次のとおりである。

```text
fields @timestamp, cache_read_input_tokens, cache_creation_input_tokens
| filter event = "llm_call"
| stats sum(cache_read_input_tokens) as read_tok, sum(cache_creation_input_tokens) as write_tok by bin(15m)
| fields read_tok / (read_tok + write_tok) as rho_proxy
```

アラームは2種類を設定する。1つ目は $\hat{\rho}$ が 0.8 を下回る状態が3期間続いたときである。2つ目は `prefix_tokens` が 3,500 を下回ったときで、圧縮比が tier 境界を越えたことを示す。

### セキュリティ

- **IAM最小権限**: `bedrock:InvokeModel` と DynamoDB の操作は、モデルARNとテーブルARNに限定する。
- **KMS暗号化**: DynamoDB、Lambda環境変数、EKSのSecretsをKMSで暗号化する。
- **CloudTrail**: Bedrock と KMS の API 呼び出しを記録する。
- **秘密情報**: 文書本文や利用者の情報はログに出さず、`doc_hash` のみを記録する。

### 監視: X-Ray と Cost Explorer

- **X-Ray**: Lambda の `tracing_config` を `Active` にし、Bedrock 呼び出しを計測する。
- **Cost Explorer**: コスト配分タグ（例: `Project=capc`）でモデル費用とインフラ費用を分ける。
- **コスト試算**: 2026年11月時点のAWS東京リージョン料金に基づく概算値として示す想定だったが、執筆時点で単価を確認できなかったため、金額は示さない。モデル費用の式のみ示す。

### コスト最適化チェックリスト

- [ ] 文書ごとの圧縮を1回だけ行い、結果を保存しているか
- [ ] `cache_control` を圧縮済み文書のブロックにだけ付けているか
- [ ] 問いのブロックにはキャッシュマーカーを付けていないか
- [ ] 接頭辞の順序（システム、ツール定義、文書、問い）が呼び出し間で固定されているか
- [ ] ツール定義や日時など、毎回変わる値を接頭辞に含めていないか
- [ ] 圧縮後の実トークン数が 3,500 を下回っていないか（tier の確認）
- [ ] 圧縮比 $r$ が $\lfloor |D|/3500 \rfloor$ 以下か
- [ ] $\hat{\rho}$ を CloudWatch で計測しているか
- [ ] $\hat{\rho}$ が $\rho_{\text{cross}}(r)$ を下回ったときにアラートが出るか
- [ ] キャッシュ書き込み（$c_w$）の回数を追跡しているか
- [ ] 問い間隔が TTL（5分）を超えていないか。超える場合は書き込み費用を再評価したか
- [ ] Bedrock 上でも閾値と ρ が成り立つか、少量の実測で確認したか
- [ ] Spot 中断時の再試行に指数バックオフとジッタ、上限回数とタイムアウトを設定しているか
- [ ] DynamoDB の Point-in-Time Recovery と KMS 暗号化を有効にしたか
- [ ] IAM ポリシーの Resource を ARN で限定しているか
- [ ] Cost Explorer でコスト配分タグを有効にしたか
- [ ] 品質評価（LLMジャッジなど）を圧縮比ごとに実施しているか

## 実験結果

論文の主な結果は次のとおりである。すべて論文の報告であり、本記事で再現実験を行ったものではない。

- **LongBench-v2（Table 7, Section 6.1）**: 文書サイズと圧縮比の16構成すべてで CAPC が最安だったと報告している。平均削減率は cache-only 比 49%（範囲 24〜67%）、query-aware 比 64%（範囲 42〜76%）、vanilla 比 90%（範囲 84〜94%）である。品質は、tier を保つ圧縮比では非圧縮のベースラインから 0.05 以内に収まったと報告している。品質の評価には Haiku 4.5 をジャッジとして使っている。
- **エンタープライズ業務アシスタント（Table 10, Section 6.3）**: 94,000トークンのツール定義を含む接頭辞で、$r = 3$ の CAPC は vanilla 比 51.7% の削減だったと報告している。ただし論文は、ツール配列が明示的に指定されていなくても暗黙にキャッシュされる現象を観測しており、この結果はその現象によって限定されると述べている（Section 7.1）。
- **graphify RAG（Table 12, 13, Section 6.4）**: FastAPI のコードベースでは cache-all の 9.3 倍安く、httpx では 2.4 倍安かったと報告している。キャッシュヒット率は 85% 以上だった。
- **τ-bench retail（Table 14, Section 6.5）**: 50タスクで CAPC の報酬は vanilla と同じ 36/50 だった（二比率の z = 0.00、p = 1.00）。コストは vanilla より 7.9% 安かった。query-aware 圧縮は vanilla より 40.1% 高かったと報告している。

τ-bench の 7.9% は、LongBench-v2 の 90% と大きく異なる。削減率は文書サイズや圧縮比、タスクによって大きく変わるため、見出しの数値だけで判断しないことが重要である。

### 制約・限界

論文自身が挙げている制約は次のとおりである。

- **単一モデル・単一TTL**: 測定は Sonnet 4.6 と5分TTLのみで行われている（Section 7.3）。論文は1時間TTLでは $\alpha = 2.0$ になると述べており、クロスオーバーの値はそのまま移せない。
- **LLMジャッジによる品質評価**: 品質は Haiku 4.5 によるジャッジで評価されており、人手の評価ではない（Section 7.4）。
- **合成データによる検証**: AdaptiveCacheBoundary の検証は、主に合成的なバージョン変動で行われている（Section 7.6）。
- **内容に依存する品質の崖**: 品質の崖は内容に依存するとして、限界の節で扱われている（Section 7.5）。
- **測定時期**: 論文は2026年5月に行われた測定を基にしている。API の仕様や単価は変わりうる。

## 実運用への応用

論文の主張を実運用に移すと、判断の手順は次のようになる。

1. 圧縮比 $r$ の候補を $r \le \lfloor |D|/3500 \rfloor$ の範囲で挙げる。
2. 本番で測定した $\hat{\rho}$ を $\rho_{\text{cross}}(r)$ と比べる。$\hat{\rho} < \rho_{\text{cross}}(r)$ なら、query-aware 圧縮の方が安い可能性がある。
3. 品質を圧縮比ごとに評価する。論文のLLMジャッジの結果は、そのまま本番に当てはまるとは限らない。
論文は測定を単一モデル・単一TTLに限っているため、他の設定への一般化は限定的だと述べている（Section 7.3）。

## 関連研究

論文は、既存研究と業界ガイダンスを5系統に分けて位置づけている（Table 1）。要旨によれば、圧縮の文献はクエリ依存の圧縮を標準とし、文献はしばしば ρ = 1.0 を仮定している。キャッシュ挙動の実測に基づく圧縮設計は、この空白を埋めるものとして位置づけられている。

## まとめ

論文は、Sonnet 4.6 のプロンプトキャッシュが約3,500トークンを境とする二層構造を持つと実測で示した。この構造を前提にすると、問い依存の圧縮はキャッシュを無効化し、コストを増やすことがある。論文が提案するCAPCは、問い非依存の圧縮を1回だけ行い、tier を保つ範囲で圧縮比を選ぶ手法である。論文は、LongBench-v2 の16構成で最安だったと報告しているが、τ-bench では削減幅が7.9%にとどまっていた。本番で導入する際は、論文の数値を前提とせず、自社の ρ と品質を測定することが必要である。
