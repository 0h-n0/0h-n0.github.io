## 論文概要（Abstract）

Model Context Protocol（MCP）は2024年11月にAnthropicが発表した、LLMと外部ツール・データ・サービスを接続するためのオープンプロトコルである。発表以降、コミュニティ主導で数百のMCPサーバーが開発されてきたが、本番環境での設計パターンを体系的に整理した研究は存在しなかった。

Rodriguesら（Celabe / University of Waterloo）は、音声AIプラットフォームANSYRの本番MCPサーバー5台と公式レジストリから選定した公開サーバー10台、計15台のコーパスを対象に質的コーディング分析を行い、5つのアーキテクチャパターンと4つのアンチパターンを抽出したと報告している。さらに認証・バージョニング・可観測性などの横断的関心事と、54台の追加サーバーを対象としたLLMレーターによる分類評価（Cohen's κ = 0.76）も提示されている。

## 背景と動機（Background & Motivation）

MCPはLLMがツール・リソース・プロンプトを動的に発見・実行するための標準プロトコルであり、Language Server Protocol（LSP）からインスピレーションを得て設計されている。しかし、MCPサーバーの設計について体系的なガイダンスは整備されておらず、開発者は個々の経験に依存してアーキテクチャを決定せざるを得ない状態にあった。

著者らは、MCPサーバー設計は本質的に「LLMクライアント向けのAPI設計」であると位置づけている。従来のREST APIではOpenAPI仕様やエンドポイント構造がインターフェースの中心だったが、MCPではツールの名前と説明文がLLMのツール選択を左右するため、設計上の考慮事項が従来のAPI設計とは異なる。この差分を著者らは「LLMクライアント・デルタ」と呼んでいる。

## 技術的詳細（Technical Details）

### 方法論とコーパス

著者らは2サイクルの質的コーディングを採用している。第1サイクルではオープンコーディングにより各サーバーから5種類のアーティファクト（ツール・リソース・プロンプト登録、トランスポート設定、セッション/状態管理、他MCPサーバーへの委譲、ドメインロジック）を抽出し、第2サイクルでパターンコーディングによりコードをグループ化したと報告している。候補がパターンとして採用される条件は、少なくとも2台のサーバーで独立に出現し、既存の解決策では十分に対処できないことである。

コーパスの構成は以下の通りである（論文Table IIより）。

| 区分 | サーバー数 | 例 |
|------|-----------|-----|
| 本番（ANSYR） | 5 | CRM読み取りゲートウェイ、音声ツール集約、テレフォニー/SIPアダプタ等 |
| 公開（MCPレジストリ） | 10 | filesystem, postgres, github, slack, puppeteer, memory, git等 |

### パターン1: Resource Gateway（データファサード）

**古典的祖先**: Repository / REST

**コンテキスト**: エージェントがデータベース、ドキュメントストア、サードパーティAPIから構造化データを読み取る必要がある場合。

**問題**: バックエンドデータを、プロンプトインジェクションから保護しつつ、バックエンドスキーマ変更に対して安定したインターフェースで公開する方法。

**解決策**: ゲートウェイが全データアクセスを仲介する。読み取り操作はMCPのResourceとして公開（list/get by ID）し、パラメータ化クエリはURIテンプレートでの表現が安全でない場合にToolとして公開する。サニタイゼーション層がバックエンドレスポンスからインジェクションコンテンツを除去する。

```python
from mcp.server import MCPServer

mcp = MCPServer()

@mcp.resource("customers/{customer_id}")
async def get_customer(customer_id: str) -> dict:
    """顧客情報を取得する（読み取り専用・冪等）"""
    raw = await db.customers.find_one({"_id": customer_id})
    return sanitize_response(raw)

@mcp.tool()
async def search_customers(query: str, limit: int = 10) -> list[dict]:
    """顧客を検索する（パラメータ化クエリはToolとして公開）"""
    results = await db.customers.find(
        {"$text": {"$search": query}}
    ).limit(limit).to_list()
    return [sanitize_response(r) for r in results]
```

**結果**: 単一のアクセス制御ポイント、バックエンド変更からの安定性、インジェクションリスクの封じ込め。一方、読み取りごとに1ホップ追加、複雑なJOINの扱いが困難という代償がある。

**既知の適用例**: PostgreSQL/MongoDBコネクタ、Notion/Google Driveブリッジ、GitHub/Jira/Linearラッパー

### パターン2: Tool Orchestrator（ワークフローファサード）

**古典的祖先**: Facade / Mediator

**コンテキスト**: チケット作成 → 担当者通知 → チャンネル投稿のように、アクションが複数システムにまたがる場合。

**問題**: LLMが各APIを理解し、中間状態を管理し、部分失敗を処理する必要をなくしたい。

**解決策**: 複合ツールが内部で全サブコールを実行し、1つのサマリーを返す。著者らは論文のListing 2で、3つのAPIを呼び出す`create_and_notify_ticket`ツールの例を示している。

```python
@mcp.tool()
async def create_and_notify_ticket(
    title: str, assignee: str, channel: str
) -> dict:
    """チケット作成→担当者通知→チャンネル投稿を一括実行（副作用あり）"""
    ticket = await jira.create_issue(title=title, assignee=assignee)
    await slack.send_dm(user=assignee, message=f"Ticket {ticket.key} assigned")
    await slack.post_message(channel=channel, text=f"New ticket: {ticket.key}")
    return {"ticket_key": ticket.key, "status": "created_and_notified"}
```

**結果**: LLMの推論負荷軽減、トランザクション的セマンティクス。代償として、サブツールの再利用が困難、部分失敗処理がサーバー側の責任となる。

**既知の適用例**: CI/CD自動化、DevOpsワークフロー、サポートアクションハブ

### パターン3: Stateful Session Server（セッション管理）

**古典的祖先**: Session / Memento

**コンテキスト**: マルチターン作業で後続呼び出しが先行状態に依存する場合（開いているファイル、トランザクション、認証済みユーザー等）。

**問題**: MCPのツール呼び出しはデフォルトでステートレスなリクエスト-レスポンスである。

**解決策**: 接続時にセッションIDを発行し、全呼び出しに付与する。サーバーはセッション単位のコンテキストをメモリ（水平スケール時はRedis）に保持し、非アクティブ時に期限切れとする。

```python
@mcp.tool()
async def open_file(session_id: str, path: str) -> dict:
    """ファイルを開いてセッションに関連付ける"""
    content = await fs.read(path)
    sessions[session_id] = {"path": path, "content": content}
    return {"status": "opened", "lines": len(content.splitlines())}

@mcp.tool()
async def edit_file(session_id: str, line: int, new_text: str) -> dict:
    """セッション内の開いているファイルを編集する"""
    ctx = sessions[session_id]
    lines = ctx["content"].splitlines()
    lines[line - 1] = new_text
    ctx["content"] = "\n".join(lines)
    return {"status": "edited", "line": line}
```

**結果**: 自然なマルチターンフロー、冗長なデータ転送の削減。代償として、セッション未回収時のメモリリーク、分散ストア必要性、LLMがセッションIDを正しく渡す保証がない。

Zenn記事で解説されているAgentCore Runtimeのセッションアフィニティ（`X-Amzn-Bedrock-AgentCore-Runtime-Session-Id`ヘッダー）は、このStateful Session Serverパターンのインフラ層での実装に相当する。

### パターン4: Proxy Aggregator（集約プロキシ）

**古典的祖先**: Proxy / API Gateway

**コンテキスト**: エージェントが複数サーバーの機能を必要とするが、クライアント接続数に制限がある、または運用者が認証・ログの一元化を求める場合。

**問題**: 複数のアップストリームサーバーを1つのエンドポイントとして提示しつつ、サーバー単位のアイデンティティ・バージョニング・障害分離を維持する方法。

**解決策**: プロキシがN個のアップストリームサーバーに接続し、ツール名にネームスペースプレフィックスを付与して衝突を回避し、各呼び出しを適切なアップストリームにルーティングする。著者らは2つのバリアントを提示している。

1. **Static-merge**: 全アップストリームツールの和集合を公開。設定は単純だが可視ツール数が増加
2. **Scoped**: リクエスト単位で関連サブセットのみ公開。ツール取得ステップが高速かつ正確である必要がある

```python
# Proxy Aggregatorのルーティング例
UPSTREAM_SERVERS = {
    "github": "http://github-mcp:8000/mcp",
    "slack": "http://slack-mcp:8000/mcp",
    "jira": "http://jira-mcp:8000/mcp",
}

@mcp.tool()
async def github__create_pr(title: str, branch: str) -> dict:
    """ネームスペース付きツール: githubアップストリームにルーティング"""
    return await forward_to_upstream("github", "create_pr", {
        "title": title, "branch": branch
    })
```

**結果**: クライアント設定の簡素化、認証・監査の一元化。代償として単一障害点、呼び出しごとの追加ホップ、ネームスペース管理の必要性がある。

### パターン5: Domain-Specific Adapter（ドメイン変換）

**古典的祖先**: GoFのAdapterパターン

**コンテキスト**: 既存システムのAPIがLLMにとって扱いにくい場合（機械可読ID、低レベル操作、複雑な認証、重い後処理等）。

**問題**: ビジネスロジックをサーバー側で再実装せずに、LLMが正確に使える形に変換する方法。

**解決策**: 4つの変換層を持つセマンティックアダプタを構築する。

1. **説明文**: ツール選択を導く人間可読な説明
2. **入力正規化**: 自然言語の日付・名前・曖昧なIDを正規化
3. **出力エンリッチメント**: IDを表示名に解決
4. **エラー変換**: APIエラーコードを平易な説明に変換

**結果**: 説明が正確であればツール選択精度が向上し、API複雑性が1層に隔離される。代償としてAPI変更時のメンテナンスコストがある。

### 古典パターンとの対応（論文Table Iより）

| MCPパターン | 古典的祖先 | LLMクライアント・デルタ |
|------------|-----------|----------------------|
| Resource Gateway | Repository / REST | LLM検索向けにリソースを命名 |
| Tool Orchestrator | Facade / Mediator | ツールセットをLLM選択精度に合わせてサイジング |
| Stateful Session Server | Session / Memento | 状態を暗黙化（プロンプトに含めない） |
| Proxy Aggregator | Proxy / API Gateway | コンテキストに収まるようツールを分割 |
| Domain-Specific Adapter | Adapter (GoF) | 自然言語ガードレールとしてバリデーションを実装 |

## アンチパターン（Anti-Patterns）

著者らは、コーパス内のサーバーを定義するものではなく、開発・コードレビューで繰り返し観察されたローカルな設計ミスとして4つのアンチパターンを記録している。

### 1. The God Tool

1つのツールが`do_anything(action, params)`のような汎用スキーマを持ち、LLMが"action"の意味を推測する必要がある。ツール選択精度が低下する。**修正**: 操作ごとに1つの名前付きツールを作り、各ツールに正確なスキーマと説明を持たせる。

### 2. Unsanitized Resource Content

ユーザー生成コンテンツ（コメント、ドキュメント本文、フォーム入力）がサニタイゼーションなしでリソースレスポンスに含まれ、埋め込まれた指示がLLMにコマンドとして読み取られる。**修正**: 外部ソースのコンテンツを全てサニタイズする。

### 3. Synchronous Long-Running Operations

動画エンコードのような長時間処理を単一のツール呼び出しでブロッキング実行する。MCPにはプログレス通知（2024年11月以降）や実験的タスク機能（2025年11月以降）が仕様として存在するため、これらを活用すべきである。**修正**: ジョブIDを返し、別のポーリングツールで状態確認する、またはプログレス通知を利用する。

### 4. Missing or Vague Tool Descriptions

LLMは説明文を読んでツールを選択するため、説明が不十分だとツールが無視されるか誤ったパラメータで呼び出される。**修正**: ツールが何をするか、いつ使うべきか、何を返すかを明記する。

## 横断的関心事（Cross-Cutting Concerns）

著者らは5つのパターン全てに共通する4つの横断的関心事を整理している。

### 認証（Authentication）

トランスポート層で認証し、トークンをツールセット単位にスコープし、呼び出し元のアイデンティティをログに記録する。Zenn記事で解説されているAgentCore RuntimeのCustom JWT認証設定は、この推奨に沿った実装である。

### エラー処理（Error Handling）

構造化されたツールエラーを返し、LLMがリトライの判断を推論できるようにする。Zenn記事のMCPエラーハンドリング（HTTP/JSON-RPCの2層モデル）と直接対応する。

### バージョニング（Versioning）

`initialize`レスポンスにバージョンを含め、マイグレーション中は旧スキーマを維持する。

### 可観測性（Observability）

呼び出しごとにツール名、入力ハッシュ、レイテンシ、出力サイズ、エラーコードをログに記録する。Zenn記事のOverheadLatencyメトリクスによるCloudWatch監視は、この可観測性パターンの具体的実装例に位置づけられる。

## 評価（Evaluation）

### パターン分類と評価者間信頼性

著者らは54台の追加MCPサーバーを対象に、2つのLLMレーター（Claude Haiku 4.5、Claude Sonnet 4）によるパターン分類を実施したと報告している。

| 指標 | 値 |
|------|-----|
| Cohen's κ（レーター間） | 0.76（95% CI [0.62, 0.88]） |
| 一致率（raw agreement） | 81.5% |
| 著者ラベルとの一致（Haiku） | 68.5% |
| 著者ラベルとの一致（Sonnet） | 75.9% |

不一致は3つの境界に集中していたと報告されている：(1) ステートフルネスは機能リストからは不可視、(2) ドメインロジックは関数説明からは不可視、(3) 読み取り型オーケストレータがResource Gatewayに見える。著者らはステートフルネスとドメインロジックを排他的カテゴリではなく横断的属性として扱うと述べている。

### トランスポートレイテンシ

著者らはループバック環境でのトランスポートオーバーヘッドを測定している（論文Table IIIより）。

| トランスポート | p50レイテンシ | 備考 |
|--------------|-------------|------|
| stdio（ローカル） | 0.01 ms | 実測値 |
| streamable-http（ローカル） | 0.39 ms | 実測値 |
| 同一リージョンリモート | 約30.4 ms | モデル値（ネットワークベースライン） |
| Stateful Session Server | 38.4 ms | モデル値 |
| Proxy Aggregator | 62.4 ms | モデル値 |

著者らは、ネットワークRTTがプロトコルオーバーヘッドを支配するため、サーバー配置がトランスポート選択より重要であると結論づけている。5行中3行はモデル値（同一リージョンのネットワークベースラインからの推定）であり、実測ではない点に注意が必要である。

## Production Deployment Guide

MCPサーバーをAWS上で5パターンに基づいて設計・運用する際の実装ガイドを示す。以下のコスト試算は2026年11月時点のAWS ap-northeast-1（東京）リージョン料金に基づく概算値であり、実際のコストはトラフィックパターンやリージョンにより変動する。最新料金は[AWS料金計算ツール](https://calculator.aws/)で確認されたい。

### AWS実装パターン（コスト最適化重視）

**トラフィック量別の推奨構成**:

| 規模 | 月間リクエスト | 推奨構成 | 月額コスト | パターン適用 |
|------|--------------|---------|-----------|------------|
| **Small** | ~3,000 (100/日) | Serverless | $50-150 | Resource Gateway + Domain Adapter |
| **Medium** | ~30,000 (1,000/日) | Hybrid | $300-800 | Tool Orchestrator + Session Server |
| **Large** | 300,000+ (10,000/日) | Container | $2,000-5,000 | Proxy Aggregator + 全パターン |

**Small構成の詳細**（月額$50-150）:
- **Lambda**: 1GB RAM, 30秒タイムアウト ($20/月) — Resource Gateway/Domain Adapterに最適
- **Bedrock**: Claude 3.5 Haiku, Prompt Caching有効 ($80/月)
- **DynamoDB**: On-Demand ($10/月) — セッション状態不要のステートレス設計
- **API Gateway**: REST API ($5/月) — streamable-http対応

**Large構成の詳細**（月額$2,000-5,000）:
- **EKS**: Proxy Aggregatorをメッシュとして配置 ($72/月)
- **EC2 Spot**: g5.xlarge × 2-4台 ($800/月) — Karpenter自動管理
- **ElastiCache Redis**: Stateful Session Serverのセッションストア ($50/月)
- **ALB**: パターン別ルーティング ($20/月)
