## 論文概要（Abstract）

本記事は [https://arxiv.org/abs/2501.03440](https://arxiv.org/abs/2501.03440) の解説記事です。

Uberが運用するGo・iOS・Androidの大規模モノレポにおいて、マージキューシステム「SubmitQueue」のCI効率を改善した研究について解説します。著者らは確率的モデルによるビルド優先度付けとMLベースのビルド時間予測を組み合わせ、CIリソース使用量を約53%、CPU使用量を約44%、P95待機時間を約37%削減したと報告しています。

この記事は [Zenn記事: Kiroスペック駆動開発×git worktreeでモノレポリファクタリングを並列化しCI検証を自動化する](https://zenn.dev/0h_n0/articles/8a678eb93c4aca) の深掘りです。Zenn記事で扱うモノレポCI自動化の背景として、実際の大規模モノレポでCIがどのようなボトルネックを抱え、どう解決されているかを理解するために有用です。

## 背景と動機（Background & Motivation）

大規模モノレポ（monolithic repository）では、多数の開発者が同時に変更をコミットするため、mainブランチを常にグリーン（全テスト通過）に保つことが困難です。Uberでは「SubmitQueue」と呼ばれるマージキューシステムを運用しており、変更を投機的（speculative）にビルドし、パスした変更のみをランディングさせる仕組みを採用しています。

しかし、既存のSubmitQueueには2つの問題がありました。第一に、投機的ビルドの多くが途中で中止（abort）され、リソースが浪費されていたことです。著者らによれば、主要モノレポにおいてビルドの40-65%が中止されていました。第二に、変更は投入順に処理されるため、小さな変更が大きな変更の後ろで待機し続ける問題がありました。

## 主要な貢献（Key Contributions）

- **貢献1**: BLRD（Bypassing Large Diffs）に対応した拡張確率的モデル。複数の投機的ビルドの優先度を計算し、必要確率の低いビルドをスケジュールから除外する
- **貢献2**: NGBoostによるビルド時間予測モデル。各変更のビルド完了時刻を正規分布でモデル化し、変更間の完了順序を閉形式で推定する
- **貢献3**: 投機閾値（speculation threshold）の導入。最小必要確率を設定し、低確率のビルドをスケジュールしないことでリソース浪費を削減する
- **貢献4**: 3つのモノレポ（Go・iOS・Android）での21週間にわたる本番環境での評価

## 技術的詳細（Technical Details）

### SubmitQueueと投機ツリー

SubmitQueueは変更の投入を受け付け、投機ツリー（speculation tree）を構築します。ツリーの各ノードは「ある変更が特定の先行変更の結果に依存してビルドされる状態」を表します。競合（conflict）する変更は枝分かれし、独立した変更は並列にビルドされます。

### BLRD（Bypassing Large Diffs）

BLRDは、小さな変更$C_2$が大きな変更$C_1$よりも先にランディングできるかを判定する機構です。$C_2$のビルド結果が$C_1$の有無に関わらず同一であれば、$C_1$を「バイパス」できます。著者らの報告によれば、BLRDのトリガー率はモノレポによって0%から45%の範囲で変動しています（論文Figure 4より）。

### 拡張確率的モデル

各投機的ビルド$B_C$の必要確率（needed probability）は以下の式で計算されます：

$$
P_{\text{needed}}(B_C) = \prod_{C_i \in \text{conflict}} P_{\text{outcome}}(B_{C_i}) \times \prod_{C_j \in \text{bypass}} P(\text{FT}_C < \text{FT}_{C_j})
$$

ここで、
- $P_{\text{outcome}}(B_{C_i})$: 競合する変更$C_i$のビルド結果の確率
- $P(\text{FT}_C < \text{FT}_{C_j})$: 変更$C$が変更$C_j$よりも先に完了する確率
- $\text{FT}$: 完了時刻（Finish Time）

バイパス対象が深い場合（確率積が0に近づく場合）、システムはオリジナルモデルにフォールバックし、最も確率の高いビルドのみをスケジュールします。

### ビルド完了順序の推定

各変更のビルド時間は正規分布$T \sim \mathcal{N}(\mu, \sigma^2)$でモデル化されます。変更$x$と$y$の到着時刻を$AT_x, AT_y$、予測ビルド時間の平均と標準偏差を$\mu_x, \sigma_x, \mu_y, \sigma_y$とすると、$y$が$x$より先に完了する確率は：

$$
P(\text{FT}_y < \text{FT}_x) = \Phi(Z)
$$

$$
Z = \frac{(AT_x - AT_y) - (\mu_y - \mu_x)}{\sqrt{\sigma_x^2 + \sigma_y^2}}
$$

ここで$\Phi$は標準正規分布の累積分布関数です。

**具体例**（論文Section VIIより）：
- 到着間隔5分、平均ビルド時間25分と20分、$\sigma$ 5と4の場合：$Z = 0$、確率$\approx 0.5$
- 到着間隔約8時間、平均20分と5分の場合：確率$\approx 0$（先に到着した方がほぼ確実に先に完了）
- 到着間隔1分、平均35分と15分、$\sigma$ 6と3の場合：$Z \approx 2.83$、確率$\approx 0.998$

### NGBoostによるビルド時間予測

ビルド時間予測にはNGBoost（Natural Gradient Boosting）回帰モデルを使用しています。NGBoostは点推定だけでなく予測分布（平均$\mu$と標準偏差$\sigma$）を出力できる確率的回帰手法です。

**モデルの特徴**（論文Section IXより）：
- 学習データ: 直近3ヶ月のビルド履歴、80%訓練/20%検証
- 再学習頻度: 週次
- プラットフォーム: Uber社内のMichelangelo ML基盤

**重要度上位の特徴量**:
1. 変更されたビルドターゲット数
2. 追加されたターゲット数
3. 削除されたターゲット数
4. 競合数
5. 投機ツリーの高さ
6. 追加行数・削除行数
7. 変更セット数・コミット数
8. 開発者名

**予測精度（MAPE）**:

| モノレポ | MAPE |
|---------|------|
| Go | 3% |
| iOS | 6% |
| Android | 3.5% |

著者らは誤差が概ね5%以下に収まると報告しています（論文Section IXより）。

### 投機閾値

投機閾値を設定しない場合、低確率のビルドもスケジュールされ、キャンセルとリソース浪費が発生します。閾値は履歴データから経験的に設定され、モノレポごとにチューニングされます。閾値を高く設定しすぎると、負荷が高い場合にランディング時間が悪化するため、バランスが重要です。

## 実装のポイント（Implementation）

著者らが報告する実装の構成は以下の通りです（論文Section IXより）：

- **コアサービス**: Java実装、MySQLストレージ、Bazelビルドシステム
- **キューシャーディング**: Apache Helix
- **イベント処理**: RxJava
- **シミュレータ**: 本番トラフィックをリプレイし、アルゴリズム変更を事前検証

シミュレータは投機的ビルド時間を本番ビルド時間の平均で近似しており、著者ら自身がこれを近似であると認めています。

```python
from dataclasses import dataclass
from scipy.stats import norm
import numpy as np

@dataclass
class Change:
    """マージキュー内の変更を表す"""
    arrival_time: float  # 到着時刻（分）
    mu: float            # 予測ビルド時間の平均（分）
    sigma: float         # 予測ビルド時間の標準偏差（分）

def prob_finishes_before(x: Change, y: Change) -> float:
    """変更yが変更xより先に完了する確率を計算する

    Args:
        x: 比較対象の変更（後に完了すると仮定する側）
        y: 先に完了するかを判定する変更

    Returns:
        P(FT_y < FT_x) の値
    """
    z_numerator = (x.arrival_time - y.arrival_time) - (y.mu - x.mu)
    z_denominator = np.sqrt(x.sigma**2 + y.sigma**2)
    if z_denominator == 0:
        return 0.5
    z = z_numerator / z_denominator
    return float(norm.cdf(z))

def compute_needed_probability(
    target: Change,
    conflicting: list[Change],
    bypassable: list[Change],
    outcome_probs: dict[int, float],
) -> float:
    """投機的ビルドの必要確率を計算する

    Args:
        target: 対象の変更
        conflicting: 競合する変更のリスト
        bypassable: バイパス可能な変更のリスト
        outcome_probs: 各競合変更のビルド成功確率

    Returns:
        必要確率 P_needed
    """
    p = 1.0
    for i, c in enumerate(conflicting):
        p *= outcome_probs.get(i, 0.5)
    for b in bypassable:
        p *= prob_finishes_before(b, target)
    return p
```

**CloudWatch Logs Insights クエリ**:

```sql
-- ビルドスケジューリング効率の監視
fields @timestamp, change_id, needed_probability, was_aborted
| stats avg(needed_probability) as avg_prob,
        sum(case when was_aborted = 1 then 1 else 0 end) as aborted_count,
        count(*) as total_builds
  by bin(1h)
| filter total_builds > 0
| sort @timestamp desc

-- NGBoost予測精度の監視
fields @timestamp, predicted_duration, actual_duration
| stats avg(abs(predicted_duration - actual_duration) / actual_duration * 100) as mape
  by bin(1d)
```

### ビルド対変更比（Builds-to-Changes Ratio）

著者らはロールアウト（2024年7月22日）前後の21週間（2024年5月13日〜9月30日）にわたるデータで評価を行っています。

## 実運用への応用（Practical Applications）

本論文の手法は、Zenn記事で扱うモノレポ CI/CD パイプラインの最適化に直接関連します。

**モノレポCIへの示唆**:
- `nx affected`のような差分ベースのタスク選択は「何をビルドするか」を最適化するが、本論文の手法は「いつ・どの順序でビルドするか」を最適化する。両者は補完的である
- worktreeベースの並列リファクタリングでは多数のブランチが同時にCIを要求するため、本論文の投機的スケジューリングのようなキュー管理が重要になる
- NGBoostによるビルド時間予測はCI待機時間の見積もりにも応用可能であり、開発者体験の改善に寄与する

**スケーリングの課題**:
著者らは投機閾値が静的である点を制約として認めており、リアルタイム負荷に応じた動的調整を将来課題として挙げています。また、シミュレータのビルド時間近似は本番環境との乖離がある点も指摘されています。

## 関連研究（Related Work）

- **GitHub Merge Queue / GitLab Merge Train**: 投機的実行や競合解決が不十分であると著者らは指摘している
- **BuildFast（ASE 2020）/ SmartBuildSkip（ICSE 2020）**: ビルド結果の予測に焦点を当てた研究。本論文はビルド「時間」の予測に特化している点で異なる
- **NGBoost（ICML 2020）**: 本論文が採用した確率的回帰手法。平均と分散の同時推定が可能
- **先行SubmitQueue論文（EuroSys 2019）**: 本論文の基盤となるシステム。BLRDとスケジューリング最適化は本論文の新規貢献

## まとめと今後の展望

本論文は、大規模モノレポにおけるCIリソース浪費の問題に対して、確率的モデルとML予測を組み合わせた実践的なアプローチを提案しています。Go・iOS・Androidの3つのモノレポでの21週間の本番評価により、ビルド対変更比で45-64%、CPU使用時間で35-52%、P95待機時間で31-45%の削減が確認されています。

今後の研究方向として、著者らは動的な投機閾値の調整、ビルド成功予測を活用したバッチサイズの適応的制御を挙げています。モノレポの規模が拡大する現代のソフトウェア開発において、本論文の知見はCI/CDパイプライン設計の重要な参考になります。
