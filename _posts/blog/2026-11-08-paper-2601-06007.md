本記事は [Don't Break the Cache: An Evaluation of Prompt Caching for Long-Horizon Agentic Tasks](https://arxiv.org/abs/2601.06007) の解説記事です。

## 論文概要（Abstract）

著者らは、多ターンのLLMエージェントにおけるプロンプトキャッシュの効果を、OpenAI・Anthropic・Googleの3プロバイダにまたがって評価したと報告している。DeepResearch Benchを用い、500を超えるセッションで4つのキャッシュ条件を比較した。著者らの報告では、キャッシュ戦略の選び方によって41〜80%のコスト削減と13〜31%のTTFT改善が得られ、単純な全コンテキストのキャッシュよりも、動的な内容を分離した設計のほうが安定して効果を出すという。

## 背景と動機

LLMエージェントは、ツール呼び出しを挟みながら1つのタスクを数十ターンかけて解く。各ターンのAPIリクエストには、システムプロンプト、ツール定義、それまでの会話履歴、ツールの実行結果を含めた全文を送る必要がある。そのため入力トークン数はターンを重ねるごとに増え続け、コストと応答遅延の両方に影響する。

プロンプトキャッシュは、リクエスト先頭から共通するプレフィックス（接頭部）について再計算を省く仕組みで、主要プロバイダが提供している。キャッシュが効けば入力コストとTTFT（Time To First Token）の低下が期待できる。一方でキャッシュは完全一致したプレフィックスに対して効くため、タイムスタンプやセッションIDのような動的な内容が先頭付近に混ざると、以降のキャッシュがヒットしなくなる。

著者らは、このトレードオフが実際にどの程度の効果を生むのか、そしてキャッシュ戦略の最適解がプロバイダごとに異なるのかを、3社横断で測定することを目的としている。本研究は3プロバイダを同一のベンチマークと条件で包括的に評価した点に新規性があると著者らは位置づけている。

## 主要な貢献

- OpenAI・Anthropic・Googleの3プロバイダを同一のDeepResearch Benchで比較し、多ターンエージェントにおけるプロンプトキャッシュを評価したと著者らは述べている。
- 4つのキャッシュ条件（No Cache、Full Context Caching、System Prompt Only、Exclude Tool Results）を定義し、コストとTTFTを比較している。
- プロンプト長とツール数についてアブレーションを行い、キャッシュ効果の主要因はツール数よりもプロンプト長であると報告している。
- 動的コンテンツがプレフィックスを壊すことを指摘し、キャッシュブロックの設計指針として整理している。

## 技術的詳細

### 実験設定

DeepResearch Benchは、22分野の博士レベルの調査課題100件からなるベンチマークとされている。エージェントは実際にWeb検索などのツールを呼び出し、その結果をコンテキストに積み上げながら調査レポートを作成する。

対象モデルは GPT-5.2、GPT-4o、Claude Sonnet 4.5、Gemini 2.5 Pro である。モデルごと、条件ごとに40セッション（独立 n=40）を実行し、システムプロンプトは10,000トークンとされる。条件間では24時間以上の待機を入れ、キャッシュのTTL（保持期間）切れが結果に混入しないようにしたと著者らは述べている。全体で500を超えるセッションという数字はこの設計から来ている。

### 4つのキャッシュ条件

- **No Cache（ベースライン）**: 各リクエストにUUIDを埋め込み、強制的にキャッシュミスを起こす。
- **Full Context Caching**: システムプロンプト、ツール定義、履歴、ツール結果など、会話全体をキャッシュ対象にする。
- **System Prompt Only**: システムプロンプトだけをキャッシュ対象にする。
- **Exclude Tool Results**: 履歴のうちツール結果を除いた部分をキャッシュ対象にする。

### コストの見積もり式

以下の式は、論文の定式化そのものではなく、結果の読み方を整理するための簡略化したモデルである。

ターン $t$ の入力トークン数を $L^{(t)}$ とし、そのうちキャッシュから読み出される部分を $L_c^{(t)}$、残りを $L_u^{(t)} = L^{(t)} - L_c^{(t)}$ とする。通常の入力単価を $p_u$、キャッシュ読み出しの単価を $p_r$ とすると、$T$ ターンのセッション全体の入力コストは次のように書ける。

$$
C_{\text{no}} = \sum_{t=1}^{T} p_u \, L^{(t)}, \qquad
C_{\text{cache}} = \sum_{t=1}^{T} \left( p_u \, L_u^{(t)} + p_r \, L_c^{(t)} \right)
$$

コスト削減率は次の式で定義する。

$$
R_{\text{cost}} = 1 - \frac{C_{\text{cache}}}{C_{\text{no}}}
$$

この簡略化では、キャッシュ書き込み時の割増料金と、プロバイダごとの最小キャッシュ長の制約を無視している。それでも、$L_c^{(t)}$ が大きくなるほど $R_{\text{cost}}$ が大きくなるという直感は捉えられる。TTFTについては、未キャッシュ部分の長さに概ね依存すると考えられるが、本記事では式を立てず、論文の報告値の解釈にとどめる。

## 実装のポイント

プレフィックスを安定させることが、キャッシュを効かせる最も基本的な条件である。システムプロンプトとツール定義の順序を固定し、タイムスタンプやリクエストごとのUUIDはプロンプトの末尾に置く。ツール定義のJSONは毎回同じ文字列になるように生成する。

キャッシュが有効になるための最小トークン数はプロバイダごとに異なるため、短いプロンプトでは効果が出ない場合がある。論文のアブレーションでは、プロンプト長がキャッシュ効果の主要因であると著者らは報告している。また、キャッシュの保持時間（TTL）を超えるとキャッシュは失効するため、ターン間隔が長いエージェントでは再書き込みのコストを考慮する必要がある。

APIレスポンスのusage情報からキャッシュ読み出しトークン数を記録し、ヒット率を監視することを推奨する。以下は静的部分と動的部分を分けて組み立てる例である。

```python
from __future__ import annotations

from dataclasses import dataclass


@dataclass(frozen=True)
class PromptLayout:
    """キャッシュ可能な静的部分と、毎ターン変わる動的部分を分けたプロンプト構成。"""

    system_prompt: str
    tool_schema_json: str

    def build_prefix(self) -> str:
        """キャッシュ対象になる、変化しない先頭部分を返す。

        Returns:
            システムプロンプトとツール定義を連結した文字列。
        """
        return f"{self.system_prompt}\n{self.tool_schema_json}"

    def build_turn(self, history: list[str], timestamp: str) -> str:
        """動的情報を末尾に置き、先頭のプレフィックスを壊さないようにする。

        Args:
            history: これまでの会話ログ。
            timestamp: 現在時刻などの動的情報。

        Returns:
            そのターンに送信する完全なプロンプト文字列。
        """
        body = "\n".join(history)
        return f"{self.build_prefix()}\n{body}\n[now] {timestamp}"
```

## Production Deployment Guide

本章は、論文の内容を踏まえて解説者が作成した運用設計の案である。論文が扱う範囲を超える部分を含む。AWSの料金は2026年11月時点の東京リージョン料金に基づく概算値として記載しているが、執筆時点で料金ページを照合した値ではない。実際の見積もりは AWS Pricing Calculator で行うこと。

### AWS実装パターン

トラフィック量ごとの推奨構成は次のとおり。

| 規模 | 月間リクエスト | 推奨構成 | 月額コスト |
|------|--------------|---------|-----------|
| Small | ~3,000 | Lambda + Bedrock + DynamoDB | $50-150 |
| Medium | ~30,000 | Lambda + ECS Fargate + ElastiCache | $300-800 |
| Large | 300,000+ | EKS + Karpenter + EC2 Spot | $2,000-5,000 |

**Small構成**では、Lambdaがリクエストの入口とターン制御を担い、Bedrockがモデル呼び出しを行う。会話状態はDynamoDBのOn-Demandモードに保存する。

**Medium構成**では、長時間のエージェントループをLambdaの実行時間制限（最大900秒）に収めにくくなるため、ECS Fargateのワーカーに移す。セッション状態と、ツール結果の一時キャッシュにはElastiCache（Redis互換）を使う。

**Large構成**では、EKSにKarpenterを載せ、中断に耐えるワーカーをEC2 Spotで動かす。

コスト削減の主な手段は次のとおり。

1. プレフィックスを安定させ、キャッシュヒット率を上げる（論文の知見に直接対応する）。
2. Spotは中断に耐えるワーカーに限定し、対話の応答経路はOn-Demandに置く。
3. 不要なツール定義を削り、プロンプト長を必要最小限にする。
4. ログの保持期間を短くし、CloudWatch Logsの取り込み量を抑える。
5. 安定した基盤負荷にはSavings Plansを検討する。

### セキュリティベストプラクティス

- **ネットワーク**: ワーカーは private subnet に配置し、Bedrock・DynamoDB へはVPCエンドポイント経由で通信する。インバウンドは ALB などの入口だけに限定する。
- **認証・認可**: IAMロールは最小権限にし、`bedrock:InvokeModel` は使用するモデルのARNに限定する。ワーカーに長期のアクセスキーを持たせない。
- **シークレット管理**: LLMのAPIキーはSecrets Managerに保管し、ローテーションを有効にする。環境変数へ平文で置かない。
- **監査**: CloudTrailを全リージョンで有効にし、IAMとSecrets Managerの操作を記録する。
- **データ保護**: 会話ログには個人情報が含まれうるため、保存前にマスキングし、保持期間を定める。KMSで保存データを暗号化する。

### 運用・監視設定

キャッシュ効果を確認するため、アプリケーションはターンごとに次のような構造化ログを出力する想定である（フィールド名は例）。

```
fields @timestamp, session_id, input_tokens, cache_read_tokens
| stats sum(cache_read_tokens) as cached, sum(input_tokens) as total by bin(1h)
| sort @timestamp asc
```

監視の柱は次のとおり。

- **CloudWatchアラーム**: Lambdaのエラー数、スロットリング、DynamoDBのスロットリングに閾値を設ける。キャッシュ読み出し比率が急に下がったときも通知する。
- **X-Ray・Cost Explorer**: ツール呼び出しごとのレイテンシを追い、月次コストをサービス別とタグ別に分解する。

ログは1行1イベントとし、プロンプト本文や個人情報は記録しない。

### コスト最適化チェックリスト

- [ ] システムプロンプトの先頭部分は毎ターン同じ文字列になっている
- [ ] ツール定義のJSONはキー順を固定して生成している
- [ ] タイムスタンプやUUIDはプロンプトの末尾に置いている
- [ ] 不要なツール定義を削除している
- [ ] プロンプト長がプロバイダの最小キャッシュ長を満たしている
- [ ] キャッシュ読み出しトークン数をログに記録している
- [ ] キャッシュヒット率のアラームを設定している
- [ ] ターン間隔がキャッシュのTTLを超えないよう設計している
- [ ] 会話履歴の要約・切り詰め方針を決めている
- [ ] 小さいモデルでツール選択などの前処理を行うか検討している
- [ ] Lambdaの実行時間が長い処理はECSやEKSへ移している
- [ ] DynamoDBはOn-Demandの利用量を定期的に確認している
- [ ] CloudWatch Logsの保持期間を設定している
- [ ] 不要なログ出力（プロンプト全文など）を止めている
- [ ] NAT Gatewayが不要な構成ではVPCエンドポイントを使っている
- [ ] Spotは中断に耐えるワーカーに限定している
- [ ] Karpenterのコンソリデーションが有効になっている
- [ ] Savings Plansの対象になる安定負荷を把握している
- [ ] AWS Budgetsで月次の上限と通知を設定している
- [ ] 料金は執筆時点の概算値であり、定期的に料金ページを確認している

## 実験結果

著者らは、最良の戦略がモデルごとに異なることを報告している。表1は、各モデルで最もコスト削減が大きかったモード、またはTTFTが最も改善したモードを示す（論文の表1を転記）。

| モデル | 最良モード | コスト削減 | TTFT改善 |
|---|---|---|---|
| GPT-5.2 | Excl. Tool Results | 79.6% | 13.0% |
| Claude Sonnet 4.5 | System Prompt | 78.5% | 22.9% |
| Gemini 2.5 Pro | System Prompt | 41.4% | 6.1% |
| GPT-4o | System Prompt | 45.9% | 30.9% |

表2は、全モードの比較を示す（論文の表2を転記。各セルは「コスト削減率 / TTFT改善率」）。

| モデル | Full Context | System Prompt | Excl. Tool Results |
|---|---|---|---|
| GPT-5.2 | 79.3% / 9.5% | 81.4% / 10.5% | 79.6% / 13.0% |
| Claude Sonnet 4.5 | 77.8% / 21.8% | 78.5% / 22.9% | 78.1% / 20.9% |
| Gemini 2.5 Pro | 38.3% / 6.0% | 41.4% / 6.1% | 27.8% / -2.9% |
| GPT-4o | 47.8% / -8.8% | 45.9% / 30.9% | 46.8% / 28.1% |

表2の負の値はTTFTが悪化したことを意味する。GPT-4oのFull Context Cachingでは8.8%の悪化、Gemini 2.5 ProのExclude Tool Resultsでは2.9%の悪化が報告されている。著者らは、全コンテキストのキャッシュが遅延を悪化させるケースがあると述べている。

プロンプト長のアブレーションでは、システムプロンプトを50,000トークンにした場合、GPT-5.2で89%、Claude Sonnet 4.5で88%のコスト削減が報告されている。GPT-4oのTTFTは4,290msから1,699msへ低下し、60%の改善となる（論文本文の値）。ツール数を3、5、10、20、50と変えたアブレーションでは、変動は10ポイント以内に収まったとされる。著者らは、キャッシュ効果を決める主要因はツール数よりもプロンプト長であると結論づけている。なお、Gemini 2.5 Proはアブレーションから除外されている。

## 実運用への応用

実務上の含意は、キャッシュの効き方が「何を毎ターン同じに保つか」で決まる点である。

一方で、最適な戦略はモデルによって異なる。Excl. Tool Resultsが最良となるのはGPT-5.2であり、Claude Sonnet 4.5ではSystem Prompt Onlyが最良である。したがって、本番の設定を決める前に、対象モデルでの計測を行うことが望ましい。

関連する Zenn記事 [プロンプトキャッシュのプレフィックス設計とマルチターン最適化で対話コストを90%削減する](https://zenn.dev/0h_n0/articles/a0eef8c309235f) のプレフィックス設計の考え方は本論文の知見と整合する。ただし両者の数値は条件が異なるため、直接比較はできない。

## 関連研究

本記事では関連研究を網羅的に調査していない。料金や最小キャッシュ長などの仕様は時期によって変わるため、各プロバイダの公式ドキュメントで一次情報を確認することが必要である。

## 制約と限界

著者らが挙げている限界は次のとおり。

- サーバー負荷によってTTFTがばらつく。TTFTの改善率は、計測時の負荷状況の影響を受ける。
- 価格とTTLは変更される可能性がある。論文の数値は計測時点のものである。
- キャッシュのヒットの有無を時間差から推測できる場合、タイミングによるサイドチャネルのセキュリティリスクがある。
- Gemini 2.5 Proはアブレーションから除外されており、プロンプト長やツール数の効果は3モデルでしか確認されていない。

論文の評価は、DeepResearch Benchと10,000トークンのシステムプロンプトという特定の条件に基づく。本記事は解説であり、筆者による追加の実験は行っていない。

## まとめと今後の展望

著者らは、多ターンのLLMエージェントにおけるプロンプトキャッシュを、OpenAI・Anthropic・Googleの3プロバイダで評価し、41〜80%のコスト削減と13〜31%のTTFT改善を報告している。最も一貫して安全な戦略はSystem Prompt Onlyであり、全コンテキストのキャッシュは遅延を悪化させるケースがあると著者らは述べている。

今後の課題として、価格やTTLの変化への追従、モデルの追加、より多様なタスクでの検証が挙げられる。実務では、プレフィックス設計を先に固めたうえで、対象モデルごとにキャッシュ戦略を計測することが妥当だと考えられる。
