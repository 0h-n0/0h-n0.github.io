## 論文概要（Abstract）

LAMaS（Latency-Aware Multi-Agent System）は、マルチエージェントシステムの並列実行におけるレイテンシを明示的に最適化するフレームワークである。著者らは、既存手法が精度とコストのみに焦点を当て、並列実行下のレイテンシ（クリティカルパスの長さ）を無視していることを指摘している。論文の実験結果によると、GSM8K、HumanEval、MATHの各ベンチマークで、ベースライン比38〜46%のクリティカルパス長削減を達成し、タスク精度を維持または向上させている。

## 背景と動機（Background & Motivation）

マルチエージェントシステムのオーケストレーション研究は、主に2つの目的関数を最適化してきた: タスク精度とAPIコスト。しかし著者らは、並列実行環境下では第3の指標——レイテンシ——が精度やコストとは独立した最適化対象であることを指摘している。

この区別が重要になる理由は、並列実行下でのレイテンシとコストの計算方法が根本的に異なるためである:

$$
\text{コスト} = \sum_{o \in \mathcal{O}} c(o) \quad \text{（加算的）}
$$

$$
\text{レイテンシ} = \sum_{\ell \in \mathcal{L}} \max_{o \in \mathcal{O}_\ell} t(o) \quad \text{（クリティカルパス）}
$$

コストは全オペレータの実行コストの総和だが、レイテンシは各レイヤーの最遅オペレータの実行時間の和で決まる。同じレイヤー内のオペレータは並列実行されるため、レイテンシには加算的に寄与しない。

例えば、2つのオペレータA（1秒）とB（3秒）が並列実行される場合:
- コスト: 1 + 3 = 4（加算的）
- レイテンシ: max(1, 3) = 3（クリティカルパスのみ）

このため、コスト最適化だけではレイテンシの改善は保証されない。精度を維持しながらレイテンシを削減するには、クリティカルパス上のオペレータを特定し、そこに焦点を当てた最適化が必要になる。

## 主要な貢献（Key Contributions）

- **レイテンシ認識型報酬設計**: タスクスコア、コスト、レイテンシを統合した報酬関数 $R = S - \lambda_c C - \lambda_t T$ の提案
- **クリティカルパス認識型クレジット割り当て**: クリティカルパス上のオペレータにのみレイテンシペナルティを適用する選択的勾配伝播
- **確率的スーパーネット**: レイヤーごとにオペレータを動的に選択・活性化するポリシーネットワーク
- **レイヤー間依存関係の除去**: 従来の逐次的なリファインメントオペレータを並列実行可能に再設計

## 技術的詳細（Technical Details）

### 確率的スーパーネットアーキテクチャ

LAMaSのコントローラは、レイヤーごとにオペレータを選択する自己回帰型ポリシーネットワークである。トポロジ $\mathcal{G}$ の生成確率は各レイヤーの選択確率の積で分解される:

$$
P_\theta(\mathcal{G} | x) = \prod_{\ell=1}^{L} \pi_\theta(\mathcal{V}_\ell | x, \mathcal{G}_{1:\ell-1})
$$

ここで、
- $\theta$: ポリシーネットワークのパラメータ
- $x$: 入力クエリ
- $\mathcal{V}_\ell$: レイヤー $\ell$ で選択されたオペレータの集合
- $L$: 最大レイヤー数（論文では $L=4$）

### 閾値ベースのオペレータ選択

各オペレータの活性化はtop-1選択ではなく、閾値ベースの選択で決定される:

$$
\mathcal{V}_\ell = \{o \mid o \in \text{top-}k(\mathcal{O}), \sum s_o > \tau\}
$$

ここで、$s_o$ はオペレータ $o$ の活性化スコア、$\tau$ は活性化閾値（論文では $\tau = 0.3$）である。この設計により、クエリの難易度に応じてレイヤー幅が動的に調整される。

### レイテンシ認識型報酬設計

グローバル報酬関数は以下の形式をとる:

$$
R = S - \lambda_c C - \lambda_t T
$$

ここで、
- $S$: タスクスコア（精度）
- $C$: 総コスト（トークン消費の加算）
- $T$: レイテンシプロキシ（クリティカルパス長）
- $\lambda_c, \lambda_t$: 重み係数（論文では $\lambda_t = 0.005$）

### クリティカルパス認識型クレジット割り当て

全オペレータに一様なレイテンシペナルティを適用すると、クリティカルパス上にないオペレータにも不要な勾配が伝播し、最適化が非効率になる。著者らはこの問題を「クレジット割り当て問題」と呼び、以下の選択的ペナルティで解決する:

各レイヤー $\ell$ のクリティカルパスオペレータを特定する:

$$
o_\ell^* = \arg\max_{o \in \mathcal{O}_\ell} \tilde{t}(o)
$$

オペレータレベルの報酬は:

$$
R(o) = \begin{cases}
S - \lambda_c C - \lambda_t \tilde{T} & \text{if } o = o_\ell^* \\
S - \lambda_c C & \text{otherwise}
\end{cases}
$$

これにより、レイテンシのボトルネックとなるオペレータだけに最適化の勾配が伝播する。

### レイテンシプロキシ指標

実測のwall-clock時間はキューイングやレート制限の影響を受けるため信頼性が低い。著者らは以下のプロキシ指標を使用する:

$$
\text{CP\_len} = \sum_{\ell \in \mathcal{L}} \max_{o \in \mathcal{O}_\ell} (N_{\text{out}}(o) + \gamma \cdot t_{\text{tool}}(o))
$$

ここで、$N_{\text{out}}(o)$ は出力トークン数、$t_{\text{tool}}(o)$ はツール実行時間、$\gamma = 50$ はスケーリング係数（1秒 = 50仮想トークン）である。

### オペレータの種類

LAMaSは6つの基本オペレータを実装している:

| オペレータ | 説明 | 並列性 |
|----------|------|--------|
| Generate | 直接的なテキスト/コード生成 | レイヤー内並列 |
| GenerateCoT | Chain-of-Thoughtによる推論 | レイヤー内並列 |
| MultiGenerateCoT | 多様性指向のCoT（3候補） | レイヤー内並列 |
| ScEnsemble | Self-consistencyによる集約 | 前レイヤー依存 |
| SelfRefine | エラー分析と反復改善 | 前レイヤー依存 |
| EarlyStop | 実行終了プレースホルダ | — |

### 学習目標

ポリシー勾配最適化を使用する:

$$
\mathcal{L}(\theta) = -\mathbb{E}_{\tau \sim \pi_\theta} \left[ \sum_{o \in \tau} R(o) \log \pi_\theta(o | x) \right]
$$

安定性のために、バッチごとの正規化ではなく指数移動平均による正規化を採用している。

## 実験結果（Results）

### クリティカルパス削減（論文Table 2より、MaAS比）

| データセット | 精度変化 | CP長削減 | 元CP長 → 最適化後 |
|------------|---------|---------|-----------------|
| GSM8K | +0.24% | **38.0%** | 1,475 → 914 |
| HumanEval | -0.89% | **42.4%** | 1,811 → 1,043 |
| MATH | +1.03% | **46.1%** | 2,219 → 1,196 |

すべてのベンチマークで、精度を維持しながら38〜46%のクリティカルパス長削減を達成している。MATHでは精度が+1.03%向上しつつ、CP長を46.1%削減している。

### 固定ベースラインとの比較（論文Table 1より、GSM8K）

| 手法 | コスト($) | 精度 |
|------|---------|------|
| Generate | 0.31 | 92.80% |
| Gen-CoT | 0.32 | 92.23% |
| CoT×5+SC | 1.96 | 92.99% |
| MaAS | 0.56 | 93.04% |
| **LAMaS** | **0.88** | **93.37%** |

LAMaSはCoT×5+SCと同等以上の精度を、半分以下のコストで達成している。

### アブレーション（論文Section 5.3より）

レイテンシ最適化を除去（$\lambda_t = 0$）した場合、並列実行を有効にしてもCP長の削減は大幅に悪化する。これは、並列化だけではレイテンシ削減が保証されないことの実証である。

## 実装のポイント（Implementation）

LAMaSの設計思想は、LangGraphの並列実行パターンに以下の示唆を与える:

1. **クリティカルパスの特定**: LangGraphの並列ノード実行において、レイテンシのボトルネックは最も遅いノードで決まる。Zenn記事のSend APIによる動的fan-outでは、並列ノード数を増やしてもクリティカルパス上のノードのレイテンシが律速になる

2. **レイヤー間依存関係の設計**: LAMaSがリファインメントオペレータを再設計して並列実行可能にしたように、LangGraphのSubGraph間の依存関係を最小化することがレイテンシ削減の鍵となる

3. **動的幅調整**: LAMaSの閾値ベース選択は、入力の難易度に応じて並列ノード数を調整する。LangGraphのSend APIでも、条件に応じてSendの数を変えることで同様の最適化が可能

4. **コストとレイテンシのトレードオフ**: 並列実行はレイテンシを削減するが、APIのレート制限に並列数分ヒットし、コストが増加する。LAMaSの報酬関数のように、コストとレイテンシのバランスを明示的に設計する必要がある

```python
from typing import TypedDict, Annotated
from operator import add
from langgraph.graph import StateGraph, START, END

class LatencyAwareState(TypedDict):
    query: str
    layer_results: Annotated[list[dict], add]
    critical_path_ms: float

def identify_critical_path(results: list[dict]) -> float:
    """クリティカルパスのレイテンシを計算

    Args:
        results: 各ノードの実行結果（latency_msフィールド含む）

    Returns:
        クリティカルパスのレイテンシ（ms）
    """
    layers: dict[int, list[float]] = {}
    for r in results:
        layer = r.get("layer", 0)
        latency = r.get("latency_ms", 0)
        layers.setdefault(layer, []).append(latency)

    return sum(max(latencies) for latencies in layers.values())

def build_latency_aware_graph(
    operators: list[dict],
    n_layers: int = 3,
) -> StateGraph:
    """レイテンシ認識型の並列実行グラフ構築

    Args:
        operators: オペレータ定義のリスト
        n_layers: レイヤー数

    Returns:
        コンパイル済みグラフ
    """
    builder = StateGraph(LatencyAwareState)

    for layer_idx in range(n_layers):
        layer_ops = [
            op for op in operators
            if op.get("layer") == layer_idx
        ]
        for op in layer_ops:
            node_name = f"layer{layer_idx}_{op['name']}"
            builder.add_node(node_name, create_operator(op))

            if layer_idx == 0:
                builder.add_edge(START, node_name)
            else:
                prev_layer_ops = [
                    o for o in operators
                    if o.get("layer") == layer_idx - 1
                ]
                for prev_op in prev_layer_ops:
                    prev_name = f"layer{layer_idx-1}_{prev_op['name']}"
                    builder.add_edge(prev_name, node_name)

    last_layer_ops = [
        op for op in operators
        if op.get("layer") == n_layers - 1
    ]
    for op in last_layer_ops:
        builder.add_edge(f"layer{n_layers-1}_{op['name']}", END)

    return builder
```

## 実運用への応用（Practical Applications）

LAMaSの知見は、LangGraphベースのプロダクションシステムに以下の形で応用できる:

1. **並列パイプラインのプロファイリング**: 各ノードの実行時間を計測し、クリティカルパスを特定する。LangGraphのチェックポイントにノードごとの実行時間を記録することで、最適化対象を定量的に判断できる

2. **適応的並列度制御**: クエリの複雑さに応じて並列ノード数を動的に調整する。簡単なクエリは少数のオペレータで高速処理し、複雑なクエリには多数のオペレータを投入する

3. **トークン予算に基づくオペレータ選択**: コスト制約の下でレイテンシを最小化するオペレータ選択。LAMaSの報酬設計は、API予算管理に直接応用できる

## 関連研究（Related Work）

- **MaAS** (Shi et al., 2024): LAMaSの直接的なベースライン。精度とコストの最適化に焦点を当て、レイテンシは考慮していない。LAMaSはMaASに対して38-46%のCP長削減を達成
- **AgentDropout** (2025): マルチエージェントシステムのリソース効率化。DAGトポロジをサポートするが、レイテンシ最適化は目的としていない
- **G-designer** (2025): グラフベースのマルチエージェント設計。DAGの自動構築を扱うが、並列実行下のレイテンシは最適化対象外

## まとめと今後の展望

LAMaSは、マルチエージェントシステムの並列実行において「コスト最適化だけではレイテンシ改善は保証されない」という重要な知見を実証的に示した。クリティカルパス認識型のクレジット割り当てにより、ボトルネックオペレータに選択的に最適化の勾配を伝播させるアプローチは、LangGraphの並列ノード設計にも直接的な示唆を与える。

Zenn記事で議論されているSend APIの動的fan-outパターンにおいても、単に並列数を増やすだけでなく、クリティカルパスを意識した設計が重要である。LAMaSの報酬設計（$R = S - \lambda_c C - \lambda_t T$）は、精度・コスト・レイテンシのバランスを定量的に管理するための指針となる。
