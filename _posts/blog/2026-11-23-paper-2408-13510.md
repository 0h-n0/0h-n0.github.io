## 論文概要（Abstract）

本記事は [https://arxiv.org/abs/2408.13510](https://arxiv.org/abs/2408.13510) の解説記事です。

LLM（大規模言語モデル）の推論リクエストには、プロンプト処理を行う**prefillフェーズ**とトークン逐次生成を行う**decodeフェーズ**がある。著者らは、既存のスケジューラがこれらを区別せず単一ジョブとして扱うために最適化が不十分となる問題を指摘している。本論文では、ワークロード特性を考慮したRL（強化学習）ベースのインテリジェントルーターを提案し、複数のLLMインスタンスへのリクエスト振り分けを最適化する手法を報告している。

## 背景と動機（Background & Motivation）

LLM推論では、1つのリクエストが2つの異なるフェーズを経る。prefillフェーズはプロンプト全体を一括処理してKVキャッシュを構築し、decodeフェーズはトークンを1つずつ自己回帰的に生成する。これらのフェーズはGPU上で異なる計算特性を持つ。prefillは計算バウンド（大量のトークンを並列処理）、decodeはメモリバウンド（逐次的なトークン生成）である。

既存のラウンドロビンやランダム割り当てでは、あるインスタンスにprefillが重いリクエストとdecodeが重いリクエストが混在すると、**prefill-decode干渉**が発生する。著者らは、prefill処理中に他のリクエストのdecode処理がプリエンプトされ、Time Between Tokens（TBT）が悪化する現象を観察したと報告している。

この問題に対し、インスタンス内のスケジューラを改善するアプローチには限界がある。著者らは、**インスタンス間のリクエスト分配（ルーティング）を最適化する方がレイテンシ改善に寄与する**と主張しており、実験でその効果を検証している。

## 主要な貢献（Key Contributions）

- **貢献1**: LLMリクエストのprefillフェーズとdecodeフェーズの混在がインスタンスレベルのスケジューリングに与える干渉を体系的に分析
- **貢献2**: 出力長を事前予測する軽量なDistilBERTベース分類器の構築（タスクタイプ付加で精度79.15%）
- **貢献3**: ヒューリスティック誘導型のRL（Double DQN）ルーターの設計。ワークロード混在の影響をMDPとして定式化
- **貢献4**: 推論スケジューラの比較用ベンチマーク標準の提案
- **貢献5**: Chunked PrefillやPrefix Cachingなど既存最適化との統合をサポートするプラグイン設計

## 技術的詳細（Technical Details）

### ワークロード分類

著者らは各リクエストをprefillフェーズとdecodeフェーズそれぞれについて「重い」か「軽い」かに分類する。論文で報告されている閾値は以下の通りである。

- **Heavy Prefill**: prefill処理に0.5秒以上かかるリクエスト
- **Heavy Decode**: decode処理に5秒以上かかるリクエスト

これにより、リクエストは**LL**（両方軽い）、**LH**（prefill軽い・decode重い）、**HL**（prefill重い・decode軽い）、**HH**（両方重い）の4クラスに分類される。同じクラスのリクエストをまとめてインスタンスに割り当てることでprefill-decode干渉を軽減できるという仮説が、本研究の出発点である。

### 動機付け実験

論文Figure 2で報告されている実験では、8リクエストを1リクエスト/秒で2インスタンスに割り当てる全探索を行っている。著者らによれば、最良の割り当てでE2Eレイテンシは27.03秒、最悪は32.34秒、ランダム割り当ての平均は29.81秒であり、最適割り当てとの差は約10%であったと報告されている。

### 出力長予測器

ルーティング時にdecodeの長さが未知であるため、著者らはDistilBERTベースのバケット分類器で出力長を事前予測する。

- **バケット定義**: 均等なトークン範囲ではなく、推定処理時間に基づく不等間隔バケット（0–0.5秒、0.5–2秒、2–4秒など）
- **タスクタイプの活用**: プロンプトにタスクタイプ（要約、コード生成など）を付加することで精度が向上。著者らは、タスクタイプなしでの精度が5.5%（不等間隔バケット）であったのに対し、タスクタイプ付加で**79.15%**に向上したと報告している（論文Section 5.1より）
- **タスクタイプ予測精度**: 93.79%

### MDP定式化とRLルーター

著者らはルーティング問題をマルコフ決定過程（MDP）として定式化している。

**状態空間**（27次元、4インスタンスの場合）:

$$
s_t = (Q_t,\ p_i,\ d_i^{\text{bucket}},\ \{P_m, D_m, C_m^t, \hat{T}_m^{\text{earliest}}\}_{m=1}^{M})
$$

ここで、
- $Q_t$: キュー長
- $p_i$: 次のリクエストのプロンプトトークン数
- $d_i^{\text{bucket}}$: 予測されたdecodeバケット
- $P_m, D_m$: インスタンス$m$のprefill/decodeトークン行列
- $C_m^t$: インスタンス$m$のキャパシティ（バッチサイズ、$P_m$、$D_m$の関数）
- $\hat{T}_m^{\text{earliest}}$: インスタンス$m$の最も早いリクエスト完了推定時刻

**行動空間**: $a \in \{0, 1, \ldots, M\}$（$M$はインスタンス数、$M$は「まだルーティングしない」を意味する遅延アクション）

**ワークロード混在ペナルティ**:

prefillフェーズのペナルティは以下の式で表される（論文Section 5.2より）:

$$
T = \text{grad}_1 \times \left(p_i^2 + \sum_j (p_j^m + d_j^m)\right)
$$

ここで$\text{grad}_1 = 3.2 \times 10^{-4}$であり、報酬は:

$$
r_p = \begin{cases} 1 & \text{if } T \leq \varepsilon \\ 1 - T/\varepsilon & \text{otherwise} \end{cases}
$$

decodeフェーズの報酬は:

$$
r_d = -\text{grad}_2 \times \left(\sum_j (p_j^m + d_j^m) + p_i + d_i\right)
$$

ここで$\text{grad}_2 = 3.3 \times 10^{-5}$。混在報酬は$r_{\text{mixing}} = \alpha \cdot r_p + (1 - \alpha) \cdot r_d$（$\alpha = 0.5$）である。

**報酬関数**（論文Eq. 3より）:

$$
r(s_t, a_t) = \underbrace{-\sum_j \frac{1}{\hat{T}_j}(1 - f_{j,t})}_{\text{待機ペナルティ}} + \underbrace{r_w \cdot \mathbb{1}[\text{完了}]}_{\text{完了報酬}} - \underbrace{(\gamma - \tilde{\gamma}_k) \cdot h(s_t, s_{t+1})}_{\text{ヒューリスティック誘導}}
$$

ここで、
- $\hat{T}_j$: リクエスト$j$の推定処理時間
- $f_{j,t}$: リクエスト$j$の進捗率
- $r_w = 60$: 完了報酬
- $h(s_t, s_{t+1})$: 選択されたインスタンスの混在ペナルティと最良代替の差分
- $\tilde{\gamma}_k = \lambda_k \gamma$（$\lambda_k = e^{-\beta_d \cdot k}$、$\beta_d = 0.5$）: 学習が進むにつれヒューリスティック誘導を減衰させるスケジュール

**学習**: Double DQN、ネットワーク構造は27→64→64→5（ReLU）、バッチサイズ512、探索はエピソード20で終了。

### アルゴリズム

```python
class IntelligentRouter:
    """RL-based workload-aware router for LLM instances."""

    def __init__(self, num_instances: int, model_path: str) -> None:
        self.num_instances = num_instances
        self.length_predictor = DistilBERTBucketClassifier(model_path)
        self.policy_net = DoubleDQN(
            state_dim=27, action_dim=num_instances + 1, hidden_dim=64
        )

    def route(self, request: Request, instance_states: list[InstanceState]) -> int:
        """Route a request to the optimal instance.

        Args:
            request: Incoming LLM request with prompt tokens.
            instance_states: Current state of each instance.

        Returns:
            Instance index (0 to M-1) or M for delay.
        """
        decode_bucket = self.length_predictor.predict(request.prompt)

        state = self._build_state(request, decode_bucket, instance_states)

        action = self.policy_net.select_action(state)

        if action == self.num_instances:
            return -1  # delay routing
        return action

    def _build_state(
        self,
        request: Request,
        decode_bucket: int,
        instance_states: list[InstanceState],
    ) -> np.ndarray:
        """Build 27-dimensional state vector."""
        state = [len(self.queue), request.prompt_tokens, decode_bucket]
        for inst in instance_states:
            state.extend([
                inst.prompt_matrix_sum,
                inst.decode_matrix_sum,
                inst.capacity,
                inst.earliest_completion,
                inst.batch_size,
                inst.pending_count,
            ])
        return np.array(state, dtype=np.float32)
```

## 実装のポイント（Implementation）

著者らの実装に関する報告から、実装上の重要な考慮点を以下にまとめる。

- **出力長予測のオーバーヘッド**: DistilBERTの推論はGPU上で1バッチ（64件）あたり0.01秒、CPU上では0.8秒と報告されている（論文Appendix A.3より）。本番環境ではGPU推論を推奨
- **ポリシーネットワーク**: 演算回数は$10^6$未満であり、ルーティング判断は十分高速
- **ルーティング頻度**: 0.02秒間隔で判断を行う設計
- **プロファイリングの必要性**: grad$_1$、grad$_2$の係数はモデル・ハードウェアの組み合わせごとにプロファイリングで取得する必要がある
- **遅延アクション**: すべてのインスタンスが高負荷の場合、ルーティングを遅延させるアクション($a = M$)が有効。ただし過度な遅延はキュー待ち時間を増大させるトレードオフがある

## 実験結果（Results）

### メインセットアップ

著者らは、Llama-2-7b-hfを4台のV100 GPUにデプロイし、vLLM（FCFSイテレーションレベルスケジューリング）を使用して実験を行ったと報告している。到着レートは20リクエスト/秒である。訓練にはIMDb、Eli5、WNUT、SQuAD、Booksの混合データセットから2,000リクエストを使用している。

### E2Eレイテンシ改善（論文Table 1相当）

| 手法 | Round Robin比改善率 |
|------|-------------------|
| **Workload-Guided RL（提案手法）** | **11.43%** |
| Workload-Aware RL | 7.79% |
| Baseline RL | 4.35% |
| Maximum Capacity Usage | 2.60% |
| Min-Min | 1.50% |
| Join Shortest Queue | 0.46% |

著者らは、ヒューリスティック誘導を導入した**Workload-Guided RL**が最も高い改善率を示したと報告している。Join Shortest Queue（JSQ）のような単純なヒューリスティックでは0.46%の改善にとどまり、ワークロード特性を考慮しないルーティングの限界が示されている。

### スケーラビリティ

8インスタンス（40リクエスト/秒）に拡張した場合、著者らはWorkload-Guided RLで**11.62%**の改善を報告しており、スケールアウト時にも有効性が維持されることを示している。

### 本番トレース（Cloud Provider X）

著者らは匿名のクラウドプロバイダの本番トレース（4,000リクエスト、平均プロンプト5,527トークン、平均decode 113トークン）でも評価を行っている。

| 手法 | E2Eレイテンシ（秒） | 改善率 |
|------|------------------|--------|

| Workload-Guided RL | 926.49 | **7.84%** |

本番環境ではプロンプトがdecodeに対して長いため、プリエンプションの影響が小さく、混合データセットよりも改善率が低いと著者らは分析している。

## 実運用への応用（Practical Applications）

本論文のアプローチは、Azure OpenAIやAmazon Bedrockのような複数デプロイメント構成でのリクエストルーティングに直接応用できる。Zenn記事で紹介されているAPIMバックエンドプールの重み付けルーティングに対し、本論文のワークロード分類に基づくルーティングは以下の点で補完的である。

- **TTFT/TBTの改善**: prefillが重いリクエストとdecodeが重いリクエストを分離することで、TBTのばらつきを低減できる
- **429エラーの予防**: インスタンスの負荷状態を考慮したルーティングにより、特定インスタンスへの過負荷を事前に回避できる
- **スケーリング判断**: Utilization V2の監視と組み合わせ、ルーティング精度の向上によりPTUの必要量を削減できる可能性がある

ただし、本論文のRLルーターは同種インスタンス構成を前提としており、PTUとPay-as-you-goの混在構成（異種インスタンス）への拡張は今後の課題として残されている。

## 関連研究（Related Work）

- **DistServe（Zhong et al., OSDI 2024）**: prefillとdecodeを異なるGPUに分離するアプローチ。本論文はインスタンス内での分離ではなく、インスタンス間のルーティング最適化に焦点を当てている点で相補的である
- **S³（Jin et al., 2023）**: 出力長予測に基づくスケジューリング手法。本論文の出力長予測器はS³のアプローチを拡張し、タスクタイプを活用して精度を向上させている
- **vLLM（Kwon et al., 2023）**: PagedAttentionによるメモリ管理。本論文のベースラインとして使用されており、vLLMのFCFSスケジューラの上にルーターを配置する構成が採用されている

## まとめと今後の展望

本論文は、LLM推論リクエストのprefill/decodeフェーズの特性差に着目し、ワークロード混在の影響をMDPとして定式化した上で、ヒューリスティック誘導型RLルーターを提案している。著者らは、Round Robinに対して最大11.43%のE2Eレイテンシ改善を報告しており、単純な負荷分散では解決できないLLM推論特有の課題に対するアプローチを示している。

今後の方向性として、著者らは(1)異種インスタンス構成への拡張、(2)スループットを報酬に含めた定式化の検討を挙げている。Azure OpenAIのような複数デプロイメントタイプを混在させるシナリオでは、異種インスタンス対応が実用上の重要な課題となる。
