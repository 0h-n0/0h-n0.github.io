## 論文概要（Abstract）

本論文は、LLMベースのエージェントで広く採用されているAgent Loopパラダイムの構造的限界を体系的に分析したポジションペーパーである。著者は70件のシステムを調査し、Agent Loopに共通する3つの欠陥——暗黙的なタスク依存関係、制御不能なリカバリ機構、実行履歴の変更可能性——を特定している。これらの問題を解決するために、Structured Graph Harness（SGH）と呼ばれるフレームワークを提案し、制御フローを暗黙的なコンテキストから明示的な静的DAGへと引き上げる設計を示している。SGHは古典的スケジューリング理論をLLMエージェントに適用する枠組みを提供し、ノード状態機械による終了保証と形式的な仕様を備えている。

## 背景と動機（Background & Motivation）

ReAct（Yao et al., 2023）やChain-of-Thought（Wei et al., 2022）の登場以降、LLMエージェントの多くは「観察→思考→行動」のループを繰り返すAgent Loopパターンを採用してきた。著者はこのパラダイムが、単純なタスクでは有効だが、複雑なマルチステップタスクにおいて根本的な構造的問題を抱えていると主張している。

具体的には、70件のLLMエージェントシステムを調査した結果、60%（42/70件）がAgent Loopアーキテクチャを採用しており、そのうち多くがタスク依存関係の不透明性、エラー回復の非決定性、実行計画の事後的書き換えという共通課題に直面していることが報告されている。著者はこの問題を古典的スケジューリング理論（Graham, 1969; Topcuoglu et al., 2002）の観点から再定式化し、LLMエージェント実行に特有の5つの課題（非決定的出力、推論エラーが主要障害モード、非冪等なリトライ、コンテキスト汚染リスク、副作用の安全性）を明示している。

## 主要な貢献（Key Contributions）

- **Agent Loopの3つの構造的欠陥の形式化**: 暗黙的依存関係、無制限リカバリ、可変実行計画の3点を理論的に特定し、なぜこれらがスケーラビリティの障壁となるかを分析
- **Structured Graph Harness（SGH）の提案**: 計画層・実行層・回復層の3層分離アーキテクチャにより、実行計画を不変DAGとして扱うフレームワーク設計
- **古典スケジューリング理論のLLMエージェントへの適用**: Ready Set計算、スケジューリングポリシー、ノード状態機械を含む形式的な実行システム定義（Definition 3.1）
- **70システムの体系的比較分析**: 9次元の評価軸（Multi-ready、Deterministic policy、Bounded recovery等）による分類と、Agent Loop・Event-driven・State-machine・Graph/Flowの各アーキテクチャの比較
- **7群実験プロトコルの設計**: 各アーキテクチャコンポーネントの寄与を分離可能な評価手法の提案

## 技術的詳細（Technical Details）

### Agent Loopの3つの構造的欠陥

著者が指摘する3つの構造的限界を詳しく見る。

**第1の欠陥: 暗黙的な依存関係（Implicit Dependencies）**。Agent Loopでは、ステップ間の依存関係がコンテキストウィンドウ内にのみ存在する。「コードを修正してからテストを実行する」というタスクにおいて、テスト実行がコード修正に依存するという事実はLLMの推論に暗黙的に埋め込まれているだけで、外部から検証できない。これにより、依存関係違反の検出やタスクの並列化が不可能となる。

**第2の欠陥: 無制限のリカバリ（Unbounded Recovery）**。ステップが失敗した場合、LLMが自律的にリトライ・スキップ・再計画を決定するが、どのリカバリアクションが利用可能かを規定する明示的な契約（contract）が存在しない。これにより、無限ループやリカバリの暴走が生じるリスクがある。

**第3の欠陥: 可変な実行計画（Mutable Execution Plans）**。LLMが実行途中で計画を修正すると、元の計画がコンテキスト内で上書きされる。この結果、実行計画の監査証跡（audit trail）が失われ、何が実行され何が変更されたかを事後的に追跡することが不可能となる。

### 形式的な実行システム定義

著者はDefinition 3.1において、実行システムを以下の5つ組として定義している。

$$
\mathcal{E} = (\mathcal{S}, \mathcal{U}, \mathcal{P}, \mathcal{O}, \Delta)
$$

ここで、
- $\mathcal{S} = \{(v, s_v) \mid v \in V, s_v \in \Sigma\}$: 各ノード$v$とその状態$s_v$の集合（グローバル状態）
- $\mathcal{U}: \mathcal{S} \to 2^V$: Ready Set関数。現在のグローバル状態から実行可能なノード集合を返す
- $\mathcal{P}: 2^V \to V$: スケジューリングポリシー。Ready Setから実行するノードを選択する決定的関数
- $\mathcal{O} = \{\text{success}, \text{failure}, \text{retry}, \text{escalate}\}$: 実行結果の空間
- $\Delta: \mathcal{S} \times V \times \mathcal{O} \to \mathcal{S}$: 状態遷移関数

Ready Setの計算は、DAGの位相順序に基づく。ノード$v$がReady Setに含まれる条件は以下の通りである。

$$
\mathcal{U}(\mathcal{S}) = \{v \in V \mid s_v = \text{ready} \land \forall (u, v) \in E: s_u = \text{executed}\}
$$

すなわち、ノード$v$自体がready状態であり、かつすべての先行ノード$u$がexecuted状態にあるとき、$v$は実行可能となる。Ready Setの濃度$|\mathcal{U}|$がスケジューラの特性を決定する。$|\mathcal{U}| \leq 1$ならば逐次実行、$|\mathcal{U}| \geq 2$ならば並列実行が可能となる。

### ノード状態機械（Node State Machine）

Definition 6.1に基づき、各ノードは以下の状態を持つ有限状態機械として定義される。

$$
\Sigma = \{\text{initial}, \text{ready}, \text{running}, \text{executed}, \text{failed}, \text{cancelled}\}
$$

終端状態は$\Sigma_{\text{term}} = \{\text{executed}, \text{failed}, \text{cancelled}\}$である。状態遷移は以下の規則に従う。

- $\text{initial} \to \text{ready}$: すべての先行ノードが$\Sigma_{\text{term}}$に到達
- $\text{ready} \to \text{running}$: スケジューラによる実行開始
- $\text{running} \to \text{executed}$: 実行成功（outcome = success）
- $\text{running} \to \text{failed}$: リカバリ予算を使い切った場合
- $\text{ready/initial} \to \text{cancelled}$: Join意味論による取り消し

### Join意味論

DAGの合流点（join）では、2種類の意味論が定義されている。

**all_of**: すべての先行ノードがexecutedになったときにreadyとなる。いずれかの先行ノードがfailedになった場合、合流ノードもfailedとなる。

**any_of**: いずれか1つの先行ノードがexecutedになった時点でreadyとなる。1つの先行ノードが成功すると、他の代替先行ノードはcancelledとなる。

著者は、first_of（複数ブランチが競合的に実行される意味論）を意図的に除外している。その理由として、競合的並列実行は検証可能性を損なうためと説明している。

### 3層分離アーキテクチャ（SGH）

SGHのコアとなる設計原則は、Definition 5.3で示される3層分離である。

**計画層（Planner Layer）**: 実行開始前にタスクを静的DAGに分解する。実行中にDAGの構造変更は許可されない。DAGはイミュータブルなコミットメントとして扱われる。

**実行層（Runtime Layer）**: 位相順序に従いノードを実行する。Ready Setの全ノードを並行ディスパッチし、各ノードの実行結果に基づいて状態遷移関数$\Delta$を適用する。

**回復層（Recovery Layer）**: 3段階のエスカレーションプロトコルを実装する。

### 3段階エスカレーションプロトコル

エラー回復は以下の3レベルで厳格に制御される。

**Level 1（Retry）**: 同一ノードを同一実行コンテキスト$\mathcal{C}_{\text{exec}}$で再実行する。一過性障害やマイナーなハルシネーションに対応する。試行回数は有限のバジェットで制約される。

**Level 2（Patch）**: LLMが修正介入（プロンプト書き換え、制約追加等）を生成するが、DAG構造自体は維持する。単一ノード内の推論エラーに対応する。

**Level 3（Replan）**: タスク全体を新しいDAGとして再分解する。新しい計画バージョンが生成され、旧バージョンとの差分が追跡可能となる。Level 1・2のリカバリバジェットを使い切った場合にのみ発動する。

各レベルは明示的な判断ポイントを持ち、バジェット上限により無制限の再帰が防止される。

### コンテキスト分離

SGHは実行コンテキストと診断コンテキストを分離する設計を採用している。

- **実行コンテキスト（$\mathcal{C}_{\text{exec}}$）**: タスクパラメータと現在のノード入力のみを含む
- **診断コンテキスト（$\mathcal{C}_{\text{diag}}$）**: 障害履歴とリカバリ試行記録を含む

この分離により、障害トレースが後続のLLM推論を汚染する「検証ギャップ」問題を防止する。

## 実装のポイント（Implementation）

SGHの概念をPythonで実装する際の主要なポイントを示す。ノード状態機械とReady Set計算は、Pythonの`graphlib.TopologicalSorter`と組み合わせることで効率的に実現できる。

```python
from __future__ import annotations

import enum
from dataclasses import dataclass, field
from typing import Callable, Awaitable


class NodeState(enum.Enum):
    """SGHノード状態機械（Definition 6.1）"""
    INITIAL = "initial"
    READY = "ready"
    RUNNING = "running"
    EXECUTED = "executed"
    FAILED = "failed"
    CANCELLED = "cancelled"

    @property
    def is_terminal(self) -> bool:
        """終端状態かどうかを判定する"""
        return self in (NodeState.EXECUTED, NodeState.FAILED, NodeState.CANCELLED)


class JoinSemantics(enum.Enum):
    """合流ノードの意味論"""
    ALL_OF = "all_of"   # すべての先行ノードが成功する必要がある
    ANY_OF = "any_of"   # いずれか1つの先行ノードが成功すればよい


@dataclass
class DAGNode:
    """DAGの各ノードを表現するデータクラス

    Attributes:
        node_id: ノードの一意識別子
        task: 非同期実行関数
        state: 現在のノード状態
        join: 合流意味論（デフォルトはall_of）
        retry_budget: Level 1リトライの残りバジェット
        patch_budget: Level 2パッチの残りバジェット
    """
    node_id: str
    task: Callable[..., Awaitable[str]]
    state: NodeState = NodeState.INITIAL
    join: JoinSemantics = JoinSemantics.ALL_OF
    retry_budget: int = 3
    patch_budget: int = 1
```

Ready Set計算の実装では、DAGの辺情報とノード状態を組み合わせる。

```python
from typing import Dict, Set, List, Tuple


def compute_ready_set(
    nodes: Dict[str, DAGNode],
    edges: List[Tuple[str, str]],
) -> Set[str]:
    """Ready Set U(S)を計算する（Definition 3.1）

    Args:
        nodes: ノードID→DAGNodeの辞書
        edges: (src, dst)の辺リスト

    Returns:
        実行可能なノードIDの集合
    """
    predecessors: Dict[str, List[str]] = {nid: [] for nid in nodes}
    for src, dst in edges:
        predecessors[dst].append(src)

    ready: Set[str] = set()
    for nid, node in nodes.items():
        if node.state != NodeState.READY:
            continue
        preds = predecessors[nid]
        if node.join == JoinSemantics.ALL_OF:
            # all_of: すべての先行ノードがexecuted
            if all(nodes[p].state == NodeState.EXECUTED for p in preds):
                ready.add(nid)
        elif node.join == JoinSemantics.ANY_OF:
            # any_of: いずれかの先行ノードがexecuted
            if any(nodes[p].state == NodeState.EXECUTED for p in preds):
                ready.add(nid)
    return ready
```

3段階エスカレーションの実装では、各レベルのバジェット管理が重要となる。

```python
import enum


class Outcome(enum.Enum):
    """実行結果空間 O（Definition 3.1）"""
    SUCCESS = "success"
    FAILURE = "failure"
    RETRY = "retry"
    ESCALATE = "escalate"


def escalation_handler(
    node: DAGNode,
    error: Exception,
) -> Outcome:
    """3段階エスカレーションプロトコルの判定ロジック

    Args:
        node: 失敗したノード
        error: 発生した例外

    Returns:
        次に取るべきアクション
    """
    # Level 1: リトライバジェットが残っている場合
    if node.retry_budget > 0:
        node.retry_budget -= 1
        return Outcome.RETRY

    # Level 2: パッチバジェットが残っている場合
    if node.patch_budget > 0:
        node.patch_budget -= 1
        return Outcome.ESCALATE  # パッチ生成へ

    # Level 3: 全バジェット消費→再計画へ
    node.state = NodeState.FAILED
    return Outcome.FAILURE  # 上位で replan を判断
```

実装上の注意点として、(1) DAGの非巡回性検証は`graphlib.TopologicalSorter`の`prepare()`で自動的に`CycleError`として検出される、(2) コンテキスト分離のために実行コンテキストと診断コンテキストを別オブジェクトとして管理する、(3) any_of joinでは成功ノード以外の代替ブランチを即座にcancelledに遷移させる必要がある。

## Production Deployment Guide

本論文はポジションペーパーであるが、SGHフレームワークの概念をDAGベースのエージェントオーケストレーションシステムとして実装・デプロイする場合の構成を示す。

### AWS実装パターン（コスト最適化重視）

**トラフィック量別の推奨構成**:

| 構成 | 想定規模 | AWSサービス | 月額概算 |
|------|----------|------------|----------|
| Small | ~100 DAG実行/日 | Lambda + Step Functions + DynamoDB + Bedrock | $80-200 |
| Medium | ~1,000 DAG実行/日 | ECS Fargate + Step Functions + ElastiCache + Bedrock | $400-900 |
| Large | 10,000+ DAG実行/日 | EKS + Karpenter (Spot) + Redis Cluster + Bedrock Batch | $2,500-6,000 |

**Small構成 (~100 DAG実行/日)**: AWS Step FunctionsがSGHの3層分離と直接対応する。Step Functionsのステートマシンが計画層のDAG構造を表現し、Lambda関数が実行層の各ノードを処理する。DynamoDBに実行コンテキスト($\mathcal{C}_{\text{exec}}$)と診断コンテキスト($\mathcal{C}_{\text{diag}}$)を分離して格納する。Step Functionsの組み込みリトライ・キャッチ機構がLevel 1/Level 2のエスカレーションに対応する。Lambda 128MB構成でBedrock Claude呼び出し1回あたり約$0.002、Step Functions状態遷移$0.000025/遷移。

**Medium構成 (~1,000 DAG実行/日)**: ECS Fargate上でDAGスケジューラをlong-runningプロセスとして実行する。ElastiCacheにReady Set計算結果をキャッシュし、ノード状態の高速読み書きを実現する。Bedrock APIへの並列リクエストを制御するためセマフォベースのレート制限を実装する。Fargate Spot利用で最大70%コスト削減。

**Large構成 (10,000+ DAG実行/日)**: EKS上にDAGスケジューラをデプロイし、KarpenterでSpot Instancesを自動プロビジョニングする。Redisクラスタでノード状態を管理し、複数のワーカーノードが並列にReady Setからタスクをポーリングする。Bedrock Batch APIで非リアルタイム処理を50%コスト削減。

**コスト削減テクニック**:
- Spot Instances活用（EKS/Fargate Spot）で最大90%コスト削減
- Reserved Instances（1年コミット）でオンデマンド比72%削減
- Bedrock Batch API使用で50%削減（レイテンシ許容時）

**コスト試算の注意事項**: 上記は2026年9月時点のAWS ap-northeast-1（東京）リージョン料金に基づく概算値である。実際のコストはDAG構造の複雑さ、ノードあたりのLLM呼び出し回数、リカバリ発生率により変動する。最新料金はAWS料金計算ツールで確認を推奨する。

**Cost Explorer自動レポート（Python）**:

```python
import boto3
from datetime import date, timedelta

ce = boto3.client("ce", region_name="ap-northeast-1")
sns = boto3.client("sns", region_name="ap-northeast-1")

def daily_cost_report(sns_topic_arn: str) -> dict:
    """日次コストレポートを取得しSNS通知する

    Args:
        sns_topic_arn: 通知先のSNSトピックARN

    Returns:
        コストデータの辞書
    """
    today = date.today()
    yesterday = today - timedelta(days=1)

    result = ce.get_cost_and_usage(
        TimePeriod={"Start": str(yesterday), "End": str(today)},
        Granularity="DAILY",
        Metrics=["UnblendedCost"],
        Filter={"Tags": {"Key": "Project", "Values": ["sgh-scheduler"]}},
        GroupBy=[{"Type": "DIMENSION", "Key": "SERVICE"}],
    )

    total = sum(
        float(g["Metrics"]["UnblendedCost"]["Amount"])
        for g in result["ResultsByTime"][0]["Groups"]
    )

    if total > 100:  # $100/日超過で通知
        sns.publish(
            TopicArn=sns_topic_arn,
            Subject="SGH Cost Alert",
            Message=f"Daily cost: ${total:.2f}",
        )

    return {"date": str(yesterday), "total_usd": total}
```

## 実験結果（Comparative Analysis）

本論文はポジションペーパーであり、実験結果ではなく比較分析と実験プロトコルの提案を行っている。

著者は70件のLLMエージェントシステムを調査し、以下の分布を報告している（論文Table 5付近）。

| アーキテクチャ | システム数 | 割合 |
|---------------|-----------|------|
| Agent Loop | 42 | 60% |
| Event-driven | 11 | 16% |
| Hybrid | 7 | 10% |
| Graph/Flow orchestration | 5 | 7% |
| State-machine | 4 | 6% |

著者はこの調査結果から、Agent Loopが支配的であるものの、Graph/Flow方式（LangGraphなど）が台頭しつつあることを指摘している。9次元の比較軸（Multi-ready、Deterministic policy、Bounded recovery、Immutable plan、Recovery protocol、Contract validation等）による13システムの詳細比較（Table 5）では、SGHが全次元で要件を満たす唯一の設計であると著者は主張している。

また、著者は7群の実験プロトコルを提案しているが、実験自体は未実施である。このプロトコルは、Baseline（Agent Loop）からOracle（完全計画）まで段階的にコンポーネントを追加し、各コンポーネントの寄与（$G_{\text{plan}}$, $G_{\text{scaffold}}$, $G_{\text{graph}}$, $G_{\text{patch}}$, $G_{\text{replan}}$）を分離可能に設計されている。測定変数として成功率、トークン消費量、成功率分散（安定性）、トレース完全性（可観測性）が挙げられている。

## 実運用への応用（Practical Applications）

SGHフレームワークの概念は、関連Zenn記事で実装したgraphlib + LangGraphベースのDAGスケジューラと直接対応する。Zenn記事のgraphlib.TopologicalSorterによるReady Set計算はSGHの$\mathcal{U}(\mathcal{S})$に相当し、LangGraphのSend() APIによるfan-out/fan-inはall_of/any_ofのJoin意味論に対応する。

プロダクション環境での適用においては、以下の点が重要となる。

**DAG設計の事前検証**: SGHの「イミュータブルなコミットメント」原則に従い、DAGの構造をデプロイ前にバリデーションする。非巡回性、到達可能性、Join整合性の3点を静的解析で検証する仕組みが必要である。

**スケーラビリティ**: Ready Setの濃度$|\mathcal{U}|$が並列度の上限を決定する。タスク分解の粒度を細かくすることで$|\mathcal{U}|$を大きくし、スループットを向上させることができる。ただし、ノード間通信のオーバーヘッドとのトレードオフが存在する。

**可観測性**: SGHの3層分離により、計画層・実行層・回復層それぞれの監視メトリクスを独立に設計できる。特にLevel 3 replanの発生率は、DAG設計の品質指標として有用である。

## 関連研究（Related Work）

- **ReAct（Yao et al., 2023）**: Agent Loopの代表的フレームワーク。SGHが批判するパラダイムの基盤
- **LangGraph（LangChain Team, 2024）**: グラフベースのエージェントオーケストレーション。SGHのGraph/Flow分類に該当するが、実行時のDAG変更を許容する点でSGHとは異なる
- **Task-Decoupled Planning / TDP（Li et al., 2026）**: 計画と実行の分離を提案。SGHの3層分離と類似するが、回復層の形式化が異なる
- **AutoGen（Wu et al., 2023）**: 会話型マルチエージェント。SGHの分類ではAgent Loop + Event-drivenのハイブリッドに位置する

## まとめと今後の展望

本論文は、Agent Loopの構造的限界を古典スケジューリング理論の枠組みで形式化し、SGHという3層分離アーキテクチャを提案したポジションペーパーである。70システムの比較分析は、現行のLLMエージェント設計の現状を俯瞰する資料として有用である。ただし、著者自身が認めるように、SGHの有効性は提案された7群実験プロトコルによる実証を待つ段階にある。DAGベースのエージェントオーケストレーションを設計・実装する際に、本論文が提示するReady Set計算、Join意味論、エスカレーションプロトコルの形式化は、設計判断の理論的根拠として参照できる。
