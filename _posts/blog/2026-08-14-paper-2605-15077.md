本記事は [Concurrency without Model Changes: Future-based Asynchronous Function Calling for LLMs](https://arxiv.org/abs/2605.15077) の解説記事です。

## 論文概要（Abstract）

AsyncFCは、LLMエージェントの関数呼び出しにおける同期的ブロッキングを解消するフレームワークである。著者らは、LLMのデコード処理と関数実行を分離し、未解決の実行結果をFutureプレースホルダとして扱う非同期パラダイムを提案している。論文の実験結果によると、モデルの再訓練やプロトコル変更なしに、SWE-bench Liteで1.44倍、BFCL v3で1.22倍のレイテンシ短縮を達成し、タスク精度を維持している。

## 背景と動機（Background & Motivation）

現在のLLMエージェントにおける関数呼び出しは、同期的に動作する。LLMが関数呼び出しを生成すると、その関数の実行が完了するまでLLMのデコードが停止する。この「デコード→実行→デコード→実行」の逐次パターンは、ツール実行のレイテンシがLLMのデコード時間を上回る場合に深刻なボトルネックとなる。

著者らは、このブロッキング問題を2つの並列化の観点から分析している:

1. **デコード・実行オーバーラップ**: LLMがデコードを続けている間にバックグラウンドで関数を実行する
2. **関数間並列性**: 依存関係のない関数を同時に実行する

従来のアプローチ（OpenAIのParallel Function CallingやLLMCompiler等）は関数間並列性に焦点を当てているが、デコード・実行のオーバーラップを実現するものはなかった。AsyncFCは両方を同時に実現する初めてのフレームワークである。

## 主要な貢献（Key Contributions）

- **実行層フレームワーク**: モデルの再訓練やファインチューニングなしに、標準の同期関数呼び出しプロトコル上で動作する非同期実行層
- **Futureベースのシンボリック推論**: LLMが未解決の実行結果を表すFutureプレースホルダに対して推論する能力を実証。これはモデルの「ネイティブ能力」であり、追加訓練は不要（論文Section 4.1より）
- **依存関係認識スケジューリング**: Read/Writeセット解析に基づく関数間の依存関係検出と、安全な並列実行の保証
- **非同期思考への拡張**: 外部関数だけでなく、委任された思考タスクも「長レイテンシの関数呼び出し」として扱い、思考の並列化を実現

## 技術的詳細（Technical Details）

### Futureプレースホルダの仕組み

AsyncFCの中核は、関数呼び出しの結果を即座に返すのではなく、Futureプレースホルダを返す点にある。

```mermaid
graph LR
    LLM[LLMデコード] -->|関数呼び出し| RT[AsyncFCランタイム]
    RT -->|Futureプレースホルダ即返| LLM
    RT -->|非同期実行| EXEC[関数実行]
    EXEC -->|結果| RT
    RT -->|ターン境界で結果統合| LLM
```

従来の同期呼び出し:

```
LLM: call search("Microsoft") → [BLOCKED 2秒] → 結果受信 → 次のcall生成
```

AsyncFC:

```
LLM: call search("Microsoft") → Future<$f1>即返 → call search("Apple") → Future<$f2>即返
[バックグラウンドで$f1, $f2が並列実行中]
LLM: await_futures → [結果統合] → 次の処理
```

### スキーマ変換

AsyncFCはツールのスキーマを自動的に変換し、引数がFuture値も受け取れるようにする。元の関数実装は変更不要である。

```python
# 元のスキーマ（同期）
def search(query: str) -> dict:
    """検索を実行し結果を返す"""
    ...

# AsyncFCによる自動変換後のスキーマ（概念的）
def search(query: str | FutureRef) -> Future[dict]:
    """引数にFutureを受け取り、Futureを返す"""
    ...
```

LLMから見ると、関数呼び出しの返り値がFutureプレースホルダに置き換わるだけで、呼び出しプロトコル自体は変わらない。

### 依存関係認識スケジューラ

AsyncFCのスケジューラは3段階のパイプラインで構成される:

**1. Admission Barrier（入場バリア）**

関数呼び出しはデコード順にエンキューされ、参照する状態パスが解決済みであることを確認してからState Treeに入場する。

**2. Conflict Analysis（競合解析）**

State Tree上で、新しい関数呼び出しのRead/Writeセットと、既に登録されている関数のアクセスラベルを比較し、依存関係を検出する。

リソースは階層的なパス形式で表現される:

```python
@op(
    reads=[{"/vehicle/doors": True}, {"/vehicle/fuel": True}],
    writes=[{"/vehicle/drive": True}],
)
def start_engine(ignition_mode: str) -> dict:
    """エンジンを始動する"""
    ...
```

**3. Execution（実行）**

ワーカーは未解決の引数Futureをローカルで待機してから実行する。完了時に結果Futureを解決し、アクセスラベルを除去する。

### 高速化の理論的上界

著者らは高速化比率の理論的上界を以下の式で定義している:

$$
R = \frac{T_{\text{LLM}} + T_{\text{tool}}}{\max(T_{\text{LLM}}, T_{\text{cp}})}
$$

ここで、
- $T_{\text{LLM}}$: LLMの総デコード時間
- $T_{\text{tool}}$: ツールの総実行時間
- $T_{\text{cp}}$: クリティカルパスの実行時間（依存関係のある最長のツール実行チェーン）

この式から2つの高速化モードが導かれる:

1. **低レイテンシツール** ($T_{\text{tool}} \ll T_{\text{LLM}}$): デコード・実行オーバーラップが支配的。高速化は $R \approx 1 + T_{\text{tool}} / T_{\text{LLM}}$
2. **高レイテンシツール** ($T_{\text{tool}} \gg T_{\text{LLM}}$): 関数間並列性が支配的。高速化は $R \approx T_{\text{tool}} / T_{\text{cp}}$

論文のレイテンシスイープ分析（Figure 5）によると、この遷移は1関数あたり5-10秒の遅延付近で発生する。

### エラーハンドリング

関数が失敗した場合、AsyncFCは推移的に依存するすべての後続関数呼び出しをキャンセルし、独立した呼び出しはそのまま実行を継続する。

```python
# 概念的なエラー伝播
def on_function_failure(failed_future: FutureRef):
    """失敗した関数に推移的に依存する関数をキャンセル"""
    dependents = state_tree.get_transitive_dependents(failed_future)
    for dep in dependents:
        dep.cancel()
    # 独立した関数はそのまま実行継続
```

## 実装のポイント（Implementation）

AsyncFCの設計思想は、LangGraphのReducerパターンおよびSend APIと以下の点で対応する:

1. **Futureプレースホルダ ↔ Reducer**: AsyncFCのFutureが並列実行の結果を後で統合する仕組みは、LangGraphの`Annotated[list, add]`によるReducerパターンと同じ設計意図を持つ。Reducerは並列ノードの書き込みを安全にマージし、データ消失を防ぐ

2. **Read/Writeセット解析 ↔ 状態キーの分離**: AsyncFCのリソースパスに基づく依存関係解析は、LangGraphにおけるSubGraphごとの状態キー分離と同じ目的を果たす。独立した関心事を分離することで並列実行を安全にする

3. **非同期実行 ↔ Send APIの動的fan-out**: AsyncFCの非ブロッキングディスパッチは、LangGraphのSend APIによる動的fan-outパターンに対応する。実行時にノード数を決定し、並列実行後に結果を集約する

4. **エラー伝播 ↔ 状態遷移のエラーハンドリング**: AsyncFCの推移的依存キャンセルは、LangGraphの条件付きエッジによるエラーハンドリングパスと同じ設計パターンである

```python
from typing import TypedDict, Annotated
from operator import add
from langgraph.graph import StateGraph, START, END
from langgraph.types import Send
import asyncio

class AsyncState(TypedDict):
    queries: list[str]
    results: Annotated[list[dict], add]

def route_to_async_workers(state: AsyncState) -> list[Send]:
    """AsyncFCのFutureディスパッチをSend APIで実現"""
    return [
        Send("async_worker", {"query": q, "index": i})
        for i, q in enumerate(state["queries"])
    ]

def async_worker(state: dict) -> dict:
    """非同期ワーカー（各関数呼び出しに対応）"""
    result = execute_tool(state["query"])
    return {"results": [{"index": state["index"], "result": result}]}

def aggregate(state: AsyncState) -> dict:
    """結果集約（Futureの解決に対応）"""
    sorted_results = sorted(state["results"], key=lambda r: r["index"])
    return {"results": sorted_results}

builder = StateGraph(AsyncState)
builder.add_node("async_worker", async_worker)
builder.add_node("aggregate", aggregate)
builder.add_conditional_edges(START, route_to_async_workers)
builder.add_edge("async_worker", "aggregate")
builder.add_edge("aggregate", END)
```

## 実運用への応用（Practical Applications）

AsyncFCの非同期パラダイムは以下のプロダクションシナリオで有効である:

1. **ソフトウェアエンジニアリングエージェント**: SWE-bench Liteでの1.44倍高速化は、コード生成・テスト・デバッグの反復サイクルを短縮する。ファイル読み書きやテスト実行をバックグラウンドで行いながら、LLMが次のコード変更を推論できる

2. **マルチステップ検索パイプライン**: Web検索、DB検索、API呼び出しを含むRAGパイプラインで、各検索をFutureとしてディスパッチし、LLMが検索結果を待たずに次のクエリ計画を立てられる

3. **デコード・実行のオーバーラップ**: 高速なツール（計算、文字列操作等）でもデコード時間中にオーバーラップすることで、累積的なレイテンシ削減が得られる

## 関連研究（Related Work）

- **LLMCompiler** (Kim et al., ICML 2024): DAGベースの並列関数呼び出し。関数間並列性に焦点を当て、最大3.7倍の高速化を達成。AsyncFCはこれに加えてデコード・実行オーバーラップを実現する
- **OpenAI Parallel Function Calling**: APIレベルの並列関数呼び出し。AsyncFCのベースラインの1つ（AsyncFC(P)がこれに相当）
- **Speculative Tool Calling** (2605.13360): 投機的ツール実行による高速化。AsyncFCとは異なるアプローチだが、同じ「LLMデコードとツール実行のオーバーラップ」という目標を共有

## まとめと今後の展望

AsyncFCは、LLMが未解決のFutureプレースホルダに対して推論する「ネイティブ能力」を発見し、それを活用した非同期関数呼び出しフレームワークを実現した。モデルの変更なしにレイテンシを最大1.44倍短縮できることは、既存のLLMエージェントシステムへの後付け適用を可能にする。

LangGraphの文脈では、Send APIとReducerパターンが提供する並列実行の基盤の上に、AsyncFCのデコード・実行オーバーラップの概念を追加することで、さらなるレイテンシ削減が期待できる。Zenn記事で議論されている「逐次処理比で60〜70%の短縮」は、LLMCompiler的な関数間並列性によるものだが、AsyncFCのオーバーラップを加えることでさらに改善の余地がある。
