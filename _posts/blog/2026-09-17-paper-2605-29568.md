## 論文概要（Abstract）

DeepToolは、LLMによるツール統合推論（Tool-Integrated Reasoning, TIR）において、思考・行動・観察のインターリーブプロセス内で熟考（deliberation）をスケールさせるフレームワークである。著者らは、MOSAIC軌跡合成・冷起動ファインチューニング・プロセス監督型強化学習の3段階パイプラインを提案し、Qwen2.5-7BベースでAIME24を3.2%から40.4%へ改善したと報告している。

## 背景と動機（Background & Motivation）

従来のツール統合推論（TIR）では、LLMがPythonインタプリタ等の外部ツールを逐次呼び出して数学的推論を行う。しかし、既存手法には大きな課題がある。モデルがツール呼び出しの間に十分な「熟考（deliberation）」を行わず、戦略的な思考なしに機械的にコードを生成・実行する傾向がある。

具体的には、(1) ツール呼び出し間の思考が浅く、エラー発生時の自己修正能力が低い、(2) 単一ツール呼び出しで問題を解こうとし、複数ステップの分解ができない、(3) 環境からの予期せぬ出力（実行エラー、タイムアウト等）に対する適応力が不足している、という3つの問題が著者らによって指摘されている。DeepToolはこれらの課題に対し、インターリーブ型の熟考をプロセス監督型強化学習で強化するアプローチを提案している。

## 主要な貢献（Key Contributions）

- **MOSAIC軌跡合成**: Manager-Actor階層フレームワークにより、戦略的意図と実行を分離した高品質な訓練データを自動合成する手法を提案。敵対的摂動（adversarial perturbation）により、モデルのエラー回復能力を訓練データレベルで強化
- **Action-Centric Process Reward**: 従来の結果ベース報酬に代わり、各ステップの行動（コード生成）に対してGestalt Pattern Matchingベースの類似度報酬を与えるプロセス監督型報酬関数を設計
- **状態保存型インターリーブ思考**: 思考・コード生成・実行結果の3要素を保持しながら推論を進める構造化フォーマットにより、AIME25で25.8%から30.0%への改善を実現（論文Table 5より）

## 技術的詳細（Technical Details）

### アーキテクチャ/手法

DeepToolの3段階パイプラインの核心は、MOSAIC（Manager-Orchestrated Synthesis with Adversarial Interleaved Challenges）軌跡合成にある。

#### Stage 1: MOSAIC軌跡合成

Manager $\pi_M$ とActor $\pi_A$ の2層構造で訓練データを生成する。各ステップ$t$において、Managerは履歴 $H_t$ に基づき戦略的意図 $I_{t+1}$ を生成する。

$$
I_{t+1} \sim \pi_M(\cdot \mid x, y^*, H_t)
$$

ここで、
- $x$: 入力問題
- $y^*$: 正解
- $H_t = \{(th_1, a_1, o_1), \ldots, (th_t, a_t, o_t)\}$: ステップ$t$までの履歴（思考・行動・観察の三つ組）

Actorは意図 $I_{t+1}$ を受けて、具体的な思考 $th_{t+1}$ と行動 $a_{t+1}$ を生成する。

敵対的摂動演算子 $\Phi$ が確率 $\rho$ で適用され、2種類の故障モードを注入する。

$$
\Phi = \begin{cases}
\Phi_{\text{gen}} & \text{(内因性生成異常: コードのバグ注入)} \\
\Phi_{\text{env}} & \text{(外因性環境故障: タイムアウト、メモリエラー等)}
\end{cases}
$$

著者らはSFTフェーズで $\rho = 0.1$、RLフェーズで $\rho = 0.2$ を使用したと報告している。

#### Stage 2: 冷起動ファインチューニング

2つの構造化スキーマで訓練データをフォーマットする。

- **Schema 1（中間ステップ）**: `<think>思考</think><code>コード</code><interpreter>実行結果</interpreter>`
- **Schema 2（最終ステップ）**: `<think>思考</think><answer>最終回答</answer>`

OpenR1-Math-220kから8,000インスタンスを選択し、最大シーケンス長15,000トークンでSFTを実施する。

#### Stage 3: プロセス監督型強化学習

Action-Centric Process Rewardは以下の式で定義される。

$$
r(s_t, s_t^*) = I_{\text{fmt}}(th_t, a_t) \cdot r_{\text{sim}}(a_t, a_t^*)
$$

ここで、
- $s_t = (th_t, a_t)$: ステップ$t$の状態（思考と行動）
- $s_t^*$: 参照軌跡のステップ$t$
- $I_{\text{fmt}}$: フォーマット整合性インジケータ（正しいスキーマに従っているか）
- $r_{\text{sim}}$: 行動類似度報酬

行動類似度 $r_{\text{sim}}$ にはGestalt Pattern Matchingを採用している。

$$
r_{\text{sim}}(a_t, a_t^*) = \frac{2 \cdot \sum_{k} \text{len}(k)}{|a_t| + |a_t^*|}
$$

ここで、$k$ は $a_t$ と $a_t^*$ の間の最長共通部分列群、$\text{len}(k)$ はその長さである。

最適化にはGRPO（Group Relative Policy Optimization）を使用し、KLダイバージェンス制約の係数を $\beta = 0.0$ に設定している（論文Section 3.3より）。

### アルゴリズム

DeepToolのプロセス監督型RL訓練の擬似コードを以下に示す。

```python
from dataclasses import dataclass
from typing import Sequence


@dataclass
class Step:
    """インターリーブ推論の1ステップを表す構造体"""
    think: str       # 思考テキスト
    action: str      # 生成されたコード
    observation: str  # 実行結果


def gestalt_similarity(a: str, a_ref: str) -> float:
    """Gestalt Pattern Matchingによる行動類似度を計算する

    Args:
        a: 生成された行動（コード文字列）
        a_ref: 参照軌跡の行動（コード文字列）

    Returns:
        0.0〜1.0の類似度スコア
    """
    import difflib
    matcher = difflib.SequenceMatcher(None, a, a_ref)
    matching_blocks = matcher.get_matching_blocks()
    total_match_len = sum(block.size for block in matching_blocks)
    return 2.0 * total_match_len / (len(a) + len(a_ref) + 1e-8)


def compute_process_reward(
    generated: Step,
    reference: Step,
    schema_valid: bool,
) -> float:
    """Action-Centric Process Rewardを計算する

    Args:
        generated: モデルが生成したステップ
        reference: 参照軌跡のステップ
        schema_valid: Schema 1/2のフォーマットに準拠しているか

    Returns:
        ステップレベルの報酬値
    """
    format_indicator = 1.0 if schema_valid else 0.0
    similarity = gestalt_similarity(generated.action, reference.action)
    return format_indicator * similarity


def decompose_trajectory(
    trajectory: Sequence[Step],
    reference: Sequence[Step],
) -> list[dict]:
    """単一軌跡をステップ単位の独立訓練インスタンスに分解する

    Args:
        trajectory: モデル生成の完全な軌跡
        reference: MOSAIC合成の参照軌跡

    Returns:
        各ステップの(prefix, step, reward)を持つ訓練インスタンスのリスト
    """
    instances = []
    n = min(len(trajectory), len(reference))
    for t in range(n):
        prefix = trajectory[:t]  # ステップtまでのコンテキスト
        step = trajectory[t]
        reward = compute_process_reward(
            generated=step,
            reference=reference[t],
            schema_valid=_validate_schema(step),
        )
        instances.append({
            "prefix": prefix,
            "step": step,
            "reward": reward,
        })
    return instances


def _validate_schema(step: Step) -> bool:
    """ステップがSchema 1またはSchema 2に準拠しているか検証する"""
    has_think = bool(step.think.strip())
    has_action = bool(step.action.strip())
    has_obs = bool(step.observation.strip())
    # Schema 1: think + code + interpreter
    # Schema 2: think + answer (observationなし)
    return has_think and (has_action or has_obs)
```

## 実装のポイント（Implementation）

著者らが報告している訓練設定の要点を以下に整理する。

**SFTフェーズ**: バッチサイズ64、学習率1e-5、5エポック、cosineスケジューラ、最大シーケンス長15,000トークン。OpenR1-Math-220kから厳選した8,000インスタンスを使用する。

**RLフェーズ**: GRPO最適化、バッチサイズ32、学習率1e-6、1,000ステップ、4生成（グループサイズ）、最大補完長6,000トークン。KL係数 $\beta = 0.0$ により、参照ポリシーからの制約を緩和している。

**ハードウェア**: 最大4台のNVIDIA A100（80GB）を使用。7Bモデルでの訓練であるため、比較的小規模なGPUクラスタで再現可能である。

**敵対的摂動の設計**: $\Phi_{\text{gen}}$ はコード内の変数名改変やインデント崩しといった内因性バグを注入し、$\Phi_{\text{env}}$ はタイムアウトやメモリ超過といった外部環境の障害をシミュレートする。SFTで $\rho = 0.1$、RLで $\rho = 0.2$ と段階的に摂動率を上げることで、モデルのロバスト性を漸進的に高めている。
