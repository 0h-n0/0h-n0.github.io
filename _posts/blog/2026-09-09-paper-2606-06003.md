本記事は [Beyond Vector Similarity: A Structural Analysis of Graph-Augmented Retrieval for Industrial Knowledge Graphs](https://arxiv.org/abs/2606.06003) の解説記事です。

## 論文概要（Abstract）

標準的なRAGは、相互接続されたエンティティに対する構造的推論を必要とするクエリで体系的に失敗する。著者は46ノードの航空宇宙サプライチェーンナレッジグラフ（64の型付きエッジ）を用いて、10の意図カテゴリにまたがる23クエリで8つの検索アーキテクチャを評価した。単一パスのベクトル検索では10カテゴリ中5カテゴリが「構造的に到達不可能」であることを示し、9つの型付きトラバーサルプリミティブを備えたLLM Query PlannerがF1=0.632を達成したと報告している。さらに6つのグラフ計算ツールを追加したAdaptive Graph Plannerにより、従来解決不可能だったクエリカテゴリへの対応を可能にした。

この記事は [Zenn記事: Neo4j×Graph-RAGで製造業の障害対応ナレッジ検索基盤を構築する](https://zenn.dev/0h_n0/articles/e5948129f3494d) の深掘りです。

## 背景と動機（Background & Motivation）

標準的なRAGパイプラインは、テキストチャンクをベクトル空間に埋め込み、コサイン類似度で検索する。この手法は自然言語の意味的マッチングには有効だが、産業用ナレッジグラフ（KG）に対しては根本的な限界がある。サプライチェーン、製造ライン、部品依存関係といったグラフ構造化データでは、エンティティ間の接続関係・経路・次数といった**構造的情報**がクエリ応答の鍵となる。

著者は、ベクトル検索がこうした構造的クエリで失敗する原因を「テキストチャンクにはグラフのトポロジ情報が存在しない」点に求めている。TF-IDFやDense Embeddingで取得したチャンクには、ノード間の接続関係やパス長、次数分布といった情報が含まれないため、LLMがどれほど高性能であっても正確な回答を生成できない。この問題は、モデルの知性の限界ではなく、**検索アーキテクチャの設計上の限界**であるという点が、本論文の中心的な主張である。

## 主要な貢献（Key Contributions）

- **構造的到達不可能性の定式化**: ベクトル検索では原理的に回答できない5カテゴリのクエリパターンを定義し、それぞれの失敗モードを分類した
- **オペレータ語彙テーゼの提唱**: 「LLMベースのグラフ推論における障壁はモデルの知性ではなく、ツールとして利用可能な計算オペレータである」という仮説を実験的に検証した
- **段階的アーキテクチャ評価**: Standard RAG（F1=0.349）からAdaptive Graph Planner（F1=0.636）まで、8段階のアーキテクチャを同一評価セットで比較し、各段階の寄与を定量化した

## 技術的詳細（Technical Details）

### ナレッジベース設計

著者が構築したナレッジグラフは航空宇宙サプライチェーンを模したもので、以下のスキーマを持つ。

| エンティティタイプ | ノード数 | 例 |
|---|---|---|
| Supplier | 9 | TechChip Inc, AeroMetal Corp |
| Component | 15 | Flight Control Unit, Landing Gear Assembly |
| Factory | 5 | Assembly Plant Alpha |
| Product | 6 | WideBird-X50, RegionalJet-150 |
| Customer | 4 | AirGlobal Airlines, DefenseTech Corp |
| Risk Event | 8 | Thailand flood (EVT-001) |

エッジは5つのリレーションシップタイプ（SUPPLIES: 15+2期限切れ、USES: 20、PRODUCES: 13、DELIVERS_TO: 8、AFFECTS: 自動生成）で構成され、各エッジにはeffective_dateとオプションのexpired_dateが付与される。この時間メタデータにより、有効な関係と期限切れの関係を区別できる。

### 5つの構造的に到達不可能なクエリカテゴリ

著者は、ベクトル検索では原理的に解決できないクエリを5カテゴリに分類している。

**1. What-If / 反事実分析**

「Flight Control Unitをデュアルソーシングする場合、代替サプライヤーはどこか」のようなクエリ。コンポーネントの種別を特定し、同種の部品を供給する全サプライヤーを列挙したうえで、既に接続済みのサプライヤーを除外する必要がある。ベクトル検索は「存在しないエッジ」を表現できないため、構造的不在に対して盲目である。

**2. 単一障害点（SPOF）検出**

「サプライヤーが1社しかないコンポーネントはどれか」。全コンポーネントノードのSUPPLIESエッジの入次数を計算し、次数1のものをフィルタリングする必要がある。自然な分解点がなく、グローバルな集約演算が必要なため、Agentic RAGでも解決困難と著者は報告している。

**3. 逆/否定クエリ**

「タイ洪水の影響を受けないカスタマーは？」。AFFECTS→SUPPLIES→USES→PRODUCES→DELIVERS_TOの4ホップで爆発半径（blast radius）を計算し、その補集合を返す必要がある。

**4. 比較サブグラフ分析**

「WideBird-X50とRegionalJet-150のサプライチェーンの深さを比較せよ」。2つの製品それぞれの上流サブグラフを走査し、ホップ深度、サプライヤー数、コンポーネント数、工場数、地理的集中度、共有インフラを並列に比較する。

**5. リスク伝播スコアリング**

「全製品のリスク伝播スコアを表示せよ」。各製品の上流サブグラフ全体にわたる重み付きマルチホップスコアを計算する必要がある。

### 失敗モード分類

著者は上記5カテゴリに対応する6つの失敗モードを定義している。

| 失敗モード | 根本原因 | 対応するクエリカテゴリ |
|---|---|---|
| 不在盲目 (Absence blindness) | 欠損エッジを表現できない | What-If分析 |
| 次数盲目 (Degree blindness) | 入次数/出次数を計数できない | SPOF検出 |
| 補集合盲目 (Complement blindness) | 「X以外の全て」を計算できない | 逆/否定クエリ |
| トポロジー盲目 (Topology blindness) | サブグラフの構造的性質を比較できない | 比較分析 |
| 伝播盲目 (Propagation blindness) | 重み付きスコアを計算できない | リスク伝播 |
| 時間盲目 (Temporal blindness) | テキストチャンクに有効期間がない | 時間的クエリ |

### リスク伝播方程式

リスク伝播スコアリング（カテゴリ5）は以下の数式で定義される（論文Equation 1）。

$$
R(p) = \sum_{(c,s) \in \text{paths}(p)} \sum_{e \in \text{events}(s)} w_{\text{sev}}(e) \cdot \delta_{\text{hop}}(c, p)
$$

ここで、
- $R(p)$: 製品 $p$ のリスク伝播スコア
- $\text{paths}(p)$: 製品 $p$ から逆方向トラバーサルで到達可能な（コンポーネント, サプライヤー）ペアの集合
- $\text{events}(s)$: サプライヤー $s$ に影響するリスクイベントの集合
- $w_{\text{sev}}(e)$: イベント $e$ の重大度重み
- $\delta_{\text{hop}}(c, p)$: コンポーネント $c$ から製品 $p$ までのホップ距離に基づく減衰係数

重大度重みと減衰係数は以下の値が用いられている。

| 重大度 | $w_{\text{sev}}$ | ホップ距離 | $\delta_{\text{hop}}$ |
|---|---|---|---|
| Critical | 1.0 | 1-hop | 1.0 |
| High | 0.7 | 2-hop | 0.6 |
| Medium | 0.4 | 3-hop | 0.35 |
| Low | 0.1 | 4-hop | 0.2 |

この方程式はテキストチャンク内に計算結果として存在しないため、TF-IDF検索ではゼロマッチとなり、ベクトル検索でも回答を生成できない。グラフトラバーサルと数値計算の両方が必要な典型的な構造的クエリである。

### 6つの計算ツール（Architecture 8）

Architecture 8（Adaptive Graph Planner）では、上記9プリミティブに加えて以下の6つの計算ツールが追加される。

| ツール | 機能 | 対象クエリカテゴリ |
|---|---|---|
| simulate_removal | ノード削除時のカスケード影響を報告 | What-If分析 |
| subgraph_diff | 2つのルートからBFS、構造的差分を出力 | 比較分析 |
| aggregate_over_type | タイプ別の到達可能ターゲットを集計 | 集約クエリ |

著者は、LLMがこれらの計算ツールを「選択的に採用」する点を強調している。Architecture 8のF1スコア向上は+0.001（0.635→0.636）とわずかだが、従来のプリミティブでは解決不可能だったクエリカテゴリに対して質的なブレークスルーが得られたと報告している。

### NetworkXベースの実装

著者の実装はNetworkX有向マルチグラフを基盤としている。8,154行、17ソースファイルで構成され、コアエンジン（data.py: 524行、graphrag_engine.py: 1,709行）はAPIキー不要で動作する。TF-IDFインデックスにはscikit-learnを使用し、WebフロントエンドはFlask + vis.jsで構築されている。

LLMベンチマーク（Architecture 3以降）にはClaude Haiku 4.5が使用されている。著者はハンドラのエンジニアリングコストとして「各ハンドラは50-200行のPython（中央値120行）、6つのインテント分類訓練フレーズ、グラウンドトゥルース構築を必要とし、ハンドラあたり約2-8時間を要した」と報告している。

### 実装上の注意点

Architecture 7（LLM Query Planner）の利点は、個別ハンドラの手動実装を不要にする点にある。9つのプリミティブを定義するだけで、LLMが自然言語クエリを適切なプリミティブの呼び出しシーケンスに分解する。ただし、プリミティブの設計自体にドメイン知識が必要であり、「どの粒度でプリミティブを切るか」が性能を左右する。

```python
# graph_query_planner.py の概念的な構造
import networkx as nx
from typing import Any

class GraphQueryPlanner:
    """LLMがプリミティブを選択・組み合わせてクエリに回答する

    Args:
        graph: NetworkX有向マルチグラフ
        primitives: 利用可能なプリミティブのレジストリ
    """

    def __init__(
        self, graph: nx.MultiDiGraph, primitives: dict[str, callable]
    ) -> None:
        self.graph = graph
        self.primitives = primitives

    def plan_and_execute(self, query: str) -> dict[str, Any]:
        """自然言語クエリをプリミティブ呼び出しに分解して実行

        Args:
            query: ユーザーの自然言語クエリ

        Returns:
            プリミティブの実行結果を集約した回答
        """
        # 1. LLMがクエリを解析し、必要なプリミティブを特定
        plan = self._generate_plan(query)

        # 2. プリミティブを順次実行
        results = []
        for step in plan:
            primitive_fn = self.primitives[step["primitive"]]
            result = primitive_fn(**step["args"])
            results.append(result)

        # 3. 結果を自然言語に変換
        return self._synthesize_answer(query, results)
```

import boto3
from datetime import date, timedelta

ce = boto3.client("ce", region_name="ap-northeast-1")
sns = boto3.client("sns", region_name="ap-northeast-1")

def daily_cost_report() -> None:
    """日次コストレポート取得、$100/日超過でSNS通知"""
    today = date.today()
    yesterday = today - timedelta(days=1)

    resp = ce.get_cost_and_usage(
        TimePeriod={"Start": str(yesterday), "End": str(today)},
        Granularity="DAILY",
        Metrics=["UnblendedCost"],
        Filter={
            "Tags": {
                "Key": "Project",
                "Values": ["graphrag"],
            }
        },
        GroupBy=[{"Type": "DIMENSION", "Key": "SERVICE"}],
    )

    total = sum(
        float(g["Metrics"]["UnblendedCost"]["Amount"])
        for g in resp["ResultsByTime"][0]["Groups"]
    )

    if total > 100.0:
        sns.publish(
            TopicArn="arn:aws:sns:ap-northeast-1:ACCOUNT:graphrag-alerts",
            Subject=f"GraphRAG Cost Alert: ${total:.2f}/day",
            Message=f"Daily cost exceeded $100: ${total:.2f}",

### コスト最適化チェックリスト

**アーキテクチャ選択**:
- [ ] ~100 req/日 → Serverless（Lambda + Neptune Serverless）
- [ ] ~1,000 req/日 → Hybrid（ECS Fargate + Neptune Serverless）
- [ ] 10,000+ req/日 → Container（EKS + Neptune Provisioned）

**リソース最適化**:
- [ ] EC2/EKS: Spot Instances優先（m5.xlarge Spot: ~$0.04/h、オンデマンド比最大90%削減）
- [ ] Reserved Instances: 1年コミットで最大72%削減

- [ ] Lambda: メモリサイズ512MBが最適（CPU性能とコストのバランス）

## 実験結果（Results）

### スケーラビリティ分析

著者は46ノード/58エッジのベースラインから1,100ノード/1,850エッジ（24倍/32倍）にスケールしたテストを実施している（論文Table VIII）。

| クエリタイプ | 46ノード | 1,100ノード | レイテンシ増加率 |
|---|---|---|---|
| 単純ルックアップ | ベースライン | - | 1.2-2.1x |
| マルチホップ | ベースライン | - | 1.8x |
| パスファインディング | ベースライン | - | 10.2x |
| 集約クエリ | ベースライン | P95: 11.01ms | **16.4x** |
| リスク伝播 | ベースライン | - | **33.7x** |

著者は、リスク伝播の33.7倍のレイテンシ増加は「全製品の上流サブグラフ全体を走査する計算量に起因する」と分析している。ただし、1,100ノード規模でもP95が11.01msであり、インタラクティブなユースケースでは許容範囲内であると著者は報告している。

### 評価メトリクスの限界

著者はエンティティレベルF1スコアの限界も指摘している。構造的クエリでは、包括的かつ正確な回答ほどF1が低く評価される「測定ギャップ」が存在する。例えば、補集合クエリ（「影響を受けない顧客」）では、正解が4顧客中3顧客の場合、1顧客の欠落でF1が大きく低下する。著者は、構造的クエリに適した評価メトリクスの開発を今後の課題としている。

## 実運用への応用（Practical Applications）

### 製造業の障害対応への応用

Zenn記事で紹介したNeo4j×Graph-RAGの障害対応ナレッジ検索基盤と本論文の知見を組み合わせると、以下の応用が考えられる。

**サプライチェーンリスク管理**: リスク伝播方程式を製造業の実データに適用し、部品調達リスクを定量化できる。特にSPOF検出（単一障害点の特定）は、調達先の冗長化判断に直接活用できる。

**障害影響分析の自動化**: What-If分析プリミティブにより、「この部品が供給停止になったら、どの製品ラインが影響を受けるか」を即座にシミュレーションできる。従来は手作業で依存関係を追跡していた工程が、グラフトラバーサルで自動化される。

**課題と制約**: 著者の実装は46ノードの小規模KGに対するものであり、実際の製造業のサプライチェーンは数万ノード規模になる。1,100ノードでのスケーラビリティテストでは、リスク伝播のレイテンシが33.7倍に増加しており、大規模グラフでのパフォーマンス最適化（インデックス設計、サブグラフの事前計算、結果キャッシュ等）が必要となる。

## 関連研究（Related Work）

- **Microsoft GraphRAG**: LLMで抽出したエンティティをコミュニティクラスタに組織化し、要約ベースの検索を行う手法。本論文のアプローチとは異なり、テキストからの自動グラフ構築に焦点を当てている。本論文のように事前定義されたスキーマを持つ産業KGではなく、非構造化テキストからのKG構築を対象とする
- **Graph Retrieval-Augmented Generation Survey (arXiv:2408.08921)**: GraphRAGのワークフロー（Graph-Based Indexing、Graph-Guided Retrieval、Graph-Enhanced Generation）を体系的に整理したサーベイ。本論文は、このサーベイで扱われていない「構造的到達不可能性」の問題に焦点を当てている
- **LightRAG (Guo et al.)**: グラフベースのテキストインデキシングとデュアルレベル検索を行う手法。本論文の競合ベンチマーク（Table IX）ではLightRAGが11クエリ中3正解に留まり、構造的クエリへの対応は限定的であると著者は報告している
- **Temporal GraphRAG (Han et al., 2025)**: 二層時間グラフモデリングにより、時間依存クエリに対応する手法。本論文のfilter_edges_by_dateプリミティブは、TG-RAGの時間フィルタリングに類似した機能を提供している

## まとめと今後の展望

本論文の核心的な知見は、**オペレータ語彙テーゼ**である。LLMの推論能力自体は十分であり、構造的クエリの失敗原因はモデルではなくツール（計算オペレータ）の不足にある。9つのトラバーサルプリミティブの提供だけでF1が0.349から0.632に向上した事実は、この仮説を裏付けている。

産業用ナレッジグラフに対するRAGを設計する際は、(1)ベクトル検索で到達不可能なクエリカテゴリを事前に特定し、(2)それぞれに対応する型付きプリミティブを設計し、(3)LLMにプリミティブ選択を委ねる、というアプローチが有効であることを著者は示している。

今後の課題として、著者は大規模グラフ（数万ノード以上）でのスケーラビリティ検証、構造的クエリに適した評価メトリクスの開発、および動的に変化するKG（リアルタイムのイベント追加）への対応を挙げている。
