## 論文概要

本記事は [JSONSchemaBench: A Rigorous Benchmark of Structured Outputs for Language Models](https://arxiv.org/abs/2501.10868) の解説記事です。

著者ら（Geng, Cooper, Moskal et al.; Microsoft Research, EPFL）は、LLMの構造化出力生成を体系的に評価するベンチマーク「JSONSchemaBench」を提案している。10,000の実世界JSONスキーマで6つの主要フレームワークを効率性・制約カバレッジ・出力品質の3次元で評価し、制約デコーディングが最大50%の高速化と最大4%の精度向上を達成しうる一方、フレームワーク間でJSON Schema機能のサポートに大きなばらつきがあることを報告している。

## 背景と動機

LLMの出力を構造化フォーマット（JSON等）に制約する「制約デコーディング（Constrained Decoding）」は、APIレスポンス生成やツール呼び出し、データ抽出で広く必要とされている。OpenAIの「Structured Outputs」やGeminiの「Controlled Generation」として商用APIにも採用されている。

しかし著者らは、この技術の体系的評価が不足していたと指摘している（論文Section 1）。(1) 制約デコーディングが生成速度にどう影響するか、(2) 各フレームワークがJSON Schemaの機能セットをどこまでサポートしているか、(3) 構造的制約が出力の意味的品質を損なわないか、という3つの問いに統一的な回答が存在しなかった。従来のベンチマークはタスク固有の狭い評価か、実世界との関連が不明確な形式文法を用いたものに限られていた。

## 主要な貢献

著者らは以下の3つの貢献を報告している（論文Section 1）。

- **ベンチマーク構築**: 7つのソースから10,000の実世界JSONスキーマを収集し複雑度別に分類したJSONSchemaBenchの構築
- **評価フレームワーク**: 宣言カバレッジ・経験的カバレッジ・準拠率の3段階カバレッジ指標と、効率性・品質を含む多次元評価体系の提案
- **包括的比較**: 6つの主要フレームワークを効率性・カバレッジ・品質の3次元で初めて統一的に評価

## 技術的詳細

### 制約デコーディングの仕組み

制約デコーディングは、LLMのトークン生成プロセスに介入し、各ステップで有効なトークンのみを選択可能にする手法である（論文Algorithm 1）。LLMが語彙$\mathcal{V}$上の確率分布$p_\theta(v_t \mid v_{<t})$を出力するとき、マスク関数$M$が制約$\mathcal{S}$に基づく有効トークン集合$M(v_{<t}, \mathcal{S}) \subseteq \mathcal{V}$を定義する。ここで$v_t$は時刻$t$のトークン、$v_{<t}$は生成済みトークン列、$\theta$はモデルパラメータである。

マスクされた分布からのサンプリングは以下で表される：

$$
v_t \sim \frac{p_\theta(v_t \mid v_{<t}) \cdot \mathbf{1}[v_t \in M(v_{<t}, \mathcal{S})]}{\sum_{v \in M(v_{<t}, \mathcal{S})} p_\theta(v \mid v_{<t})}
$$

$\mathbf{1}[\cdot]$は指示関数で、有効トークンにのみ確率質量を割り当てる。内部実装では、多くのフレームワークがJSON SchemaをCFGや正規表現に変換（Grammar Compilation）し、プッシュダウンオートマトンで有効トークン集合を追跡している。

### JSONSchemaBenchのデータセット構成

著者らは7つのソースから合計9,558のスキーマを収集し、複雑度別に分類している（論文Section 3）。主要ソースは、GitHubリポジトリ（Baazizi et al. 2021由来、フィールド数でTrivial/Easy/Medium/Hard/Ultraに分類、計5,767件）、GlaiveAI関数呼び出しスキーマ（2,000件）、Kubernetes構成スキーマ（1,064件）、Snowplow（403件）、Washington Post ANS（125件）、JSON Schema Store（199件）、JSON Schema Test Suite（164件）である。

前処理として重複除去、空スキーマ除去、未解決`$ref`処理、ドラフトバージョン不整合修正が実施されている。

### 3次元評価指標

著者らは以下の3次元で評価を行っている（論文Section 4）。

**効率性（Efficiency）**: GCT（Grammar Compilation Time）、TTFT、TPOT（Time Per Output Token）の3指標を、全エンジン共通のスキーマ集合で測定。

**カバレッジ（Coverage）**: 3段階の指標を定義。$\mathfrak{C}_{\text{Declared}}$（エラーなく処理された割合）、$\mathfrak{C}_{\text{Empirical}}$（実際にスキーマ準拠の出力を生成した割合）、Compliance Rate = $\mathfrak{C}_{\text{Empirical}} / \mathfrak{C}_{\text{Declared}}$（受け入れたスキーマのうち正しく生成できた割合）。

**品質（Quality）**: Last Letter、Shuffle Objects、GSM8Kの3タスクで意味的品質への影響を測定。

## 実装のポイント

構造化出力をプロダクションで活用する際の注意点を論文の知見に基づき整理する。

```python
def validate_schema_coverage(
    schema: dict,
    high_risk_keywords: list[str] | None = None,
) -> dict[str, bool]:
    """JSON Schemaのフレームワーク互換性を事前チェック

    JSONSchemaBenchの結果に基づき、各フレームワークで
    サポートが不安定な機能を検出する。

    Args:
        schema: 検証対象のJSON Schema（dict形式）
        high_risk_keywords: カバレッジが低い機能キーワード一覧

    Returns:
        各機能の検出結果（True=使用している）
    """
    if high_risk_keywords is None:
        high_risk_keywords = [
            "patternProperties", "additionalProperties", "oneOf",
            "not", "if", "then", "else", "$dynamicRef",
        ]
    schema_str = str(schema)
    return {kw: kw in schema_str for kw in high_risk_keywords}
```

論文の知見から導かれる実装上の重要ポイントは以下の通りである。

- **スキーマ設計の簡素化**: `patternProperties`, `oneOf`, `not`等の高度な機能はフレームワーク間でサポートが不安定なため、`properties`と`required`の基本機能で代替する
- **フレームワーク選択**: Guidanceが最高のカバレッジと効率性を示すが、OpenAI/GeminiのAPI組み込みは運用負荷の面で有利。ただしカバレッジは低い
- **フォールバック設計**: 制約デコーディング失敗に備え、無制約生成+事後バリデーションのフォールバックパスを実装する
- **Grammar Compilation Time**: Outlinesは3-8秒のコンパイル時間が発生するため、リアルタイム応答ではスキーマのプリコンパイルまたはキャッシュが必要

| 構成 | トラフィック | アーキテクチャ | 月額概算 |
|------|------------|--------------|---------|

| Medium | ~1,000 req/日 | ECS Fargate + Bedrock | $300-800 |
| Large | 10,000+ req/日 | EKS + Spot + vLLM/Guidance | $2,000-5,000 |

**コスト削減テクニック**: Spot Instances GPU（最大70-90%削減）、Bedrock Batch API（50%削減）、Prompt Caching（30-90%削減）、Grammar CompilationキャッシュをDynamoDBに保存しコンパイル時間を排除。

```python
import boto3
from aws_xray_sdk.core import patch_all
from datetime import date, timedelta

patch_all()  # boto3含む全ライブラリをX-Ray自動計装


def get_daily_cost_report(alert_threshold: float = 100.0) -> dict[str, float]:
    """日次コストレポートを取得しBedrock/Lambda/EKSコストを抽出

    Args:
        alert_threshold: SNS通知を発火する日次コスト閾値（USD）

    Returns:
        サービス別の日次コスト（USD）
    """
    ce = boto3.client("ce")
    today = date.today()
    resp = ce.get_cost_and_usage(
        TimePeriod={"Start": (today - timedelta(days=1)).isoformat(), "End": today.isoformat()},
        Granularity="DAILY", Metrics=["UnblendedCost"],
        GroupBy=[{"Type": "DIMENSION", "Key": "SERVICE"}],
    )
    costs = {g["Keys"][0]: float(g["Metrics"]["UnblendedCost"]["Amount"])
             for g in resp["ResultsByTime"][0]["Groups"]
             if float(g["Metrics"]["UnblendedCost"]["Amount"]) > 0}
    if sum(costs.values()) > alert_threshold:
        boto3.client("sns").publish(
            TopicArn="arn:aws:sns:ap-northeast-1:ACCOUNT:cost-alert",
            Subject=f"Daily cost: ${sum(costs.values()):.2f}",
            Message=str(costs))
    return costs
```

### コスト最適化チェックリスト

**アーキテクチャ選択**: トラフィック量で判断（~100: Serverless / ~1,000: Hybrid / 10,000+: Container）。Grammar Compilation頻度に応じてキャッシュ戦略を決定。

**リソース最適化**: GPU推論はSpot Instances優先（g5/g6系、最大70-90%削減）。安定ワークロードにはReserved Instances 1年コミット（最大72%削減）。LambdaはJSON Schemaバリデーション用途なら512MB-1024MBで十分。EKSはKarpenterでアイドルノードを60秒後に自動削除。

**LLMコスト削減**: Bedrock Batch APIで非同期処理時50%削減。Prompt Cachingで同一スキーマの繰り返しリクエストを最適化。単純スキーマはHaiku、複雑スキーマはSonnetとモデルを使い分け。max_tokensをスキーマ複雑度に応じて動的設定。JSONSchemaBenchの結果に基づき高カバレッジ機能のみ使用してスキーマを簡素化。

**監視・アラート**: AWS Budgets月額$5,000アラート。CloudWatch Lambda実行時間P95 > 90秒アラーム。Cost Anomaly DetectionでBedrock使用量の異常検知。Cost Explorer API + SNSで日次コストレポート。

**リソース管理**: 30日未使用リソースの自動削除。`project:structured-output`, `env:prod/dev`タグを全リソースに付与。ECRイメージ30世代保持、S3ログ90日後Glacier移行。開発環境のGPUノードを夜間・週末自動停止。Grammar CompilationキャッシュはDynamoDB TTL 7日で自動パージ。

## 実験結果

### 効率性評価

著者らはA100 GPU上でLlama-3.1-8B-Instructを用いて測定している（論文Section 5.1）。TPOT中央値（GlaiveAI）はLM-only 15.40ms、Guidance 6.37ms、Llamacpp 29.98ms、Outlines 30.33ms。Guidanceは無制約LMより高速であり、これは「fast-forwarding」（JSON構文要素のLM推論スキップ）による約50%の高速化と報告されている。Grammar Compilation Timeは、Guidance/Llamacppが0.00-0.06秒に対し、Outlinesは3.48-8.05秒（正規表現変換に起因）。

### カバレッジ評価

Llama-3.2-1B-Instructによる経験的カバレッジ（論文Section 5.2）では、GlaiveAI（単純スキーマ）でGuidance 96%、Llamacpp 95%、OpenAI 89%、Gemini 86%と全体的に高いが、GitHub Medium（30-100フィールド）ではGuidance 69%、Llamacpp 57%、OpenAI 12%、Gemini <1%と差が顕著になる。著者らは商用APIが「保守的な戦略」で確実にサポートできる機能のみを実装していると分析している。JSON Schema Test Suite（43カテゴリ）では、Guidanceが13カテゴリで100%カバレッジを達成しunder-constrainedエラーを1件に抑制、一方XGrammarは38件のunder-constrainedエラーを記録している。

### 出力品質評価

Llama-3.1-8B-Instructモデルを用いた3タスクでの正答率は以下の通りである（論文Section 5.3）。

| タスク | LM-only | XGrammar | Llamacpp | Outlines | Guidance |
|-------|---------|----------|----------|----------|----------|
| Last Letter | 50.7% | 51.2% | 52.0% | 53.3% | 54.0% |
| Shuffle Objects | 52.6% | 52.7% | 52.6% | 53.0% | 55.9% |
| GSM8K | 80.1% | 83.7% | 82.4% | 81.6% | 83.8% |

全フレームワークで制約デコーディングが無制約生成と同等以上の品質を達成しており、構造的制約が意味的品質を損なわないことが確認されている。GuidanceのGSM8K 83.8%はLM-only比で3.7ポイント改善であり、著者らは「token-healing」実装をその一因として挙げている。

## 実運用への応用

JSONSchemaBenchの知見はGemini+Pydanticによる構造化データ抽出に直接的な示唆を与える。Pydanticモデル設計時は`patternProperties`や`oneOf`等を避け`properties`, `required`, `enum`を中心に構成すべきである。Gemini APIは単純スキーマで86%のカバレッジだが複雑スキーマでは1%未満に低下するため、必要に応じてGuidanceセルフホストかスキーマ分割が有効である。Compliance Rateが100%でないケースがあるため生成後バリデーション+リトライは必須。レイテンシ面では頻用スキーマの事前コンパイル+キャッシュが重要である。

## まとめと今後の展望

JSONSchemaBenchは、LLM構造化出力生成の初の包括的評価基盤である。10,000スキーマによる評価で、制約デコーディングの最大50%高速化・最大4%精度向上、フレームワーク間のカバレッジばらつき、品質非劣化が定量的に示された。

今後の方向として、GitHub-Ultra（500フィールド超）への対応、トークナイザ固有の分布シフト問題の解決、複数モデル・ドラフトバージョンへの評価拡張が挙げられている。Pydanticを介した実務利用では、スキーマ複雑度を意識した設計とフレームワーク選択の判断基準としてJSONSchemaBenchの結果を参照することが推奨される。
