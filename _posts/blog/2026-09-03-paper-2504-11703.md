## 論文概要（Abstract）

本記事は [Progent: Securing AI Agents with Privilege Control](https://arxiv.org/abs/2504.11703)（arXiv: 2504.11703、2025年4月公開、v3: 2026年5月更新）の解説記事です。

本論文は、AIエージェントのツール呼び出しに対して最小権限の原則（PoLP）を適用するセキュリティフレームワーク「Progent」を提案している。LLMがタスクに基づいて初期ポリシーを生成し、Z3 SMTソルバーがポリシー更新を「縮小（narrowing）」と「拡大（expansion）」に分類することで、権限の静かな昇格を防止する「単調縮小保証（Monotonic Confinement）」を実現する。AgentDojoベンチマークで攻撃成功率を39.9%から1.0%に低減したと著者らは報告している。

この記事は [Zenn記事: Bedrock AgentCore Runtime×Gatewayで顧客サポートエージェントを構築しツール認証を設計する](https://zenn.dev/0h_n0/articles/391fc1f0476f7a) の深掘りです。

## 背景と動機（Background & Motivation）

AIエージェントが外部ツール（API、データベース、ファイルシステム等）にアクセスする際、プロンプトインジェクション攻撃によって意図しないツール呼び出しが実行されるリスクがある。Zenn記事のAgentCore Gatewayでは、Cedarポリシーによる静的なアクセス制御が採用されているが、Progentはこれをさらに動的に拡張し、タスクの進行に伴ってポリシーを自動更新する仕組みを提案している。

従来のアプローチには以下の課題がある。

- **ガードレールモデル**: LLMベースの攻撃検知は非決定的であり、巧妙な攻撃を見逃す可能性がある
- **アーキテクチャ侵入型防御**（CaMeL、FIDES等）: エージェント内部の大幅な改修が必要で、既存フレームワークとの互換性が低い
- **静的ポリシー**: タスクの進行に伴って必要な権限が変化する状況に対応できない

## 主要な貢献（Key Contributions）

- **貢献1**: ツール呼び出しレベルのシンボリックルールによる権限制御。ツール名と引数条件を記号的に記述し、決定論的に評価
- **貢献2**: LLM生成ポリシー + Z3 SMTソルバーによる動的ポリシー管理。ポリシー更新を数学的に「縮小」「拡大」に分類し、単調縮小保証を実現
- **貢献3**: AgentDojo（ASR 39.9%→1.0%）、ASB（ASR 70.3%→3.9%）の2つのベンチマークで有効性を実証

## 技術的詳細（Technical Details）

### アーキテクチャ概要

```mermaid
flowchart LR
    User[ユーザー] -->|タスク| LLM_Gen[LLM<br/>ポリシー生成]
    LLM_Gen -->|P₁| Agent[エージェント]
    Agent -->|ツール呼び出しc_i| Gate[Policy Gate<br/>P(c_i)]
    Gate -->|許可| Tool[ツール実行]
    Gate -->|拒否| Fallback[フォールバック]
    Tool -->|結果o_i| LLM_Upd[LLM<br/>ポリシー更新]
    LLM_Upd -->|P'| SMT[Z3 SMT Solver<br/>縮小/拡大判定]
    SMT -->|縮小| Auto[自動適用]
    SMT -->|拡大| Approve[承認要求]
```

### シンボリックルールの構造

ポリシーは各ツールに対するルールのリストで構成される。各ルールは「effect」（allow/forbid）と引数条件の組み合わせである。

```json
{
  "tool": "create_ticket",
  "rules": [
    {
      "effect": "allow",
      "conditions": {
        "priority": {"type": "enum", "values": ["low", "medium"]},
        "subject": {"type": "string", "pattern": "^support-.*"}
      }
    },
    {
      "effect": "forbid",
      "conditions": {
        "priority": {"type": "enum", "values": ["urgent"]}
      }
    }
  ],
  "default": "deny"
}
```

ルール評価は決定論的な手順（Algorithm 2）に従い、`forbid`ルールを`allow`ルールより先に評価する保守的戦略をとる。これはCedarの「Forbid Wins」原則と同様の設計である。

### 動的ポリシー管理

ポリシーはタスクの各ステップ$i$で$P_i$として管理される。

**初期ポリシー$P_1$の生成**: LLMがユーザーのタスク記述と利用可能なツール一覧から、タスク固有のベースライン権限を生成する。

**ポリシー更新の2段階プロセス**:
1. **Stage 1**: ツール実行結果（潜在的に悪意のある内容を含む可能性）への曝露なしに、更新の必要性を判断
2. **Stage 2**: ツール実行結果を含む完全なコンテキストから候補ポリシー$P'$を生成

### SMTによる縮小/拡大判定

Z3 SMTソルバーを用いて、ポリシー$P$と$P'$の許可範囲を比較する。各ツール$t$について、許可されるツール呼び出しの集合を$A_t(P)$とすると、以下の判定を行う。

**縮小（Narrowing）**: $A(P') \subseteq A(P)$、すなわち新ポリシーが旧ポリシーの許可範囲の部分集合である場合。自動適用される。

**拡大（Expansion）**: $A(P) \not\supseteq A(P')$、すなわち新ポリシーが旧ポリシーで禁止されていた操作を許可する場合。明示的な承認が必要。

SMTソルバーによる判定は以下の全称量化式の充足可能性に帰着する。

$$
\forall \bar{v}_i. \, \Phi_{P'_t}(\bar{v}_i) \Rightarrow \Phi_{P_t}(\bar{v}_i)
$$

ここで、$\bar{v}_i$はツール$t$の引数ベクトル、$\Phi_{P_t}(\bar{v}_i)$はポリシー$P$のもとでツール呼び出し$(t, \bar{v}_i)$が許可されるかを表すSMT論理式である。

### 単調縮小保証（Monotonic Confinement）

上記のSMT判定により、承認なしのポリシー変更は常に縮小方向に制約される。

$$
A(P^{(0)}) \supseteq A(P^{(1)}) \supseteq A(P^{(2)}) \supseteq \cdots
$$

この性質は、LLMが生成するポリシーが敵対的入力の影響を受けた場合でも、権限が静かに昇格することを数学的に防止する。これはProgentの最も重要な安全性保証である。

## アルゴリズム

### ポリシーゲートの評価（Algorithm 2相当）

```python
from typing import Any
from z3 import Solver, And, Or, Not, BoolRef

def evaluate_policy_gate(
    tool_call: dict[str, Any],
    policy: list[dict],
    default_action: str = "deny",
) -> str:
    """ツール呼び出しに対するポリシー評価（論文Algorithm 2の擬似実装）"""
    tool_name = tool_call["name"]
    args = tool_call["arguments"]

    relevant_rules = [r for r in policy if r["tool"] == tool_name]
    forbid_rules = [r for r in relevant_rules if r["effect"] == "forbid"]
    allow_rules = [r for r in relevant_rules if r["effect"] == "allow"]

    for rule in forbid_rules:
        if matches_conditions(args, rule["conditions"]):
            return "DENY"

    for rule in allow_rules:
        if matches_conditions(args, rule["conditions"]):
            return "ALLOW"

    return default_action.upper()


def check_narrowing(old_policy: list[dict], new_policy: list[dict]) -> bool:
    """SMTソルバーによる縮小判定（論文の手法の擬似実装）"""
    solver = Solver()
    # new_policyで許可 かつ old_policyで拒否 となる入力が存在するか？
    # 存在すれば拡大、存在しなければ縮小
    expansion_formula = And(
        encode_policy_allows(new_policy),
        Not(encode_policy_allows(old_policy)),
    )
    solver.add(expansion_formula)
    return solver.check().r == -1  # UNSAT → 縮小
```

## 実装のポイント（Implementation）

### 2つの統合モード

**ライブラリモード**: 開発者がProgentをエージェントコードに直接組み込む。LangChainではミドルウェアコンポーネントとして、OpenAI Agents SDKではAgentクラスのラッパーとして実装される。

**プロキシモード**: エンドユーザーがLLMおよびMCPサーバーのエンドポイントをProgentのプロキシにリダイレクトすることで、コード変更なしに保護を有効化する。

### AgentCore Gatewayとの比較

| 観点 | Progent | AgentCore Gateway + Cedar |
|---|---|---|
| ポリシー生成 | LLMが動的生成 | 人間が手動定義 |
| ポリシー検証 | Z3 SMTソルバー | Cedar Analysis（自動推論） |
| 適用タイミング | ツール呼び出し時（動的） | ツール呼び出し時（静的） |
| 権限変更 | 単調縮小（自動）+ 拡大（承認） | 手動変更のみ |
| 形式保証 | 単調縮小保証 | デフォルト拒否 + 禁止優先 |

Zenn記事のCedarポリシーは「静的に定義されたルール」をGatewayが評価する設計であるのに対し、Progentは「タスクの進行に伴ってポリシーが動的に変化する」設計である。両者は補完的であり、Cedarで大枠のアクセス制御を定義し、Progentでタスク固有の細かい制約を動的に適用する組み合わせが考えられる。

## 関連研究（Related Work）

- **CaMeL** (Debenedetti et al., 2025): データフロー追跡によるエージェントセキュリティ。信頼度ラベルを用いてデータの汚染を追跡するアーキテクチャ侵入型の防御。テキスト出力攻撃にも対応可能だが、エージェント内部の大幅な改修が必要。Progentは外部ラッパーとして機能するため、既存フレームワークへの統合が容易
- **Cedar** (Cutler et al., 2024, arXiv: 2403.04651): 形式検証可能な認可言語。Progentのポリシー記述をCedar形式に変換し、Cedar Analysisで検証する統合が考えられる
- **ETDI** (2025): MCP向けOAuth強化ツール定義。Progentのプロキシモードと組み合わせることで、MCP通信のセキュリティを多層化できる

## まとめと今後の展望

Progentは、LLMのポリシー生成能力とZ3 SMTソルバーの数学的検証を組み合わせることで、エージェントのツール呼び出し権限を「単調縮小的に」制御する新しいアプローチを提示している。ポリシー更新の94%が自動処理される点は、運用負荷の観点からも実用性が高い。AgentDojoでのASR 1.0%という結果は、既存のガードレール型防御を大幅に上回る性能を示している。制約として、著者らはテキスト出力のみの攻撃（ツール呼び出しを伴わない攻撃）には対応できないこと、マルチモーダルエージェントへの拡張が今後の課題であることを認めている。AgentCore GatewayのCedarポリシーとProgentの動的ポリシーを組み合わせた多層防御は、実運用における有望なアプローチとして検討に値する。
