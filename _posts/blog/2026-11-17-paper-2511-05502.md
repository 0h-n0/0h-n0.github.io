## 論文概要（Abstract）

Rajeshら（Persistent System所属、8名）は、Apple Silicon上で動作する5つのローカルLLM推論フレームワーク — MLX、MLC-LLM、Ollama、llama.cpp、PyTorch MPS — を体系的に比較評価した論文を2025年10月に公開した。Mac Studio（M2 Ultra、192GBユニファイドメモリ）上でQwen-2.5ファミリのモデルを用い、数百トークンから10万トークンまでのプロンプトに対してTTFT（Time-to-First-Token）、定常スループット、レイテンシパーセンタイル、ロングコンテキスト挙動、量子化サポート、ストリーミング、バッチ処理・並行処理、デプロイ複雑度を計測している。

この記事は [Zenn記事: Ollamaでオンプレミス推論環境を構築しNginx認証付きでチーム共有する](https://zenn.dev/0h_n0/articles/e0ac1e1b30fcc9) の深掘りです。

## 背景と動機（Background & Motivation）

Apple SiliconのユニファイドメモリアーキテクチャはLLMの推論に好都合であり、プライバシー保護・コスト管理・低レイテンシのためにローカル推論への関心が高まっている。しかし、NVIDIA GPU向けに最適化されたvLLMのようなデータセンター向けスタック（HuggingFace Transformers on CUDA、PagedAttention付きvLLM）をApple Silicon上にそのまま適用することはできない。

著者らは、実運用（プロダクショングレード）のローカル推論に必要な要件を以下の5点と定義している：

1. KV/プロンプトキャッシュによる効率的なロングコンテキスト処理
2. 高速なTTFTとスムーズなストリーミング
3. バッチ処理・並行処理による複数ユーザーサービング
4. OpenAI互換APIの提供
5. インストール・デプロイの容易さ

従来のベンチマーク記事は単発のスループット測定に偏っており、上記5要件を総合的に評価した研究は存在しなかった。

## 主要な貢献（Key Contributions）

- **貢献1**: Apple Silicon上の5フレームワーク（MLX、MLC-LLM、Ollama、llama.cpp、PyTorch MPS）を、スループット・TTFT・量子化・ストリーミング・バッチ処理・API互換性・デプロイ複雑度の7軸で体系的に比較
- **貢献2**: 再現性の確保として、スクリプト・生ログ・プロットコード・環境マニフェスト（OSバージョン、コミットハッシュ）を公開
- **貢献3**: ユースケース別の推奨フレームワーク選択ガイドラインを提示

## 技術的詳細（Technical Details）

### 実験環境と計測メトリクス

**ハードウェア**: Mac Studio, Apple M2 Ultra, 24 CPUコア, 76 GPUコア, 192GB ユニファイドメモリ

**フレームワークバージョン**:
- MLX v0.26
- MLC-LLM（コミット 3d42929）
- llama.cpp（コミット b5963）
- Ollama v0.10.1
- PyTorch 2.7.1（MPSバックエンド）

**モデル**: Qwen-2.5-Coder 3B（主要）、Qwen-2.5-7B-Instruct（スケーリングテスト用）

**量子化**: FP16/bf16ベースライン、int8、int4。MLXはmixed-bit（3/4/6/8-bit）、MLC-LLMはAWQ/GPTQ、llama.cppはGGUF 4/5/8/16。

**計測メトリクス**:

| メトリクス | 定義 |
|----------|------|
| TTFT | クライアント側で最初のトークンが利用可能になるまでの壁時計時間 |
| スループット | (a) decode throughput: 生成トークン数 / デコード時間、(b) end-to-end throughput: 生成トークン数 / (prefill + decode)時間 |
| レイテンシパーセンタイル | エンドツーエンドレイテンシのp50, p90, p99 |
| コールドスタート時間 | モデルロード＋初期化レイテンシ |
| メモリフットプリント | RSS + フレームワーク報告のデバイスメモリ使用量（Metal metrics） |

**実験手順**: 各フレームワーク × モデル × 量子化 × プロンプト長の組み合わせを N=10 試行で実行。ランダムシード・トークナイザバージョン・サンプリングパラメータを固定。

### スループット比較結果

著者らの報告による定常スループットのランキング（M2 Ultra, Qwen-2.5ファミリ）:

| フレームワーク | 定常スループット（tok/s） | inter-tokenレイテンシ |
|--------------|----------------------|---------------------|
| MLX | ~230 | 5-7ms, p99 ~12ms |
| MLC-LLM | ~190 | ~13ms |
| llama.cpp | ~150（短コンテキスト） | 中程度 |
| Ollama | 20-40 | 中程度 |
| PyTorch MPS | ~7-9 | 高い |

著者らによれば、MLXはApple Metal/Neural Engineとの密な統合によりGPU利用率90%以上を達成し、CPU使用率を3%未満に抑えている。MLC-LLMはTVM コンパイルカーネルにより、特に中程度のプロンプト（≤16kトークン）でMLXより高速なTTFTを達成している。

**ロングコンテキストでの性能変化**:

著者らは、コンテキスト長が性能に与える影響について以下のように報告している：

- **MLC-LLM**: paged KV caching（vLLM類似の設計）により、32k-128kトークンでも安定したスループット（~500 tok/s prefill, ~190 tok/s decode）を維持
- **MLX**: 回転式KVキャッシュ（デフォルト4kトークンウィンドウ）で安定だが、100kトークン時にメモリ効率は~40-50GB
- **Ollama**: paged attentionなし。32kトークン超でスループットが~1.2 tok/sに急落
- **llama.cpp**: セッション単位のスライディングウィンドウキャッシュのみで、32k超でスループット崩壊

$$
\text{Comparative Ranking:} \quad \text{MLX} \; (\sim230) > \text{MLC-LLM} \; (\sim190) > \text{llama.cpp} \; (\sim150) > \text{Ollama} \; (20\text{-}40) > \text{PyTorch MPS} \; (\sim7\text{-}9)
$$

ここで括弧内の数値はtok/sで、論文Figure 1（M2 Ultra, Qwen-2.5ファミリ, 定常状態）からの報告値である。

### NVIDIA GPU環境との比較

著者らは、NVIDIA A100 + vLLM環境は絶対性能で Apple Silicon の 5-10倍 高いスループットを達成すると報告している。ただし、Apple Siliconフレームワークは急速に成熟しており、プロダクショングレードのオンデバイス推論に実用的な選択肢になりつつあるとも指摘している。

### コールドスタート挙動

| フレームワーク | 初期化時間 | 備考 |
|--------------|----------|------|
| MLC-LLM | ~11s | 初回TVM コンパイル後。キャッシュ済みなら最速起動 |
| MLX | ~31s | 起動は遅いが定常スループットで勝る |
| llama.cpp | <0.5s | GGUF キャッシュ済みの場合 |
| Ollama | ~0.6s | サービス起動後 |
| PyTorch MPS | ~3s | 小型モデルのみ安定 |

### 量子化サポートの比較

| フレームワーク | 量子化フォーマット | 特徴 |
|--------------|-----------------|------|
| MLC-LLM | AWQ, GPTQ, FP8, mixed precision | HuggingFace取り込み + TVMコンパイル。最も柔軟 |
| MLX | mixed-bit 3/4/6/8-bit, GPTQ | Apple最適化チューニングパイプライン。事前量子化モデル利用可 |
| llama.cpp | GGUF 4/5/8/16-bit | 内蔵量子化器。GGUFフォーマットに限定 |
| Ollama | GGUF レジストリのみ | 一貫性あるがCore ML最適化なし |
| PyTorch MPS | INT4/INT8実験的, bf16不安定 | 大型モデルで頻繁にクラッシュ |

著者らの実験では、AWQ 4-bitモデルはFP16比でメモリ約50%削減（3Bモデルで~1.6GB）かつスループット約10%向上（~210 tok/s vs ~190 tok/s）を達成したと報告されている。

### KVキャッシュ設計の比較

| フレームワーク | KVキャッシュ方式 |
|--------------|---------------|
| PyTorch MPS | 最小限、4GBテンソルキャップ、OOM頻発 |
| llama.cpp | スライディングウィンドウ、セッション単位、クロスリクエスト再利用なし |
| Ollama | Prefix再利用（LRU）、ページングなし、セッションスコープ |
| MLC-LLM | Paged KV（vLLM方式）、128kトークンまで効率的 |
| MLX | 回転式KV（設定可能ウィンドウ）、プロンプトキャッシュをディスクに保存 |

Ollamaのprefix再利用について、著者らは反復的なコーディングシナリオでレイテンシ約23%削減・キャッシュヒット率80%以上を観測したと報告している。ただし、paged attentionの欠如により32kトークン超ではメモリ使用量が~56GBに達し、100kトークンのプロダクションスケールには適さないとしている。

### ストリーミングとAPI互換性

| フレームワーク | ストリーミング | OpenAI互換API |
|--------------|------------|--------------|
| PyTorch MPS | Pythonループのみ | なし（ライブラリ） |
| llama.cpp | ローカルコールバック/stdout | コミュニティサーバー（部分的） |
| Ollama | 組み込みSSEサーバー、安定 | 組み込み（/completions, /chat/completions、SDKあり） |
| MLC-LLM | Python + REST/SSE | 最も包括的（completions, chat, embeddings, SDK） |
| MLX | Pythonジェネレータ | コミュニティラッパー（mlx-openai-server） |

著者らは、Ollamaが最もターンキーなストリーミング体験を提供する一方、MLX/MLC-LLMの方がスループットで優れると報告している。

### バッチ処理と並行処理

著者らによれば、Apple Siliconの5フレームワークのいずれもvLLMの**continuous batching**を再現できていない。

- **MLC-LLM**: 現時点で最も強力なバッチ処理/並行処理を提供。内蔵マルチワーカーHTTP/SSEサーバーとTVMコンパイルカーネルにより、最大8クライアントまでテイルレイテンシを抑制
- **MLX**: 生のスループットは最高だが、単一シーケンスを逐次処理。並行処理には外部オーケストレータ（Ray Serve、BentoMLなど）が必要
- **Ollama**: ワーカープールとリクエストキューによる並行処理をサポート。ただし負荷増加時はcooperative time-slicingに近い挙動で、真のcontinuous batchingではない。1-3並列ユーザーでは十分だが、それ以上ではスループットが急落

### デプロイ複雑度とエコシステム

| フレームワーク | デプロイ特性 | GitHub Stars |
|--------------|-----------|-------------|
| Ollama | ワンコマンドインストール、最も簡単 | 75k+ |
| MLX | pip install後すぐ動作、プロダクションにはラッパー必要 | ~1.3k（成長中） |
| MLC-LLM | pip + TVMコンパイル（20-30分）、SDKは充実 | 21k |
| llama.cpp | CMakeビルド必要、Docker/K8s非公式 | 多数 |
| PyTorch MPS | pip install、プロダクション不適 | — |

## 実験結果の再現性

著者らはスクリプト、生ログ、プロットコード、環境マニフェスト（OS/ツールチェーンバージョン、コミットハッシュ、モデルカード、変換コマンド）を公開している。外部干渉を排除するため、Spotlight indexing、Time Machine、iCloudの同期を無効化して計測を行ったと記載されている。

## 実運用への応用（Practical Applications）

Zenn記事で紹介されたOllamaによるオンプレミスLLM推論環境の文脈では、本論文の知見は以下のように適用できる。

**チーム規模と推論エンジンの選択**:

- **1-3人の開発チーム**: OllamaはZenn記事の通り最も実用的。ワンコマンドセットアップ、OpenAI互換API、Docker Compose対応が利点
- **4-8人の中規模チーム**: MLC-LLMの検討を推奨。paged KVキャッシュによるロングコンテキスト対応とmicro-batch処理が、Ollamaの弱点を補う
- **Apple Silicon Mac環境**: MLXがスループット最優先の場合に最適だが、サービングには外部ラッパーが必要

**Ollamaの限界を理解した上での運用**:

本論文は、Ollamaが**デベロッパーエルゴノミクスを最優先**し、スループットとTTFTでは他フレームワークに劣ることを定量的に示している。Zenn記事で触れられているOllamaの`OLLAMA_NUM_PARALLEL`による並列制御は、本論文の知見と一致する — 並列数を増やしてもcooperative time-slicingであるため、true continuous batchingのvLLMほどのスケーラビリティは期待できない。

## 関連研究（Related Work）

- **vLLM / PagedAttention** (Kwon et al., SOSP 2023): KVキャッシュのページング管理によりGPU環境で2-4倍のスループット改善を達成。本論文はApple Silicon版の各フレームワークがこの設計をどこまで取り込んでいるかを評価
- **FlashAttention** (Dao et al., NeurIPS 2022): IO-awareなアテンション計算によるGPUメモリアクセス最適化。MLXのMetal統合やMLC-LLMのTVMカーネルは同様のアプローチをApple GPUに適用
- **GPTQ / AWQ**: ポストトレーニング量子化手法。MLC-LLMはこれらを最も柔軟にサポートし、MLXはApple最適化のmixed-bit量子化を提供

## まとめと今後の展望

本論文は、Apple Silicon上のローカルLLM推論において**MLXとMLC-LLMが唯一のプロダクションレディランタイム**であることを明確に示した。MLXはスループットとシステム効率で、MLC-LLMはKVキャッシュ管理とAPI互換性で優位性を持つ。Ollamaはプロトタイピングとワンコマンドセットアップで依然として最も容易な選択肢だが、スループットで1桁の差がある。

今後の課題として、マルチGPU/マルチノード構成での評価、より多様なモデルアーキテクチャでの検証、エネルギー効率の詳細測定が挙げられている。
