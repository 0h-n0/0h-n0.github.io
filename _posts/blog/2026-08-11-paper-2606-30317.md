## 論文概要（Abstract）

本記事は [MCP Server Architecture Patterns for LLM-Integrated Applications](https://arxiv.org/abs/2606.30317) の解説記事です。

Rodriguesらは、Anthropicが2024年11月に公開したModel Context Protocol（MCP）を対象に、独立に開発された15のMCPサーバーを分析し、繰り返し出現するアーキテクチャパターンを体系化している。著者らは5つのアーキテクチャパターンと4つのアンチパターンを特定し、トランスポートレイテンシ測定やツール数とLLM精度の関係など定量的な知見を報告している。

## 背景と動機（Background & Motivation）

LLMをプロダクション環境で活用する際、外部データソースやツールとの連携が不可欠となる。しかし各LLMプロバイダが独自のツール連携仕様を定義しており、統一的な設計指針が存在しなかった。Anthropicが2024年11月にModel Context Protocol（MCP）をオープン仕様として公開したことで、標準的なフレームワークが登場した。

MCPは急速に普及し多数のサーバー実装が開発されているが、設計判断は暗黙知として各チームに閉じている。Rodriguesらは54のMCPサーバーを対象としたコーディング分析（うち15サーバーを深掘り）を実施し、繰り返し出現するパターンとアンチパターンを特定することで、MCP開発のベストプラクティスを産業界に提供することを目指している。

## 主要な貢献（Key Contributions）

- **5つのアーキテクチャパターンの特定**: Resource Gateway、Tool Orchestrator、Stateful Session Server、Proxy Aggregator、Domain-Specific Adapterの5パターンを体系化
- **4つのアンチパターンの定義**: God Tool、Unsanitized Resource Content、Synchronous Long-Running Operations、Missing Tool Descriptionsを特定し、回避指針を提示
- **定量的な信頼性評価**: Cohen's kappa = 0.76（2名の評価者間一致度）で、パターン分類の客観性を担保
- **トランスポート層のレイテンシ測定**: stdio、streamable-httpの各構成でp50レイテンシを計測し、設計上のトレードオフを定量化
- **ツール数とLLM精度の関係**: Claude Haiku 4.5は10-15ツール、Sonnet 4は20-30ツールで精度低下が始まるという閾値を報告
- **横断的関心事の整理**: 認証（トランスポート層）、構造化エラーハンドリング、バージョニング、可観測性ログの4つを整理

## 技術的詳細（Technical Details）

### 5つのアーキテクチャパターン

著者らが特定した5つのパターンを以下の表に整理する。

| パターン | 目的 | 典型的なユースケース | ツール数の目安 |
|---------|------|-------------------|-------------|
| Resource Gateway | バックエンドデータの安全な公開 | DBコネクタ、ドキュメントブリッジ、API Wrapper | 3-8 |
| Tool Orchestrator | 複数システムにまたがるワークフローの単一ツール化 | CI/CD自動化、DevOps | 5-12 |
| Stateful Session Server | ターン間のコンテキスト保持 | コードエディタ、DBトランザクション | 4-10 |
| Proxy Aggregator | 複数の上流サーバーを単一エンドポイントに集約 | マルチサーバー統合 | 制限あり（後述） |
| Domain-Specific Adapter | 複雑なAPIのLLM向け変換 | 入力正規化、出力エンリッチメント | 3-6 |

**Resource Gateway** は、バックエンドのデータソース（データベース、ファイルシステム、外部API）をMCPのresourceインターフェースで公開するパターンである。著者らは、アクセス制御の単一実施点（single enforcement point）を設けることで、LLM側からの不正なデータアクセスを防止できると報告している。

**Tool Orchestrator** は、複数の外部システムを跨ぐワークフローを単一の複合ツールとして公開するパターンである。LLMの推論負荷を軽減し、複雑なマルチステップ処理をサーバー側に隠蔽できる利点がある。Zenn記事で紹介されているCI/CDログ調査エージェントは、このパターンの典型的な適用例といえる。

**Stateful Session Server** は、セッションIDを用いてターン間の状態を保持するパターンである。コードエディタやDBトランザクションなど、連続した操作が必要なユースケースで有効である。

**Proxy Aggregator** は、複数の上流MCPサーバーを単一エンドポイントとして集約するパターンである。著者らはstatic-merge（全ツールをフラットに統合）とscoped（名前空間で分離）の2つのバリアントを識別している。ツール数の増加に伴いLLM精度が低下するため、Haiku 4.5では10-15ツール以下、Sonnet 4では20ツール以下に抑えることを推奨している。

**Domain-Specific Adapter** は、複雑な外部APIをLLMが扱いやすい形に変換するパターンである。入力の正規化（あいまいなユーザー指示を構造化入力に変換）と出力のエンリッチメント（生のAPI応答にコンテキスト情報を付加）の2つの変換を行う。

### 4つのアンチパターン

| アンチパターン | 問題 | 対策 |
|-------------|------|------|
| God Tool | 単一ツールに過剰な責務を集中 | 単一責任原則に従いツールを分割 |
| Unsanitized Resource Content | バックエンドの生データをそのままLLMに渡す | サニタイズ・フィルタリング層の追加 |
| Synchronous Long-Running Operations | 長時間処理を同期で実行しタイムアウト | 非同期処理パターンの採用 |
| Missing Tool Descriptions | ツールの説明が不十分でLLMが適切に選択できない | 詳細なdescription・パラメータ説明の記述 |

### トランスポート層のレイテンシ

著者らはMCPの3つのトランスポート構成でレイテンシを測定している（論文Table記載値）。

| トランスポート構成 | p50レイテンシ |
|------------------|-------------|
| stdio | 0.01 ms |
| streamable-http（loopback） | 0.39 ms |
| streamable-http（same-region） | 30.4 ms |

stdioはプロセス間通信であるため高速だが、リモートアクセスが必要な場合はstreamable-httpを選択する。same-regionでも30.4msのp50レイテンシが発生するため、レイテンシに敏感なユースケースではstdioの利用を著者らは推奨している。

## 実装のポイント（Implementation）

**ツール設計の粒度**: God Toolアンチパターンを避けつつ、過度な分割によるツール数増加も防ぐ。著者らの実験結果に基づけば、1サーバーあたり10-15ツール以下（Haiku 4.5の場合）が望ましい。

**ツール説明の充実**: LLMがツールを正しく選択するにはdescriptionフィールドの品質が決定的に重要である。パラメータの意味、想定入力形式、戻り値の構造を明記すべきである。

**認証の実装層**: 著者らは認証をトランスポート層で実施することを推奨している。プロトコル層やツール層での認証は複雑化やセキュリティホールの原因となる。

**エラーハンドリング**: 構造化されたエラー応答により、LLMがリトライや代替手段を選択可能となる。生のスタックトレースをLLMに渡すことはUnsanitized Resource Contentアンチパターンに該当する。

**可観測性**: ツール呼び出しのログ記録とトレーシング設定により、プロダクション環境でのデバッグと性能分析が可能となる。

## Production Deployment Guide

本論文はMCPサーバーのアーキテクチャパターンを体系化しており、実装セクションを含むため、AWS上でのデプロイガイドを提示する。

### AWS実装パターン（コスト最適化重視）

以下は2026年8月時点のAWS ap-northeast-1（東京）リージョン料金に基づく概算値である。実際のコストはトラフィックパターンやバースト使用量により変動するため、最新料金はAWS料金計算ツールで確認を推奨する。

| 構成 | トラフィック量 | 主要サービス | 月額概算 |
|------|-------------|------------|---------|
| Small | ~100 req/日 | Lambda + DynamoDB + API Gateway | $50-150 |
| Medium | ~1,000 req/日 | ECS Fargate + ALB + ElastiCache | $300-800 |
| Large | 10,000+ req/日 | EKS + Karpenter + Spot Instances | $2,000-5,000 |

**Small構成（Serverless）**: Lambda関数でMCPサーバーを実行し、DynamoDBでセッション状態を保持する。API Gatewayをstreamable-httpエンドポイントとして利用する。月額内訳の目安はLambda $5-20、DynamoDB $5-15、API Gateway $10-30、CloudWatch $5-10である。

**Medium構成（Hybrid）**: ECS Fargateで常駐プロセスとして稼働させる。Stateful Session Serverパターンではコンテナ常駐が必要なためこの構成が適する。ElastiCacheでセッション共有、ALBで負荷分散する。

**Large構成（Container）**: EKSにKarpenterを導入しSpot Instances優先で自動スケーリングする。Proxy Aggregatorで複数サーバーを統合する場合に適する。Spot活用で最大90%のコスト削減が期待できる。

### 運用・監視設定

**CloudWatch Logs Insights クエリ**: ツール呼び出しのレイテンシ分析（P50/P95/P99をtool_name別に集計）と、1時間あたり500回超のコスト異常検知を設定する。

```
fields @timestamp, tool_name, duration_ms
| filter event = "tool_invocation"
| stats percentile(duration_ms, 50) as p50, percentile(duration_ms, 95) as p95,
        percentile(duration_ms, 99) as p99, count() as invocations by tool_name
| sort invocations desc
```

**CloudWatch アラーム設定**: Lambda実行時間のP95が3秒超過で2期間連続した場合にSNS通知するアラームを設定する。`put_metric_alarm`でMetricName=Duration、Statistic=p95、Threshold=3000ms、EvaluationPeriods=2を指定する。

**X-Ray トレーシング設定**:

```python
from aws_xray_sdk.core import xray_recorder, patch_all

patch_all()  # boto3の自動計装

@xray_recorder.capture("mcp_tool_invocation")
def handle_tool_call(tool_name: str, params: dict) -> dict:
    """MCPツール呼び出しをX-Rayでトレースする。"""
    subsegment = xray_recorder.current_subsegment()
    subsegment.put_annotation("tool_name", tool_name)
    subsegment.put_metadata("params", params, "mcp")
    result = execute_tool(tool_name, params)
    return result
```

**Cost Explorer自動レポート**: 日次でMCPサーバー関連コストを集計し、$100/日超過時にSNS通知する。

```python
import boto3
from datetime import date, timedelta

def daily_cost_report(sns_topic_arn: str) -> None:
    """日次コストレポートを取得し、閾値超過時にSNS通知する。"""
    ce = boto3.client("ce", region_name="us-east-1")
    today, yesterday = date.today(), date.today() - timedelta(days=1)
    response = ce.get_cost_and_usage(
        TimePeriod={"Start": str(yesterday), "End": str(today)},
        Granularity="DAILY", Metrics=["UnblendedCost"],
        Filter={"Tags": {"Key": "Project", "Values": ["mcp-server"]}},
        GroupBy=[{"Type": "DIMENSION", "Key": "SERVICE"}],
    )
    total = sum(float(g["Metrics"]["UnblendedCost"]["Amount"])
                for r in response["ResultsByTime"] for g in r["Groups"])
    if total > 100:
        boto3.client("sns", region_name="ap-northeast-1").publish(
            TopicArn=sns_topic_arn, Subject="MCP Server Cost Alert",
            Message=f"Daily cost exceeded $100: ${total:.2f}")
```

### コスト最適化チェックリスト

**アーキテクチャ選択**:
- [ ] トラフィック量に応じた構成を選択（~100 req/日: Serverless、~1000 req/日: Hybrid、10000+ req/日: Container）
- [ ] Stateful Session Serverパターンの場合はFargate以上を選択
- [ ] Proxy Aggregatorパターンの場合はツール数上限を設計に反映

**リソース最適化**:
- [ ] EC2/EKS: Spot Instancesを優先（最大90%削減）
- [ ] Reserved Instances: 1年コミットで最大72%削減
- [ ] Savings Plansの適用を検討
- [ ] Lambda: メモリサイズを512MB-1024MBの範囲で最適化（Power Tuningツール使用）
- [ ] EKS: Karpenterで未使用ノードの自動統合を有効化

**LLMコスト削減**:
- [ ] Bedrock Batch API使用で50%削減（非リアルタイム処理）
- [ ] Prompt Caching有効化で30-90%削減
- [ ] モデル選択ロジック実装（簡易タスクはHaiku、複雑タスクはSonnet）
- [ ] 入力トークン数の制限（Domain-Specific Adapterでの前処理）

**監視・アラート**:
- [ ] AWS Budgets: 月次予算の80%/100%でアラート
- [ ] CloudWatch Anomaly Detection: ツール呼び出し数の異常検知
- [ ] Cost Anomaly Detection: サービス別コスト異常の自動検出
- [ ] 日次コストレポートのSNS通知設定

**リソース管理**:
- [ ] 未使用のLambda関数・ECSタスク定義の削除
- [ ] タグ戦略: Project/Environment/CostCenterタグの必須化
- [ ] DynamoDB TTL: セッションデータの自動削除設定
- [ ] CloudWatch Logs: 保持期間の設定（30日/90日）
- [ ] 開発環境: 夜間・週末のEKSノード停止

## 実験結果（Results）

### 評価者間一致度

著者らは2名の評価者が54のMCPサーバーを独立に分類し、Cohen's kappa = 0.76を達成したと報告している。この値はsubstantial agreement（実質的一致）に分類され、パターン分類の客観性が確認された。

### トランスポートレイテンシ

著者らの測定結果を以下に示す（論文のTable記載値）。

| 構成 | p50レイテンシ | 用途 |
|------|-------------|------|
| stdio | 0.01 ms | ローカルプロセス間通信 |
| streamable-http loopback | 0.39 ms | 同一マシン内HTTP |
| streamable-http same-region | 30.4 ms | 同一リージョン内ネットワーク |

stdioとstreamable-http（loopback）の間には約39倍のレイテンシ差があり、loopbackとsame-regionの間にはさらに約78倍の差がある。ツール呼び出しが1回の処理で複数回発生する場合、このレイテンシ差は累積的に影響する。

### ツール数とLLM精度

著者らは、MCPサーバーに登録されたツール数がLLMのツール選択精度に与える影響を測定している。Claude Haiku 4.5は10-15ツールの範囲で精度低下が始まり、Sonnet 4は20-30ツールで同様の低下が観測されたと報告している。この結果は、Proxy Aggregatorパターンにおけるツール数の上限設計に直接的な示唆を与える。

## 実運用への応用（Practical Applications）

本論文の知見は、Zenn記事で紹介されているFastMCPを用いたCI/CDログ調査エージェントに直接的に適用可能である。

Zenn記事のCI/CDログ調査エージェントは、Tool Orchestratorパターンの典型例である。複数のCI/CDシステム（GitHub Actions、Jenkins等）のログ取得・解析を単一のMCPサーバーに集約し、LLMの推論負荷を軽減している。本論文の知見に基づけば、以下の設計改善が考えられる。

**ツール数の制御**: 論文の実験結果に基づき、1サーバーあたりのツール数をHaiku 4.5利用時は10-15以下に制限する。CI/CDログ取得、ログ解析、アラート通知をそれぞれ独立したMCPサーバーに分割し、Proxy Aggregatorで統合する構成も検討に値する。

**ツール説明の充実**: Missing Tool Descriptionsアンチパターンを避けるため、FastMCPの`@mcp.tool()`デコレータにおけるdescription記述を充実させる。パラメータの期待値やエラー時の挙動を明示的に記載することで、LLMのツール選択精度が向上する。

**トランスポート選択**: ローカル開発ではstdio（0.01ms）、プロダクションではstreamable-http（30.4ms）を使い分ける設計が有効である。

## 関連研究（Related Work）

- **OpenAI Function Calling仕様**: プロバイダ固有のツール呼び出し仕様。MCPとはスコープが異なるが、ツール記述のスキーマ設計に共通点があり、本論文のツール説明に関する知見は適用可能である。
- **LangChain Tools / LangGraph**: フレームワーク固有のツール抽象化レイヤー。MCPが標準プロトコルとしてフレームワーク非依存であるのに対し、Python固有のツール定義を提供する。両者は補完的な関係にある。
- **A2A（Agent-to-Agent Protocol）**: Googleが提案するエージェント間通信プロトコル。MCPがLLMと外部ツールの接続に焦点を当てるのに対し、A2Aはエージェント間協調に特化しており、Proxy Aggregatorパターンとの関連性が高い。

## まとめと今後の展望

Rodriguesらは、54のMCPサーバーを体系的に分析し、5つのアーキテクチャパターンと4つのアンチパターンを特定した。Cohen's kappa = 0.76の評価者間一致度により、分類の客観性が確認されている。トランスポートレイテンシの定量測定やツール数と精度の関係は、MCP実装における設計判断の根拠となる。

今後の研究方向として、マルチエージェント環境でのMCPサーバー協調、動的なツール登録・解除、およびMCPサーバーの自動テスト手法が挙げられている。
